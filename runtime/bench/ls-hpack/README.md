# `ls-hpack` Bench Tooling

`runtime/deps/ls-hpack` is byte-identical to official upstream v2.3.5.
Production HPACK hardening is generated by `build.zig`: the build applies the
same patch series into Zig's cache and compiles the HPACK shim against that
generated source. The upstream CMake suite and encode-qif bench apply the same
four patches to a temporary copy:

- `0001-ls-hpack-harden-decoder.patch`
- `0002-ls-hpack-encoder-precompute.patch`
- `0003-ls-hpack-fixups.patch`
- `0004-ls-hpack-precomputed-static-miss.patch`

Date:
`2026-07-16`

## Test Run

The production Zig HPACK shim was built against the generated patched
`runtime/deps/ls-hpack` copy. The upstream CMake test suite was also run against a
patched `runtime/deps/ls-hpack` copy in `Debug` with:

```sh
cmake -S "$work_dir/ls-hpack" -B "$work_dir/build" \
  -DCMAKE_BUILD_TYPE=Debug \
  -DLSHPACK_FAST_DECODE=ON \
  -DCMAKE_C_FLAGS="-fsanitize=address -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address"
cmake --build "$work_dir/build" -j
ASAN_OPTIONS=detect_leaks=1:abort_on_error=1 \
  ctest --test-dir "$work_dir/build" --output-on-failure
```

Result: `6/6` tests passed.

A second full lane used UndefinedBehaviorSanitizer with:

```text
-fsanitize=undefined -fno-sanitize=alignment -fno-sanitize-recover=undefined
```

The alignment check is excluded because the bundled xxHash intentionally
performs unaligned loads; all other UBSan checks halt on first error. Result:
`6/6` tests passed.

## Bench Run

Command:

```sh
runtime/bench/ls-hpack/run.sh
```

Environment used by the script:
- Compiler: `clang`
- Flags: `-O3 -DNDEBUG -std=c99 -DLS_HPACK_USE_LARGE_TABLES=1 -DLSHPACK_DEC_HTTP1X_OUTPUT=0 -DLSHPACK_DEC_CALC_HASH=0`

The runner copies `runtime/deps/ls-hpack` (upstream) twice. The `patched` copy gets
the hardening + bench/tooling patch series applied, so it matches the generated
production source and adds the `encode-qif` enhancements; the `original` copy
stays unmodified to provide the baseline microbench numbers.

The final measurement reused those verified binaries for 11 CPU-6-pinned
samples. Each binary received a separate warm-up, sample order alternated
between original-first and patched-first, decode/encode samples used five
million iterations, and QIF samples used 500,000. No sample was deleted. Two
known-overlap pilots were excluded up front, and one complete short-sample
series was rejected wholesale after it failed the predeclared dispersion
threshold. An accidental duplicate runner was stopped after one complete
sample; the entire concurrently overlapped series was excluded. The final
series began after both exited.
The accepted CPU-6 pre-gate was `97.99%` idle and its post-gate averaged
`94.61%` idle.

Every timing-normalized log was identical, including counters and wire bytes,
and the measured patched source matched the final reviewed tree byte-for-byte.
Values are median in `ns/header` (`ns/iter` for the malformed literal), median
absolute deviation, and full min–max across all 11 samples:

## Notes

- `missing_literal_value` demonstrates the security behavior difference:
  pristine upstream accepts and advances on the truncated literal; patched
  returns `LSHPACK_ERR_BAD_DATA` without advancing.
- `valid_decode`, raw encode, and preindexed encode are neutral at this
  resolution because their paired direction was inconsistent.
- The default QIF path improved consistently in all 11 pairs; its paired median
  reduction was `36.91%`. A separate complete 11-sample replication also won
  all 11 pairs, with a `36.07%` paired median reduction.

## Temporary Optimization Study

The follow-up experiment stayed under `/tmp/collo-lshpack-opt-study`; none of
its ABI prototypes are production changes. It compared:

1. `baseline`: the current C call and metadata preparation per header;
2. `prepared`: reusable static indexes, hashes, and contiguous custom storage,
   still called once per header;
3. `batch`: one C call per block while retaining per-encode metadata work;
4. `prepared_batch`: reusable metadata plus one C call per block.

The harness used clang 18 with `-O3 -DNDEBUG`, separate translation units and
no LTO. It was pinned to CPU 6 on an Intel Core Ultra 9 185H under WSL2. Every
variant produced byte-identical HPACK and the baseline stream was decoded back
to the original headers. Two independent runs collected 11 rotated-order
samples per variant and view. The ranges below span the two independent runs;
MAD is the within-run median absolute deviation in `ns/header`. Wire bytes were
identical for all four variants and are reported after encoder warm-up, when
dynamic-table references make the large-header case only four bytes per block.

The review-discovered zero-length copy guard was regenerated after these
encoder measurements, but it changes only decoder insertion. Recompiling the
final patched `lshpack.c` with the harness's exact flags produced identical
encoder symbol addresses and byte-identical encoder `.text` through
`lshpack_enc_set_max_capacity` (SHA-256
`8fe0baf6...9543` for both slices). The encoder-only comparisons below
therefore apply to the final queue; the canonical decoder microbench was rerun
separately from the post-guard tree.

### Reused preparation (`hot`)

| Scenario | Bytes/block | Baseline median (MAD) | `prepared` median | `batch` median | `prepared_batch` median (MAD) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Typical 8-header request | `26.000` | `27.91–28.98` (`0.45–1.23`) | `11.40–11.77` | `26.60–26.75` | `10.67–11.12` (`0.43–0.59`) |
| 64-block rotating corpus | `96.056` | `51.72–56.06` (`0.92–1.98`) | `28.02–30.53` | `49.20–53.40` | `26.83–29.52` (`1.42–2.17`) |
| Three custom values over 512 B | `4.000` | `136.20–138.30` (`5.66–7.41`) | `16.42–16.75` | `133.86–135.32` | `15.39–16.11` (`0.67–1.36`) |

Against baseline, `prepared_batch` reduced latency by `61.7–61.8%`
(`2.61–2.62x`) for the typical request, `47.3–48.1%` (`1.90–1.93x`) for the
rotating corpus, and `88.4–88.7%` (`8.59–8.85x`) for large custom values.

Batching without prepared metadata was much smaller: `4.2–8.2%` lower latency
for the typical request, about `4.8%` for the rotating corpus, and `0.6–3.2%`
for custom values over 512 B. The dominant cost is repeated lookup/hash/copy
work and, for large custom headers, repeated `malloc/free`; it is not the ABI
call by itself.

### Preparation paid for each block (`end_to_end`)

| Scenario | Bytes/block | Baseline median (MAD) | `prepared` median | `batch` median | `prepared_batch` median (MAD) | Combined result |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Typical 8-header request | `26.000` | `28.49–28.62` (`0.67–1.18`) | `28.88–31.31` | `26.52–26.85` | `27.96–30.95` (`0.87–1.18`) | `1.9%` faster to `8.2%` slower |
| 64-block rotating corpus | `96.056` | `50.59–50.70` (`1.81–3.24`) | `47.80–50.50` | `49.46–51.22` | `44.63–46.42` (`1.05–1.24`) | `8.5–11.8%` faster |
| Three custom values over 512 B | `4.000` | `135.12–143.80` (`4.33–5.44`) | `123.53–130.45` | `134.46–141.48` | `129.20–129.77` (`2.09–6.80`) | `4.4–9.8%` faster |

The typical request is therefore inconclusive when preparation is paid on
every block. For the large custom case, the per-header `prepared` variant was
more stable than `prepared_batch`, improving by `8.6–9.3%`.

The actionable optimization is therefore a compact prepared-header plan only
where Collo can reuse it across encodes. A batch ABI alone is not significant,
and eagerly preparing one-use typical requests is not justified. The prototype
descriptor was 80 bytes per header, so a production design should compact the
cached flags/indexes/hashes rather than expose `lsxpack_header` directly.

## Production Prepared-Headers Validation

The implemented `PreparedHeaders` plan owns a packed name/value buffer and a
20-byte descriptor per header (75% smaller than the 80-byte prototype). Encoding
a prepared block crosses the Zig/C ABI once and reuses the static indexes,
static misses, and hashes computed during preparation. The raw API remains the
path for blocks that will be encoded only once.

The final production shim was compiled together with the generated patched
ls-hpack v2.3.5 source as separate translation units, using clang 18 with
`-O3 -DNDEBUG -std=c99` and no LTO. The validation harness stayed under
`/tmp/collo-hpack-static-miss-final`, was pinned to CPU 6, warmed each path,
rotated raw/prepared order, retained all 11 paired samples, and verified both
byte-identical wire output and successful decode for every corpus.

Values are median `ns/header`; MAD is median absolute deviation. `Hot` reuses
the prepared plan, which is the intended API contract:

| Scenario | Raw median (MAD) | Prepared median (MAD) | Prepared wins | Paired median delta | Median speedup |
| --- | ---: | ---: | ---: | ---: | ---: |
| Typical 8-header request | `36.78` (`1.04`) | `14.91` (`0.82`) | `11/11` | `-59.70%` | `2.47x` |
| 64-block rotating corpus | `55.42` (`1.57`) | `28.87` (`0.87`) | `11/11` | `-46.90%` | `1.92x` |
| Custom values over 512 B | `149.07` (`2.82`) | `21.17` (`1.16`) | `11/11` | `-85.44%` | `7.04x` |

All three corpora meet the strict all-pairs direction criterion. Their direction
also matches the earlier two-run prototype study. This final rerun includes the
review fix that records a precomputed static-table miss instead of repeating the
static name/value and name-only probes during every encode.

When preparation was deliberately paid again for every block, median ratios were
`0.81x`, `0.85x`, and `1.07x` for the three corpora, with `1/11`, `0/11`, and
`10/11` prepared wins. The modest large-value result includes C metadata
preparation but not the Zig plan's two owning allocations, so it is an optimistic
one-shot comparison; typical and rotating blocks are consistently slower. These
results do not justify eager preparation or an automatic one-use cache.

The final sources also passed a strict `-Wall -Wextra -Werror` build and a
check-only run with AddressSanitizer plus UndefinedBehaviorSanitizer (excluding
xxHash's intentional unaligned-load check), with leak detection and halt-on-first
error enabled.
