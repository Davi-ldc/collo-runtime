# Worker memory

This reference follows a worker's memory from its configuration to its death: the limit and the cgroup files the host derives from it, the marks a growing worker meets inside its process, how the server tells a memory death from a crash and records it, the OOM scores of the runtime's processes, and the memory the node spends on a worker outside the worker's own cgroup. The node's pressure levels, the reaper's plans and victim score, the memory gate and the caps belong to [scheduler.md](scheduler.md), which this page links for them; the sandbox order around the cgroup checks is in [security.md](security.md#birth-and-confinement), and the lane's side of a death in [request.md](request.md#failure-domains). The mechanics belong to the code and its `//!` headers: `common/cgroup.zig`, `host/cgroup_root.zig` and `host/cgroup.zig` for the cgroup, `zygote/worker_boot/cgroup.zig` and `zygote/child_boot.zig` for the child's checks, `worker/runtime/sentinel.zig` for the watch, `server/supervisor/usage_drain.zig` for the classification and `common/limits/process.zig` for the OOM scores. Paths are relative to `runtime/src/`, a file cited once with its path may appear by its bare name later in the same section, a reference reads `file.zig:symbol`, and the code wins wherever this page disagrees with it.

## The limit

A worker definition's `limits.memoryMiB` is the memory limit of each of its worker processes, shared by every route the process runs. It cascades from the built-in default of 128 MiB (`server/config/model.zig:default_settings`) through `globalSettings` to the definition, and a configuration synthesized from an entry module keeps the default (`server/config/synthesize.zig`). The parser takes a whole number from 16 to 65,536 (`server/config/parse.zig:Parser.readLimits`, `common/limits/server.zig:worker_memory_mib_min`, `worker_memory_mib_max`). These values derive from that number in bytes, written L (`model.zig:Limits.memoryBytes`); the host writes the cgroup files, with `pids.max` beside them, and the child sets the engine's trigger:

| Value | From L | Where | Bounds |
| --- | --- | --- | --- |
| `memory.high` | L | `common/cgroup.zig:memory.configureWorkerLimitsAt` | the sentinel's mark and the kernel's throttle |
| `memory.max` | 115% of L, rounded down to a page | `common/cgroup.zig:memory.maxBytes` | the kernel's OOM kill |
| `memory.oom.group` | 1 | `memory.configureWorkerLimitsAt` | an OOM kill takes every task of the leaf together |
| engine collection trigger | 90% of L | `common/cgroup.zig:memory.gcHeapLimitBytes` | what the engine allocates between two collections |
| tmpfs root | the smaller of 256 MiB and L, or a nonzero `COLLO_WORKER_FS_TMPFS_MIB` clamped to L | `server/supervisor/launcher.zig:resolveWorkerTmpfsSizeBytes`, `host/launch.zig:resolveTmpfsSizeBytes`, `common/ipc/messages.zig:WorkerInit.defaultTmpfsSizeBytes` | the bytes of the worker's files |
| `pids.max` | 128 whatever L is | `common/cgroup.zig:pids.DEFAULT_MAX` | the leaf's tasks, threads included |

No code writes `memory.swap.max`, `memory.low` or `memory.min` on a leaf, so those keep the kernel's defaults: swap bounded only by the leaf's ancestors, and no reclaim protection of the leaf's own.

The launcher thread writes the files before the fork (`server/supervisor/launcher.zig:Launcher.startFork`). `host/cgroup_root.zig:WorkerCgroupRoot.createWorkerDir` creates the leaf `worker-<fork_job_id>` and writes `memory.max`, `memory.high`, `memory.oom.group`, `cpu.max` and `pids.max` through its descriptor (`common/cgroup.zig:worker.configureLimitsAt`), and any failure there fails the launch as `cgroup_leaf`. The quota in `cpu.max` is one core for every worker, whatever its definition (`common/limits/worker.zig:cpu_max_cores`). The leaf's descriptor rides the fork request; the zygote checks that it names an empty cgroup2 directory (`zygote/worker_boot/cgroup.zig:validateEmptyWorkerCgroupDirFd`) and clones the child into it (`zygote/fork_loop.zig:serveForkRequests`), so the limits hold from the child's first instruction. On the fork reply, `host/cgroup.zig:adoptPreparedWorkerDir` reads `memory.high` and `cpu.max` back and rewrites the whole set only when they differ, which never happens to a leaf the launcher made. `WorkerInit` then carries L, the CPU cores and the tmpfs size to the child (`host/launch.zig:Machine.sendWorkerInit`).

The leaves live under the worker cgroup root, which the server creates at boot before it spawns the zygote (`server/boot/root.zig:serve`, `host/cgroup_root.zig:WorkerCgroupRoot.init`): `<own>/workers` when the cgroup the server started in, `<own>`, is delegated to it, after the server moves itself into `<own>/main`, or a `host-<pid>-<start>-<n>` directory under `COLLO_WORKER_CGROUP_ROOT`. Either way the memory, cpu and pids controllers are enabled for the leaves, and a server that cannot place them refuses to start. The zygote and the gateway are the server's children and stay in its cgroup; nothing gives them one of their own.

The child checks its leaf after `WorkerInit` arrives and before the VM resumes (`zygote/child_boot.zig:workerChildMainImpl`, `zygote/worker_boot/cgroup.zig:validateAndOpenWorkerMemoryEventsAt`), without allocating. The descriptor must name a cgroup2 directory holding every file the limits and events use, so a missing controller fails the check; the child's pid must be the leaf's only member; and the files must hold L in `memory.high`, `maxBytes` of L in `memory.max`, `WorkerInit`'s cores over the default period in `cpu.max`, and the default in `pids.max`. The kernel keeps `memory.high` and `memory.max` in whole pages, so these exact comparisons hold only while L is a multiple of the page size, which a whole number of MiB always is; `maxBytes` rounds the 115% down for the same reason. The child then opens `memory.events.local` for the sentinel and checks the membership and the limits again. A mismatch reports `invalid_worker_init` and fails the launch. `memory.oom.group` is not read back.

The leaf's `memory.current` holds what the worker brought into memory: its heap and stacks, the copies of zygote pages it wrote to, the files in its tmpfs, kernel memory charged to its tasks, and each page of a shared file it brought into memory first, whether a memfd page or a page of the binary or of a shared library that no other process had read, since the kernel charges a page to the cgroup that first instantiated it until the page is freed. The pages it still shares with the zygote are charged to the zygote's cgroup, which is the server's.

## A growing worker

A worker that keeps allocating crosses `memory.high` before `memory.max`. The engine's trigger counts only the bytes allocated since the last collection, so it fires at its own pace and may never fire before `memory.high` does:

| Mark | Reached when | What follows |
| --- | --- | --- |
| the engine's collection trigger | the bytes allocated since the last collection exceed 90% of L | JSC requests a collection; no allocation fails |
| `memory.high` | `memory.current` goes above L | the kernel throttles the leaf and counts `high`; the sentinel marks the page and ends the process |
| `memory.max` | `memory.current` reaches 115% of L and the kernel cannot reclaim | the kernel kills every task of the leaf and counts `oom_kill` |

### The engine's collection trigger

Once the VM resumes, the child sets the trigger to 90% of L (`zygote/child_boot.zig:workerChildMainImpl`, `bindings/root.zig:setGcMaxHeapSizeOverrideBytes`, `bindings/jsc/zygote/prepare_for_fork.cpp:collo_set_gc_max_heap_size_override_bytes`). The hook is patch `runtime/patches/webkit/0002-gc-max-heap-size-override.patch`: a process-global value that `JSC::effectiveGCMaxHeapSize` returns in place of `Options::gcMaxHeapSize` in `Heap::collectIfNecessaryOrDefer`. With `USE_BUN_JSC_ADDITIONS`, which the engine build turns on (`runtime/build/buildtool.zig`), that function requests a collection as soon as the bytes allocated in the current cycle exceed the value, and JSC's own trigger still runs below it. JSC sizes its own heap growth from `WTF::ramSize`, a figure computed once in the zygote, before any fork: the machine's RAM, or the tightest `memory.max` or `memory.high` from the zygote's own cgroup up to the root (`WTF::availableMemory`). Every worker inherits that figure, so the trigger is the one place where the engine learns of L. JSC's critical mode, which shrinks the collection budget once the process's resident size passes 80% of that same figure (`Heap::overCriticalMemoryThreshold`), learns nothing of L either, and a worker cannot read its own resident size: `WTF::memoryStatus` reads a `/proc/self/statm` descriptor opened once per process, which the child closes at boot when the zygote opened it and cannot open after its chroot, so the mode never engages in a worker. The trigger bounds what the engine allocates between two collections, and the live heap can grow past it.

Nothing in the runtime refuses the engine an allocation, and the worker has no address-space limit (`zygote/worker_boot/sandbox.zig:limits.apply` sets only `RLIMIT_NOFILE` and `RLIMIT_CORE`), so a heap that keeps growing meets `memory.high`, and the process ends with no JavaScript exception. An allocation the engine itself refuses, such as a string or buffer longer than it allows, throws `RangeError: Out of memory` (`JSC::createOutOfMemoryError`), which a handler can catch; uncaught, it ends the request with 500 and the error code `js_exception` (`worker/serve/response.zig:writeException`).

### The sentinel at `memory.high`

The sentinel is a thread of the worker (`worker/runtime/sentinel.zig:Sentinel`), which also stops JavaScript turns past their deadlines. It starts before the seccomp filter and before the route's entry is evaluated (`zygote/child_boot.zig:workerChildMainImpl`, `worker/runtime/root.zig:Runtime.startSentinel`), so all tenant code runs under its watch. `Sentinel.init` reads `memory.events.local` once as a baseline, and the thread then polls that descriptor for `POLLPRI` beside its command eventfd (`Sentinel.sentinelPollLoop`). The kernel signals the file on each memory event of the leaf, and the sentinel reads it again (`common/cgroup.zig:memory.readEvents`) and acts only when the `high` count rose above the baseline (`memory.Events.highPressureFieldSince`). The leaf's `high` count rises only when the leaf's own `memory.high` is exceeded, since the kernel records the event in the cgroup over its limit and passes it up to ancestors, never down, so pressure on an ancestor's limit ends no worker.

When the count rose, `Sentinel.handleMemoryEvents` stores the reason `memory` and then the state `dead` on the page, each with release ordering (`common/worker_state/page/mapping.zig:WorkerWriterView.setState`), writes `child.memory_pressure.detected=high`, `child.memory_state_published` and `child.memory_exit` to the trace pipe, and calls `_exit` with `memory_pressure_exit_status`, 125, which ends every thread without unwinding the VM thread. No request in flight publishes a completion or a usage record; each keeps in its live slot the CPU time the VM thread flushed at its last loop tick (`worker/runtime/observability.zig:flushLiveRequestCpuBestEffort`). No code reads the exit status: the zygote lets the kernel reap its children (`zygote/fork_loop.zig:installWorkerChildAutoReap`), and the server takes only the exit itself from its pidfd, so the page's reason is what tells the server.

The watch has two gaps. Until `Sentinel.init`, which runs while the worker's runtime is built, nothing watches `memory.high` for the worker: the kernel throttles there and kills at `memory.max`, and a `high` event counted before it sits in the baseline. And the sentinel is the worker's own thread: a worker that runs native code can stop it, and `memory.high` then only throttles that worker, which leaves `memory.max` as the bound the kernel holds against every worker.

### The kernel at `memory.max`

`memory.max` sits 15% above L, rounded down to a page so that the file reads back the exact value the child compares (`common/cgroup.zig:memory.maxBytes`). Between the two marks the worker can still grow while the kernel throttles it and the sentinel acts. A worker that reaches `memory.max` with nothing the kernel can reclaim is OOM-killed, and `memory.oom.group` makes the kill take every task of the leaf at once. The kernel counts the kill in the leaf's `oom_kill`, and the page keeps the reason the worker last stored, `none` for a ready worker (`zygote/child_boot.zig` stores the state `ready` with the reason `none` before `WorkerReady`).

### Other bounds inside the worker

| Bound | Value | Where | Holds |
| --- | --- | --- | --- |
| tmpfs root | the tmpfs size above | `zygote/worker_boot/sandbox.zig:rootfs.mountTmpfsAt` | the worker's files; a full tmpfs fails writes with `ENOSPC`, and its pages count in the leaf |
| request body, buffered response body | 4 MiB each | `common/limits/http_body.zig:MATERIALIZED_BODY_BYTES_MAX`, `worker/request/context.zig:IncomingBody`, `worker/request/response_model.zig:validateShape` | one request's materialized bodies |
| requests at once | the definition's `concurrency`, at most 2 | `common/limits/server.zig:worker_concurrency_max` | live request contexts |
| fetches | 64 in flight per worker, 16 started per request; a response body at most 4 MiB | `common/ipc/messages.zig:WorkerRuntimeBootOptions`, [egress.md](egress.md#limits) | the fetch bodies the worker holds while they stream |
| crypto pool | 2 threads with 4 MiB stacks by default | `common/ipc/messages.zig:WorkerRuntimeBootOptions` | WebCrypto jobs |
| tasks | 128 | `common/cgroup.zig:pids.DEFAULT_MAX` | threads and their stacks |
| descriptors | 1024 | `zygote/worker_boot/sandbox.zig:limits.DEFAULT_MAX_OPEN_FILES` | open files |

The shared regions the worker writes, listed under [Memory outside the worker](#memory-outside-the-worker), count in its leaf as well. A request's arena (`worker/request/context.zig:RequestContext.arena`) has no cap of its own and is freed with the request's context. The libpas scavenger, which hands freed allocator pages back to the kernel, runs on one thread for the worker's life. `collo_vm_post_fork_child` resumes it in a forked worker before the filter with a deep-sleep timeout of ten years, so the thread never retires, and without the signal-based thread suspender, so the cache of an idle thread is reclaimed only when that thread next allocates (`bindings/jsc/zygote/prepare_for_fork.cpp:Collo::resumeFastMallocScavengerForSandbox`). A FIXME there notes that a thread that parks without allocating keeps the scavenger polling. The worker forces two eden collections at boot and none after: an asynchronous one whose request, still queued when the API lock is released, wakes the collector thread, and a synchronous one it waits for, so the collector thread exists and is parked before the filter (`collo_vm_prespawn_compiler_threads` in the same file). The full collection and trim run only in the zygote, after its warmup corpus (`zygote/fork_loop.zig:prepareZygoteAtBoot`).

## A memory death

A worker's death reaches the server through its pidfd or the hang-up of its sockets, on the lane that reads it, a lane that holds one of its requests, or the reaper for an idle worker no lane reads ([scheduler.md](scheduler.md#death-detection), [request.md](request.md#failure-domains)). For the reasons `exited` and `peer_closed` a lane asks why, once per worker (`server/ingress/runner/worker_fault.zig:deathStatus`); every other fault takes its error code from `worker_fault.zig:errorCodeForFault`. `server/supervisor/usage_drain.zig:classifyWorkerDeath` answers from two sources:

| What ended the worker | Page reason | `oom_kill` in `memory.events.local` | Error code |
| --- | --- | --- | --- |
| its sentinel, past `memory.high` | `memory` | 0 | `memory` |
| the kernel, at `memory.max` | `none` | 1 or more | `memory` |
| the kernel's OOM killer for the node or an ancestor cgroup | `none` | 1 or more | `memory` |
| anything else: a crash, a SIGKILL from outside the kernel's OOM killer | not `memory` | 0 | `crash` |

The page is read once (`common/worker_state/page/snapshots.zig:LifecycleSnapshot.load`), and a reason outside `TerminationReason` counts for nothing. The cgroup file is read by path, and a read that fails logs a warning and leaves `crash`; a kernel kill also logs a warning with the count. The leaf is still there when a lane asks, because the reaper removes it in the teardown (`server/supervisor/worker_table.zig:Record.vacate`) only after every lane let go of the worker. The page's reason is the worker's own claim, so a worker can mark any of its deaths `memory`, which changes only its own requests' error code; `oom_kill` is the kernel's count.

Each request of the dead worker then ends as `worker_died` with that error code (`server/ingress/runner/request_finish.zig:endingFor`): the client gets 502, or RST_STREAM once the response head went out, and the access record carries status 502, `error_code` `memory` and `worker_fault` `exited` or `peer_closed`. A request whose begin reached the worker gets a usage floor with origin `server`, the same error code and fault, and the CPU time its live slot held when one matches, unless the worker appended its own record first (`usage_drain.zig:synthesizeFinalAccountingForLifecycle`, `synthesizeRecordForLifecycle`); one whose begin never left leaves no usage. Requests still waiting in the pool wait for a replacement, or get 503 at once when nothing can serve them ([scheduler.md](scheduler.md#the-pool), `worker_fault.zig:faultWorker`, `server/ingress/runner/admission.zig:growOrStrand`).

An idle worker that no lane reads leaves no request to record: the reaper sees its exit. The retirement of every worker that died or faulted, this one or one a lane handled, logs the leaf's CPU time at `warn` with the classification (`server/supervisor/reaper/root.zig:Reaper.retire`, `usage_drain.zig:noteWorkerDeathBurn`). A worker that dies before `WorkerReady` fails its launch as `worker_init_failed`, whether the launcher sees its pidfd or the end of its init socket first (`host/launch.zig:Machine.onEvent`, `Machine.finishInitOutcome`). The launcher reads its page and its leaf's `memory.events.local` by the same rule, and its warning says whether the worker ended for memory (`host/launch.zig:Machine.endedCause`, `InitFailure`, [scheduler.md](scheduler.md#the-launcher)).

## OOM scores

A leaf's `memory.max` bounds its own worker, and an OOM kill there chooses among the leaf's tasks alone. The scores matter when the kernel's OOM killer runs for the whole node, or for an ancestor cgroup with a limit. `oom_score_adj` passes across fork and exec, so each spawn writes its child's score (`common/os.zig:process.writeOomScoreAdj`), and a write that fails only logs a warning:

| Process | `oom_score_adj` | Written by |
| --- | --- | --- |
| worker | `OOM_SCORE_ADJ_WORKER`, 500 | the zygote, between the clone and the fork reply, since the worker's chroot has no `/proc` (`zygote/fork_loop.zig:serveForkRequests`) |
| zygote | `OOM_SCORE_ADJ_ZYGOTE`, 200 | the server, after the spawn (`zygote/host_client.zig:spawnZygote`) |
| gateway | `OOM_SCORE_ADJ_EGRESS_GATEWAY`, -500 | the server, after the spawn (`server/gateway/process.zig:spawn`) |
| server | its own, as started | no code; `common/limits/process.zig` expects its systemd unit to set -1000 with `OOMScoreAdjust=`, and the repository holds no unit |

The scores put workers first in the kernel's choice, then the zygote, the gateway and the server (`common/limits/process.zig`). A worker's death costs its own requests; the zygote's stops every launch, and with it the server ([scheduler.md](scheduler.md#the-launcher)); the gateway's fails every worker's fetches in flight ([egress.md](egress.md#sessions)); losing the server loses the node. Setting a score at or above the task's `oom_score_adj_min` needs no privilege; going below it needs `CAP_SYS_RESOURCE` and otherwise fails with `EACCES`. The minimum is 0 unless a writer holding that capability set a score on the task or an ancestor, since children inherit it. The gateway's -500 therefore holds only when the server has `CAP_SYS_RESOURCE`, or when a privileged writer such as systemd's `OOMScoreAdjust=` gave the server a minimum of -500 or lower, which the gateway inherits; otherwise the write fails and the gateway keeps the server's score. With `memory.oom.group` on every leaf, a worker the node's OOM killer picks dies whole, and its leaf counts the kill, as long as no cgroup between the leaf and the OOM's domain sets it too: the kernel kills the highest such cgroup whole, sparing only tasks scored -1000, so under a unit with systemd's `OOMPolicy=kill`, which sets it on the unit's cgroup, one worker's kill ends the zygote, the gateway, every worker and with them the server.

## Memory outside the worker

[main.md](../main.md) counts in a worker's marginal memory what the server and the gateway spend on it. Per live worker the server holds a send scratch of `ipc.max_message_bytes` (1 MiB) of address space from its allocator, resident in a ReleaseFast build only as far as the largest `request_begin` it carried, from before the fork until the teardown (`server/supervisor/launcher.zig:Launcher.startFork`, `server/supervisor/worker_table.zig:Record.dispatch_send_scratch`), the handle's two path strings, the descriptors of the worker's channels, wake set and memfds, and the leaf. Records, request tables and lane registrations do not grow with the workers: the supervisor allocates a record for every pool entry at init (`server/supervisor/supervisor.zig:Supervisor.init`), and each lane has a fixed array of registrations (`server/ingress/runner/root.zig:max_completion_registrations`).

The rest are memfds the server creates and both ends map. A page of one is charged to the cgroup of the process that first touches it, by a read as much as a write, so whoever touches a region first decides whose cgroup pays:

| Region | Size | Created | First touched by |
| --- | --- | --- | --- |
| state page | 288,544 B (`common/worker_state/page/mapping.zig:Page`) | at launch (`host/launch.zig:Machine.prepare`) | the server for the page that holds the header (`mapping.zig:createMemfd` writes it), and for the page that holds the console ring's header and the completion ring when the metrics thread, which reads that header every 100 ms (`server/ingress/analytics_drain.zig`, `server/ingress/service_observability.zig:metrics_drain_interval_ns`), gets there before the worker writes a completion or a console line; the worker for the rest |
| ingress payload rings | 1 MiB per direction (`common/ipc/ingress_channel/payload_ring.zig:shared_payload_ring_capacity`) | at launch | the server for `server_to_worker`, the worker for `worker_to_server` |
| egress command ring | 1 MiB | per session (`common/ipc/egress_shared/session_fds.zig:createSessionForWorker`) | the worker |
| egress completion ring | 4 MiB | per session | the gateway |
| egress body pool | 8 MiB | per session | the gateway |
| egress upload pool | 8 MiB | per session | the worker |

The server also writes each egress region's meta at creation, a page each. The server, the zygote and the gateway share the server's cgroup, `<own>/main` in the delegated placement, which has no limit of its own, so the server's and the gateway's shares count against no worker: up to 1 MiB of payload ring in the server and 12 MiB of completion ring and body pool in the gateway per attached worker. Only the body pool gives pages back while its memfd lives: after a release drain that freed anything, the gateway punches the freed blocks out of the memfd when the pool is at most a quarter full (`egress/gateway/runtime/body_release_flow.zig:drainWorkerPoolReleases`, `common/ipc/egress_shared/body_pool.zig:BodyPoolView.punchFreeRange`). Every other region keeps each page it touched until both ends have unmapped it: the state page and the payload rings at the worker's teardown (`server/supervisor/worker_table.zig:Record.vacate`), the egress regions when the session ends.

A session also costs the gateway address space, however little of it is resident: `common/ipc/egress_shared/endpoint.zig:mapEndpointTakeForGateway` maps all four regions, 21 MiB of data and 24 pages of metas and states (with 4 KiB pages) per session. These mappings count against the gateway's `common/limits/process.zig:EGRESS_GATEWAY_ADDRESS_SPACE_BYTES_MAX` of 4 GiB, which also holds the shards' heaps under `egress/gateway/supervisor_limits.zig:shard_memory` and the pending uploads' assembly buffers on the gateway's own heap. [egress.md](egress.md#limits) lists those limits.

## The node

The reaper reads node memory as the `memory.current` of the server's own cgroup, the one `/proc/self/cgroup` names, against its `memory.max`, or as `MemTotal` less `MemAvailable` from `/proc/meminfo` when that cgroup has no limit or cannot be read (`server/supervisor/reaper/memory.zig:readMemoryPressure`). In the delegated placement the server's cgroup is `<own>/main`, which the server creates without a limit, so the reading is always the machine's; in the env-root placement it is the cgroup the server started in, which never holds the worker leaves. Besides its 5 s pass and the demand reclaim a launch wakes, a PSI trigger on the system-wide `/proc/pressure/memory` wakes the reaper for a pass as soon as tasks have stalled on memory for 300 ms within a 2 s window (`server/supervisor/reaper/memory.zig:MemoryPressureWake`, `server/supervisor/scheduler_limits.zig:memory.psi_some_trigger`). The trigger goes out in one write with a NUL after it, since the kernel turns the last byte of a write into its terminator (`memory.zig:armPsiTrigger`), and 2 s is the shortest window a process without `CAP_SYS_RESOURCE` may arm; the server, refusing to run as root (`server/boot/root.zig:rootRefusal`), holds that capability only when whatever starts it grants it. A kernel without PSI refuses the trigger, and so does one before Linux 6.4 for a process without the capability. The reaper then warns at boot with the reason (`memory.zig:psiRefusalReason`) and reads memory only on its 5 s pass and on demand reclaim, as it does once the trigger reports an error (`server/supervisor/reaper/root.zig:Reaper.memoryPressureEvent`).

Pressure acts on launches and on idle workers. The memory gate closes at `fork_deny_percent`, and a launch at or above `autoscale_high_water_percent` wakes demand reclaim ([scheduler.md](scheduler.md#the-pool)). The gate compares node usage with a percentage and ignores the limit of the worker it lets launch, so the limits of the live workers may add up to more than the node holds. The reaper's plans retire idle workers by a score of their private resident bytes weighted by idle age ([scheduler.md](scheduler.md#the-reaper), [caps](scheduler.md#caps)), and nothing retires a busy worker for memory: a busy worker is held by its own limit, and when busy workers together exhaust the node, the kernel's OOM killer chooses in the order of the scores above.

## Open points

The gateway cannot map the sessions its plan admits. The plan admits 256 sessions (`egress/gateway/sizing.zig:workers_max`) whenever the server's hard open-file limit is at least `common/limits/process.zig:EGRESS_GATEWAY_OPEN_FILES_MAX` (`sizing.zig:Plan.compute`), and they map about 21.1 MiB each, 5.3 GiB in all; 4 GiB holds at most 194 of them with nothing else mapped, and that space also holds the gateway's binary, thread stacks, shard heaps and upload buffers. An attach whose mapping fails returns the error from `egress/gateway/runtime/control_flow.zig:handleControl`, and `drainControl` ends the gateway on it. The launcher's reattach pass then attaches the same live workers to the next gateway one at a time ([scheduler.md](scheduler.md#the-launcher)), and that gateway meets the same ceiling, so on a node with more attached workers than the address space holds, each gateway ends the same way and takes every worker's fetches in flight with it.

The node's reading misses the limits placed around the server. A limit on the delegated `<own>`, such as the unit's `MemoryMax=`, is never read, because the server measures `<own>/main`, and a cgroup reading, wherever it applies, holds the server, the zygote and the gateway and no worker (`server/supervisor/reaper/memory.zig:readMemoryPressure`).

On a node with swap the kernel can swap a worker out at `memory.max` instead of killing it, since no leaf has a `memory.swap.max` of its own ([The limit](#the-limit)), so a worker whose sentinel does not act is bounded only by its ancestors' swap limits and the node's swap.

A worker's JSC critical mode never engages, because the worker cannot read its own resident size ([The engine's collection trigger](#the-engines-collection-trigger)). However close a worker comes to `memory.high`, the engine never switches to that mode's full collections, smaller collection budget and synchronous sweeps (`Heap::shouldDoFullCollection`, `Heap::collectIfNecessaryOrDefer`, `Heap::shouldSweepSynchronously`), and a readable size would still be compared with the zygote's `WTF::ramSize`, not L.

A worker that crosses its limit before `WorkerReady`, while its route's top-level code runs, fails its launch as `worker_init_failed`, and only the launcher's warning, and the boot trace when the server logs it, name memory: the waiters the failure strands get 503 with the error code `done` (`server/ingress/runner/request_finish.zig:RequestOutcome.unserved`), and no usage record exists. A route whose top-level code needs more than L fails every launch the same way.

A sentinel whose `ppoll` fails, or whose command or memory-events descriptor reads as invalid, returns from its thread (`worker/runtime/sentinel.zig:Sentinel.sentinelPollLoop`) after an `err` line on the worker's stderr, which the child pointed at `/dev/null` at boot (`zygote/child_boot.zig:closeUnexpectedWorkerFds`); the worker keeps serving with neither its deadline trap nor its memory watch, and nothing notices.

Shared regions stay resident. Apart from body-pool blocks punched at low water, every page of the regions above stays allocated until its memfd goes, so a worker that once filled each ring holds up to 23 MiB of shared regions, 2 MiB of payload rings and 21 MiB of egress regions, of which 13 MiB is charged outside its own cgroup. The body pool's punch covers only the blocks one drain freed, and only when that drain leaves the pool at most a quarter full; blocks freed while the pool was fuller keep their pages until they are reused.

No test pushes a worker past `memory.high` or `memory.max`. The sentinel's test starts the watch without crossing the mark (`worker/tests/sentinel.zig`), the classification is tested with a page stamp and a fixture file (`server/tests/supervisor/supervisor.zig`, `common/tests/cgroup.zig`), and local-e2e ends workers with SIGKILL (`runtime/tests/integration/local_server/harness.zig:killWorker`), which counts no `oom_kill` and classifies as `crash`.
