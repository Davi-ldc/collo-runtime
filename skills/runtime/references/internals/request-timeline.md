# The request timeline

This document covers what a worker measures about each request it serves: the split of the request's wall time into execution, waiting and I/O, the readiness stamps that decide the split, the two CPU clocks beside it, and the records that carry the numbers to the server. The state machine is in `runtime/src/worker/request/context.zig` and the loop that drives it in `runtime/src/worker/scheduler/` and `runtime/src/worker/runtime/`; the crypto settlement (`runtime/src/worker/js/crypto/`) and the fs fault plane (`runtime/src/worker/fs/`) drive their own sub-turns, and the finish that publishes the numbers is in `runtime/src/worker/serve/`. Their `//!` headers own the mechanics. [request.md](request.md#completion-and-finish) owns how the server reads, validates and settles these records; this document follows only which numbers reach which record and output. A reference such as `context.zig:RequestContext.noteReady` names a file and a symbol in it. A bare file name is in `worker/request/`, `worker/scheduler/`, `worker/runtime/` or `worker/serve/`, and any other path is relative to `runtime/src/`.

## What the worker measures

From the moment the worker decodes a request's begin until it finishes the request, the request is in one of three states (`context.zig:RequestContext`): executing, while a turn of its own runs on the VM thread; runnable, while it has work items ready (`ready_items` above zero) and the thread runs something else; or I/O, while none of its work is ready. Each transition closes the elapsed slice into the total of the state it leaves, `waiting_ns` for runnable and `io_time_ns` for I/O. Execution has no total of its own: it is the wall time less those two. The transitions close every instant between the start and the finish into one of the three states.

The split is measured as states over intervals because per-item sums overlap and stamps taken at the drain misplace time. `queued_ns` (`context.zig:RequestContext.queued_ns_total`) sums the ready-queue wait of each of the request's work items except timers, immediates and fault completions, so two items queued at once count the same interval twice; `waiting_ns` counts each runnable interval once. And the loop reads completions only between turns, so a stamp taken when it drains one would count the time the thread spent on another request as I/O. Where a source can, it therefore stamps the moment its work became ready, and the transition applies the stamp after the fact (`common/ipc/messages.zig:EgressFetchHeadHeader.ready_at_mono_ns`); [Readiness by source](#readiness-by-source) lists the three that cannot.

Every timeline stamp is CLOCK_MONOTONIC: the runtime's clock (`types.zig:Clock.monotonic`, which tests replace), the gateway's publish stamp and the crypto pool's completion stamp, which compare with the worker's readings because the node shares one clock. A worker holds at most two requests at once (`common/worker_state/page/live_slots.zig:LIVE_SLOT_COUNT`), so what a request waits behind is the other request's turns, the loop's own passes and work no request owns. The loop runs one work item per tick, and between two items it runs a collect pass (`loop.zig:collectFast`), the deferred-work pump and the ring's ready events, which read control packets, gateway packets and fault responses (`loop.zig:run`).

CPU time has two clocks, and neither is part of the partition. The engine bridge measures each request's turns on the VM thread's CLOCK_THREAD_CPUTIME_ID (`bindings/jsc/runtime/vm.cpp:threadCpuTimeNs`). `collo_turn_enter` opens a slice in the request's `ColloExecCtx` (`context.zig:RequestContext.exec`, field `turn_cpu_start_ns`), and `collo_turn_exit_ex` adds the slice to `cpu_used_ns_total`; the outermost exit drains the microtasks first, so the request's own reactions drained there are charged to it. A reaction another request registered runs under its registrant: `moveCpuSlice` closes the drainer's slice and opens the registrant's for its duration (`bindings/jsc/runtime/vm.cpp:ColloRestoredTurnScope`). The per-turn clock thus covers JavaScript and the bridge's native work inside the engine turns entered for the request. It leaves out the work item's Zig code outside engine turns, such as parsing the head and sending the response; the loop's passes; JavaScript no request owns; and every other thread, among them the crypto pool, JSC's compiler and collector threads and the sentinel.

The usage record carries the other clock in its `cpu_time_ns`: the CLOCK_PROCESS_CPUTIME_ID delta since the worker's previous committed record (`process_cpu.zig:peekBilledDeltaNs`), which covers every thread. The records add up to the worker's process CPU up to its last record, split among requests by the order in which they finish. A worker's first record absorbs the boot, the route module's evaluation included, and of two overlapping requests the one that finishes first takes the whole span since the previous record. The pool threads' work on a request's crypto jobs shows only on this clock; on the timeline that work is I/O.

With request tracing on, `context.zig:RequestTrace` stamps a request's phases on the runtime's clock and `trace.zig:emit` prints them to stderr when the request finishes. They enter no record.

## The state machine

The four transitions of `context.zig:RequestContext` run on the VM thread. A request starts in I/O when the worker decodes its begin (`worker/request/ingress/runtime.zig:enqueueRequestBegin`). Two fields mark where its time stands: `state_since_ns`, the start of the open slice, and `nonexec_since_ns`, the start of the current stretch in which no turn of the request has run. Both start at `started_mono_ns`. The request's `request` work item is queued right after, which closes that first slice.

| Transition | Called when | Effect |
| --- | --- | --- |
| `noteReady(stamp, now, counted)` | a work item of the request became ready | In I/O, closes the slice at the stamp clamped to [`state_since_ns`, now], and the request is runnable from there. When already runnable, a stamp earlier than `state_since_ns` opens the runnable slice at max(stamp, `nonexec_since_ns`) and takes that window back from I/O, so the next transition closes it once, as waiting. While executing, it only counts. |
| `noteTurnBegin(now, consumes)` | a turn of the request starts | Closes the open slice at now, into waiting when `ready_items` is above zero and into I/O otherwise, and marks the request executing; changes no slice when it already executes. |
| `noteTurnEnd(now)` | the turn ends | Marks the request not executing and moves `state_since_ns` and `nonexec_since_ns` to now. Whether the new slice is runnable or I/O is decided at the next transition. |
| `noteFinish(now)` | `response_finish.zig:finishRequest` | Closes an open slice as `noteTurnBegin` does, closes nothing inside a turn of the request, and seals the timeline. |

Until the timeline is sealed, `counted` adds one to `ready_items` and `consumes` takes one away, stopping at 0. `ready_items` counts the request's work items from their enqueue to the start of their turn, plus the fs fault waiters counted for it, and it alone tells runnable from I/O.

A stamp of 0 means now. The clamp keeps every slice from going negative and leaves time already booked where it is: a stamp from before the open slice, such as one taken inside the request's last turn, opens the runnable slice where the I/O slice began.

Items do not drain in the order of their stamps, so a request that is already runnable can learn of an earlier readiness. `noteReady` then takes the window between the earlier stamp and the start of the runnable slice back from I/O and opens the slice at the earlier stamp, so the drain order does not decide the split, and the next transition counts the window once, as waiting. The window starts no earlier than `nonexec_since_ns`, which `noteTurnEnd` sets. Between two turns of the request its state can only go from I/O to runnable, so the time from `nonexec_since_ns` to the start of the runnable slice is all I/O, and a stamp taken inside the request's own turn cannot turn that turn into waiting.

`noteFinish` seals the timeline: every later transition, the count included, does nothing. The finish writes its records only after a cleanup that can run JavaScript on the request's context ([Where the numbers land](#where-the-numbers-land)), so without the seal a hook transition or a count during that cleanup could move time into them. The seal also covers a context kept in the active map after a failed finish (`response_finish.zig:preserveFailedFinish`), whose stale items can still pop.

`worker/tests/request/context.zig` (lane `worker-test`) drives the transitions with stamps derived by hand. It pins that I/O closes at the stamp and waiting runs from the stamp to the turn, that a zero stamp means now, that a stamp before the slice start clamps to it, that an out-of-order drain moves the earlier window from I/O into the open runnable slice, that a fully stamped script partitions wall time exactly, as do out-of-order drains closed by a turn or a finish with a stamp below the floor at `nonexec_since_ns` among them, that the seal makes every later transition a no-op, and that a finish outside a turn closes the tail into waiting when the request was runnable and into I/O when it was not.

## Readiness by source

A work item carries its owner and its stamp in its ready-queue slot (`queue.zig:SlotMeta`): the request it belongs to, resolved once at enqueue because the handler maps can lose the entry before the pop (`scheduler.zig:readyItemOwnerRequestId`), the producer's stamp, and the enqueue time. The ready queue and its backlog each hold `RuntimeLimits.ready_queue_capacity` items (256 by default, `common/ipc/messages.zig:WorkerRuntimeBootOptions`). `scheduler.zig:tryQueueReadyWorkReadySince` pushes the item onto the queue, or onto the backlog when the queue is full, and calls the owner's `noteReady` once, at the push that succeeds, with the enqueue time as now. Moving the backlog into the queue keeps the metadata and counts nothing again (`queue.zig:ReadyQueue.drainInto`). A push that finds both full counts nothing and leaves the item with its producer, which queues it again on a later pass. The boot context's items are never counted, and an fs fault completion belongs to no request. `worker/egress/context.zig:Context.tryQueueReadyReadySince` does the same for the two egress item kinds.

| Source | Work item | Stamp | Stamped by, when |
| --- | --- | --- | --- |
| request begin | `request` | 0; the timeline itself starts at the decode | the worker, when the loop reads the packet |
| request body complete or failed | `request_body_ready` | 0 | the worker, when the loop reads the last chunk, or in the turn whose read finds the body complete |
| client reset, or a body over its bound or ended early | `request_cancelled` | 0 | the worker, when the loop reads the packet |
| route module evaluation settled | `request`, for each request parked on it | 0 | the worker, in the collect pass after the settlement (`modules.zig:collectModuleSettlements`) |
| handler's thenable settled | `request_completion` | `completion.zig:Completion.ready_at_mono_ns` | the worker, when the bridge reports the settlement during the drain that settled it |
| request deadline | `request_deadline` | the deadline (`deadlines.zig:Entry.due_mono_ns`) | known in advance |
| timer | `timer_callback` | `timers.zig:TimerEntry.due_mono_ns` | known in advance |
| setImmediate | `immediate_callback` | `immediates.zig:ImmediateEntry.scheduled_at_mono_ns` | the worker, in the turn that called setImmediate |
| fetch head or error | `fetch_completion` | the packet's `ready_at_mono_ns`, kept in `worker/egress/task.zig:Task.ready_at_mono_ns` | the gateway, when it encodes the packet it publishes ([egress.md](egress.md#a-fetch-end-to-end)) |
| fetch body chunk batch, end or error | `fetch_body_ready` | `egress/core/fetch_body.zig:Body.ready_at_mono_ns`, the first gateway stamp since the body's item last ran | the gateway |
| fetch or body settled with no gateway stamp: a detach, an abort ack (which carries none), a failed upload, a body cancel | `fetch_completion`, `fetch_body_ready` | 0 | the worker |
| crypto job | none | `worker/js/crypto/jobs.zig:Entry.completed_at_ns` | the pool thread, when the job finishes |
| fs fault response | `fs_fault_completion`, owned by no request | `worker/fs/fault.zig:Task.completed_at_ns` | the worker, when it reads the response off the fault channel |

A stamp kept in its source survives a full queue. Timers and immediates are collected only while the ready queue has room and otherwise stay in their containers with their stamps (`resources.zig:collectDueTimers`, `collectReadyImmediates`); a deadline stays on its heap; completions, tasks and bodies keep their stamps for the rescan; and a fault's waiters are counted only once its item is queued. For all of them the wait for queue room counts as waiting. The ingress items and the parked module waiters carry 0 and take the enqueue time at each attempt (`worker/request/ingress/runtime.zig:queueDispatch`, `queueBodyReady`, `queueCancel`; `modules.zig:handleModuleEvaluationSettled`), so for them that wait counts as I/O.

A body's stamp is set only while it is 0 and cleared when its item runs (`egress.zig:executeFetchBodyReady`), so a later chunk does not move the end of the request's I/O forward while the body waits for its reader. A detach clears it before it fails the body, since no gateway packet made the body ready (`worker/egress/gateway_runtime.zig:failActiveFetches`). A read that JavaScript starts on a body already readable queues the item with the body's older stamp (`worker/egress/body/consume.zig:scheduleConsume`), from inside the request's own turn, where `noteReady` only counts it.

A crypto job never enters the ready queue. The collect pass settles up to 16 finished jobs per call (`worker/js/crypto/runtime.zig:collectCompleted`), each in a turn of its request that calls `noteReady` at the pool thread's stamp and `noteTurnBegin` right after, so the request's I/O ends when the job finished and the wait for the collect pass is waiting.

An fs fault is one task per path, shared by every reader of the path (`worker/fs/fault.zig:State.faults_by_path`), and its completion item belongs to no request. Once the item is queued, `worker/fs/fault_completion.zig:noteWaitersReady` counts one ready item at the response stamp for each waiter whose request is still active under the same generation, and marks the waiter `ready_counted`; when the item runs, each waiter settles in a sub-turn of its own request that consumes the count. The stamp is taken before the file is copied into the tmpfs, so the copy is the waiters' waiting. A reader that joins a fault whose item is already queued is counted at once, from inside its own turn (`worker/fs/fault.zig:schedule`). A settle that stops early releases the counts it did not consume through turns of zero length (`worker/fs/fault_completion.zig:releaseUnconsumedWaiterCounts`), so the waiting each request accrued since its waiter was counted closes, and its next slice follows its remaining items.

Three sources are stamped when the loop gets to them instead of at the event: the ingress packets and the fault responses, which the loop reads off their sockets only between turns (a synchronous fault's wait reads fault responses at once, `worker/fs/fault_sync.zig:faultSync`), and a route module's settlement, which `worker/host/module_settlement.zig:collo_runtime_module_eval_settled` parks during a drain for the next collect pass. For a body chunk, a reset, a fault response or a module waiter, the delay between the event and the drain is I/O. For a begin it lies outside the worker's span altogether.

## Turns and work with no owner

A request executes during the turns that call `noteTurnBegin` and `noteTurnEnd` for it. Each turn also makes two other attributions, which can differ from that one: the request whose `queued_ns` and `max_turn_ns` the turn feeds, and the owner `resources.zig:publishTurnOwner` publishes to the sentinel, the one request whose expired deadline lets the sentinel terminate the turn (`sentinel.zig:Sentinel.publishTurnOwner`). For a work item, `loop.zig:beginTurnTelemetry` begins the turn of the owner its slot carries and `finishTurnTelemetry` ends it; the telemetry owner is resolved again at the pop from the item's kind, and the sentinel's through `scheduler.zig:readyItemOwnerRequestId`.

| Turn | Executing in the timeline | `queued_ns`, `max_turn_ns` | Sentinel owner | Turn CPU |
| --- | --- | --- | --- | --- |
| `request`, `request_body_ready`, `request_cancelled`, `request_deadline`, `request_completion`, `fetch_completion`, `fetch_body_ready` | the item's request | that request | that request | that request |
| `timer_callback`, `immediate_callback` | the request that scheduled it | none | that request | that request |
| `fs_fault_completion` | each live waiter, in a sub-turn of its own | each waiter's `max_turn_ns` | each waiter during its sub-turn, 0 between | each waiter |
| a crypto settlement, in the collect pass | the job's request | that request's `max_turn_ns` | that request | that request |
| a reaction another request registered, inside a drain | the registrant, while the drainer stops executing | the enclosing turn's owner, as part of that turn's length | the registrant | the registrant |
| a reaction with no owner, inside a drain | nobody, while the drainer stops executing | the enclosing turn's owner, as part of that turn's length | 0 | nobody |
| a route module evaluated in a `request` turn | that request | that request | that request | nobody |
| the deferred-work pump | nobody | the boot context's while it is open, none after | the boot id while the boot context is open, 0 after | the boot context, then the loop's request-less context |
| a route module settlement, the boot evaluation | nobody | none | the boot id | nobody |

A worker evaluates its route entry at boot, so a `request` turn evaluates a route module only when the boot left no record for the entry, as it does for a default export that is not callable (`worker/modules/routes.zig:ensureRouteHandler`, `bootEvaluateRouteEntry`). Module evaluation takes the engine's lock without entering a turn (`bindings/jsc/runtime/module_loader.cpp:collo_module_evaluate`), so the request executes in the timeline while no turn clock runs.

The engine calls `vm_hooks.zig:ownerTransitionCallback` twice around each microtask it runs under a restored owner, once before the microtask and once after (`bindings/jsc/runtime/vm.cpp:ColloRestoredTurnScope`, `collo_vm_set_owner_transition_hook` in `bindings/include/collo/abi.h`). A microtask runs under a restored owner when its promise settled while an owner other than its registrant was running, or when a restored continuation queued it (the WebKit patch `0004-microtask-owner-context`, `bindings/jsc/runtime/vm.cpp:ColloCrossTaskToken`). Usually the registrant is a request other than the drainer, but either side can be turnless, and both sides can be the drainer itself, which then ends and restarts its turn at the same instant. On the way in, the hook ends the turn of the request that leaves, publishes the entering owner to the sentinel and begins the entering request's turn without consuming an item; on the way out it does the reverse. While the foreign reaction runs, the draining request's time is its waiting or its I/O, by its own count, and the engine moves the CPU slice itself.

Some JavaScript runs while no request executes in the timeline. `loop.zig:pumpDeferredWork` runs JSC's deferred settle tasks, the asynchronous wasm settlements, as one turn under the boot context while it is open and under the loop's request-less context once it has closed, with `executing_turn_real_owner` at 0; a reaction in it whose registrant is alive is restored to that request by the hook. `modules.zig:collectModuleSettlements` reads a settled route module's export and drains around it outside any turn, and the boot evaluation (`boot_context.zig:evaluateBootRouteEntry`) runs the route entry before the worker reports ready. A reaction registered by turnless code carries the turnless token, and one registered by a request that has since ended carries a released one; both resolve to no owner (`bindings/jsc/runtime/vm.cpp:execCtxForOwnerToken`), so the hook ends the draining request's turn and publishes 0. All of this time is waiting or I/O for the live requests, and its CPU reaches no request's turn clock; only the next usage record's process delta has it.

## Where the numbers land

`response_finish.zig:finishRequest` runs once per request. A finish need not run inside one of the request's turns: a response whose last step waited in the request's outbox finishes from the loop's flush (`response.zig:flushPendingIngressResponses`, called from `loop.zig:flushParkedResponses` when the control socket turns writable or the payload ring gets room), so the time it waited for the server closes as I/O unless the request has items ready, and the usage record ends at the flush. The finish reads `finished_mono_ns` and seals the timeline with it before any cleanup, so the records' times end there; the cleanup that follows can still run JavaScript, such as the rejection of a pending body read (`body_read.zig:rejectPendingRead`), whose CPU reaches the record and whose wall time does not. When the running work item's telemetry owner is the request, the finish adds that turn's queue wait to `queued_ns` and its length so far to `max_turn_ns`. Every caller of `finishRequest` runs between engine turns, and the engine adds a turn's CPU to `cpu_used_ns_total` when the turn exits, so the record's turn CPU is `cpu_used_ns_total`. The finish then writes that CPU to the live slot, appends the usage record, and only after that publishes the completion and signals the server. The process delta is read before the append and committed after it; when the record ring is full the worker stops, and its live slot takes the larger of its turn CPU and the uncommitted delta, since the server's floor reads the slot.

| Measure | Completion record | Usage record | Live slot |
| --- | --- | --- | --- |
| start and finish | none | `started_mono_ns`, `finished_mono_ns` | `started_mono_ns` |
| turn CPU | `cpu_time_ns` | `turn_cpu_ns` | `cpu_time_ns`: completed engine turns, rewritten at the finish, at every loop tick and before the loop blocks (`observability.zig:flushLiveRequestCpuBestEffort`) |
| process CPU delta | none | `cpu_time_ns` | none |
| I/O and waiting | `io_time_ns`, `waiting_ns` | `io_time_ns`, `waiting_ns` | none |
| queue wait and longest turn | none | `queued_ns`, `max_turn_ns` | none |

The three are `common/worker_state/page/completion_ring.zig:WorkerCompletionRecord`, `common/worker_state/page/usage_records.zig:CompletedRecord` and `common/worker_state/page/live_slots.zig:LiveRequestSlot`, and the server reads them as [request.md](request.md#completion-and-finish) describes. When a worker's completion ends the request, the ingress lane copies the completion's three times into the request's access facts (`server/ingress/runner/request_finish.zig:finishDispatched`), and `access.jsonl` prints them beside the lane's own duration; every other ending prints 0. That duration runs from admission (`server/ingress/runner/admission.zig:startDynamicH2`, [request.md](request.md#deadlines)) to the lane's finish, so it also covers the wait for a worker slot, the dispatch, the time before the worker read the begin, and the time from the worker's finish to the lane's. No record carries execution. A usage record's wall time less its I/O and waiting gives it; the same subtraction on an access record, whose `duration_ms` is in milliseconds, also counts those server-side spans as execution.

The usage drain turns a worker's record into a line of `usage.jsonl` through `server/analytics/usage.zig:fromCompleted`: `wall_time_ns` is `finished_mono_ns` less `started_mono_ns`, `ts` is the finish on the wall clock and never later than the drain's own reading (`server/analytics/record.zig:Clock.wallMs`), and `cpu_time_ns`, `io_time_ns` and `waiting_ns` are copied. `turn_cpu_ns`, `queued_ns` and `max_turn_ns` stay on the page. A floor for a request the server ended (`server/supervisor/usage_drain.zig:synthesizeRecordForLifecycle`) takes `started_mono_ns` and `cpu_time_ns` from the request's live slot when one matches every identity field the dispatch assigned, zeroes that CPU when the floor's status is `internal_error`, ends at the server's clock and reports no I/O or waiting; without a matching slot it starts at the dispatch and reports nothing measured.

Every measure is the worker's claim. The completion's `status` and `http_status` are checked for range and its times not at all (`common/worker_state/page/completion_ring.zig:validateWorkerCompletionRecord`), and the access record takes the worker's `http_status` unless the worker completed without a head on a stream that is still open and was not reset, which the lane answers and records as 502 (`server/ingress/runner/request_finish.zig:completionLeftNoAnswer`, the outcome table in [request.md](request.md#completion-and-finish)). A usage record enters the log only under a request the worker's request table expects and with the server's identity ([request.md](request.md#completion-and-finish)), but its start, finish, times, byte counters, status and cold-start flag are the worker's. A live slot counts only when it matches the dispatch's identity, and its start and CPU are the worker's as well. A false number distorts only the records of that worker's own requests, since its numbers reach no others ([security.md](security.md)).

## Open points

- The loop reads begins, body chunks, resets and fault responses only between turns and stamps them then, so their wait behind a running turn is I/O, and a begin's wait is in no worker record at all. The ingress items and the module waiters count their wait for queue room as I/O, every other source as waiting ([Readiness by source](#readiness-by-source)).
- A timer or immediate that JavaScript cancels (`resources.zig:cancelTimeout`, `cancelImmediate`) leaves its queued item counted in `ready_items`, so its request reads as runnable until the stale item pops. The same holds for any queued item whose work is gone before its turn.
- Microtasks are not counted in `ready_items`. While another owner's reaction runs in a request's drain, that request's time is I/O unless it has queued items, even when its own reactions wait in the same drain.
- Execution is wall time. A synchronous fault (`worker/fs/fault_sync.zig:faultSync`) blocks the thread inside the request's turn for up to the request's deadline, and that wait counts as execution; so do preemption by the kernel and collection on the VM thread during a turn.
- Work with no owner (the pump after the boot context closes, and reactions with no owner) runs outside every request's deadline and charges its CPU to no request (the FIXME at `loop.zig:pumpDeferredWork`); the timeline shows it as the live requests' waiting or I/O.
- Multi-route workers must give a route module that settles after the boot context has closed an owner with a deadline: `modules.zig:collectModuleSettlements` publishes the boot id for every settlement, and once the boot context has closed no deadline is armed under that id.
- `cpu_time_ns` names three quantities: the process delta on a usage record the worker wrote, the live slot's turn CPU on a floor, and the turn CPU on an access record.
- `turn_cpu_ns`, `queued_ns` and `max_turn_ns` reach the usage ring, and no server code reads them (`server/analytics/usage.zig:fromCompleted`).
- A floor's CPU comes from the live slot, which holds the engine turns completed by the loop's last flush, so the turn that was running when the worker died, such as a hang the sentinel could not stop before the grace backstop retired the worker, is missing from it; the cgroup CPU that would show it is only logged (`server/supervisor/usage_drain.zig:noteWorkerDeathBurn`).
- The usage drain keeps the worker's start, finish and cold-start flag although the request table entry it matched holds the server's dispatch time and flags (`server/analytics/usage.zig:fromCompleted`, `server/supervisor/request_table.zig:Dispatched`).
- No test checks the hook's effect on the timeline or the sentinel, the crypto and fault sub-turns, or a stamp's way from its source into a record. `worker/tests/request/context.zig` pins the state machine; `worker/tests/runtime/multiplexing.zig` runs the hook but checks only which request a continuation's console line names; `worker/tests/runtime/lifecycle.zig` and `worker/tests/runtime/process_cpu.zig` pin the two CPU clocks.
