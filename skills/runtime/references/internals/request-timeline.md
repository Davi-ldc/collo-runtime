# The request timeline

This document covers what a worker measures about each request it serves: the split of the request's wall time into execution, waiting and I/O, the readiness stamps that decide the split, the owner windows that measure CPU beside it, and the records that carry the numbers to the server. The state machine is in `runtime/src/worker/request/context.zig`, the owner of the VM thread in `runtime/src/worker/runtime/owner.zig`, and the loop that drives both in `runtime/src/worker/scheduler/` and `runtime/src/worker/runtime/`; the crypto settlement (`runtime/src/worker/js/crypto/`) and the fs fault plane (`runtime/src/worker/fs/`) drive their own sub-turns, and the finish that publishes the numbers is in `runtime/src/worker/serve/`. Their `//!` headers own the mechanics. [request.md](request.md#completion-and-finish) owns how the server reads, validates and settles these records; this document follows only which numbers reach which record and output. A reference such as `context.zig:RequestContext.noteReady` names a file and a symbol in it. A bare file name is in `worker/request/`, `worker/scheduler/`, `worker/runtime/` or `worker/serve/`, and any other path is relative to `runtime/src/`.

## What the worker measures

From the moment the worker decodes a request's begin until it finishes the request, the request is in one of three states (`context.zig:RequestContext`): executing, while a window of its own is open on the VM thread; runnable, while it has work items ready (`ready_items` above zero) and the thread runs something else; or I/O, while none of its work is ready. Each transition closes the elapsed slice into the total of the state it leaves, `waiting_ns` for runnable and `io_time_ns` for I/O. Execution has no total of its own: it is the request's span in the worker less those two, which the finish computes once the timeline is sealed (`context.zig:RequestContext.execNs`). The transitions close every instant between the start and the finish into one of the three states.

The split is measured as states over intervals because per-item sums overlap and stamps taken at the drain misplace time. A sum of each work item's ready-queue wait would count the same interval twice when two items are queued at once; `waiting_ns` counts each runnable interval once. And the loop reads completions only between turns, so a stamp taken when it drains one would count the time the thread spent on another request as I/O. Where a source can, it therefore stamps the moment its work became ready, and the transition applies the stamp after the fact (`common/ipc/messages.zig:EgressFetchHeadHeader.ready_at_mono_ns`); [Readiness by source](#readiness-by-source) lists the three that cannot.

Every timeline stamp is CLOCK_MONOTONIC: the runtime's clock (`types.zig:Clock.monotonic`, which tests replace), the gateway's publish stamp and the crypto pool's completion stamp, which compare with the worker's readings because the node shares one clock. A worker holds at most `common/worker_state/page/live_slots.zig:LIVE_SLOT_COUNT` requests at once, so what a request waits behind is the other requests' windows, the windows of evaluations and of the worker owner, and the loop's own passes. The loop runs one work item per tick, and between two items it runs a collect pass (`loop.zig:collectFast`), the deferred-work pump and the ring's ready events, which read control packets, gateway packets and fault responses (`loop.zig:run`).

CPU time is measured per owner window and is not part of the partition. `owner.zig` is the one place that says whom the VM thread works for: a dispatched request; an evaluation, one per module instance being evaluated, which owns that instance's top-level code (`evaluations.zig`); or the worker owner, one per process, for JavaScript neither of those owns. A window opens when the VM thread starts work for an owner and closes when that work ends (`owner.zig:enter`, `leave`). At each border the VM thread reads its own CLOCK_THREAD_CPUTIME_ID once (`types.zig:Clock.threadCpu`, which tests replace), and the closed window's CPU goes to its owner: `context.zig:RequestContext.cpu_ns` for a request or an evaluation, `owner.zig:Owners.worker_cpu_ns` for the worker owner. A request's window covers its JavaScript and microtasks, the bridge's native work for it, the worker's Zig code around them, such as parsing its head and writing its response, and collection work the VM thread does inside it. A request's CPU also holds what the crypto pool's threads spent on its WebCrypto jobs: each pool thread reads its own CLOCK_THREAD_CPUTIME_ID around a job (`worker/js/crypto/jobs.zig:Entry.cpu_ns`), and the settlement adds it before any of the request's JavaScript runs (`worker/js/crypto/runtime.zig`). It leaves out the loop's own passes, which run in no window, the windows of evaluations and of the worker owner, and every other thread, among them JSC's compiler and collector threads and the sentinel. The engine bridge reads no clock.

This CPU is what a definition's `cpuMs` bounds (`RequestContext.cpu_budget_ns`, copied at the decode from `WorkerInit.request_cpu_budget_ns`). The charge that takes a request to its budget marks it `cpu_spent` (`owner.zig:chargeContext`), and the request answers 503 `cpu` at the next boundary, after the work item or the collect pass whose window spent it, with the VM left in service (`serve/termination.zig:endSpentBudgets`); a crypto job that spends it settles nothing. A turn that spends it without yielding is stopped by the sentinel, which watches the request's CPU deadline on the VM thread's own CPU clock ([Owner windows](#owner-windows)).

With request tracing on, `context.zig:RequestTrace` stamps a request's phases on the runtime's clock and `trace.zig:emit` prints them to stderr when the request finishes. They enter no record.

## The state machine

The four transitions of `context.zig:RequestContext` run on the VM thread. A request starts in I/O when the worker decodes its begin (`worker/request/ingress/runtime.zig:enqueueRequestBegin`). Two fields mark where its time stands: `state_since_ns`, the start of the open slice, and `nonexec_since_ns`, the start of the current stretch in which no window of the request has been open. Both start at `started_mono_ns`. The request's `request` work item is queued right after, which closes that first slice. Only a dispatched request keeps a timeline: an evaluation counts no ready item, and `owner.zig` moves no timeline for it or for the worker owner.

| Transition | Called when | Effect |
| --- | --- | --- |
| `noteReady(stamp, now, counted)` | a work item of the request became ready | In I/O, closes the slice at the stamp clamped to [`state_since_ns`, now], and the request is runnable from there. When already runnable, a stamp earlier than `state_since_ns` opens the runnable slice at max(stamp, `nonexec_since_ns`) and takes that window back from I/O, so the next transition closes it once, as waiting. While executing, it only counts. |
| `noteTurnBegin(now, consumes)` | a window of the request opens (`owner.zig:enter`) | Closes the open slice at now, into waiting when `ready_items` is above zero and into I/O otherwise, and marks the request executing; changes no slice when it already executes. |
| `noteTurnEnd(now)` | the window closes, or another owner's window interrupts it | Marks the request not executing and moves `state_since_ns` and `nonexec_since_ns` to now. Whether the new slice is runnable or I/O is decided at the next transition. |
| `noteFinish(now)` | `response_finish.zig:finishRequest` | Closes an open slice as `noteTurnBegin` does, closes nothing inside a window of the request, and seals the timeline. |

Until the timeline is sealed, `counted` adds one to `ready_items` and `consumes` takes one away, stopping at 0. `ready_items` counts the request's work items from their enqueue to the start of their turn, plus the fs fault waiters counted for it, and it alone tells runnable from I/O.

A stamp of 0 means now. The clamp keeps every slice from going negative and leaves time already booked where it is: a stamp from before the open slice, such as one taken inside the request's last turn, opens the runnable slice where the I/O slice began.

Items do not drain in the order of their stamps, so a request that is already runnable can learn of an earlier readiness. `noteReady` then takes the window between the earlier stamp and the start of the runnable slice back from I/O and opens the slice at the earlier stamp, so the drain order does not decide the split, and the next transition counts the window once, as waiting. The window starts no earlier than `nonexec_since_ns`, which `noteTurnEnd` sets. Between two windows of the request its state can only go from I/O to runnable, so the time from `nonexec_since_ns` to the start of the runnable slice is all I/O, and a stamp taken inside the request's own turn cannot turn that turn into waiting.

`noteFinish` seals the timeline: every later transition, the count included, does nothing. The finish writes its records only after a cleanup that can run JavaScript on the request's context ([Where the numbers land](#where-the-numbers-land)), so without the seal a hook transition or a count during that cleanup could move time into them. The seal also covers a context kept in the active map after a failed finish (`response_finish.zig:preserveFailedFinish`), whose stale items can still pop.

`worker/tests/request/context.zig` (lane `worker-test`) drives the transitions with stamps derived by hand. It pins that I/O closes at the stamp and waiting runs from the stamp to the turn, that a zero stamp means now, that a stamp before the slice start clamps to it, that an out-of-order drain moves the earlier window from I/O into the open runnable slice, that a fully stamped script partitions wall time exactly, as do out-of-order drains closed by a turn or a finish with a stamp below the floor at `nonexec_since_ns` among them, that the seal makes every later transition a no-op, and that a finish outside a turn closes the tail into waiting when the request was runnable and into I/O when it was not.

## Readiness by source

A work item carries its owner and its stamp in its ready-queue slot (`queue.zig:SlotMeta`): the request or evaluation it belongs to, resolved once at enqueue because the handler maps can lose the entry before the pop (`scheduler.zig:readyItemOwnerRequestId`), the producer's stamp, and the enqueue time. The ready queue and its backlog each hold `RuntimeLimits.ready_queue_capacity` items (256 by default, `common/ipc/messages.zig:WorkerRuntimeBootOptions`). `scheduler.zig:tryQueueReadyWorkReadySince` pushes the item onto the queue, or onto the backlog when the queue is full, and calls the owner's `noteReady` once, at the push that succeeds, with the enqueue time as now. Moving the backlog into the queue keeps the metadata and counts nothing again (`queue.zig:ReadyQueue.drainInto`). A push that finds both full counts nothing and leaves the item with its producer, which queues it again on a later pass. An evaluation's items are never counted, since only a dispatched request keeps a timeline, and an fs fault completion belongs to no owner. `worker/egress/context.zig:Context.tryQueueReadyReadySince` does the same for the two egress item kinds.

| Source | Work item | Stamp | Stamped by, when |
| --- | --- | --- | --- |
| request begin | `request` | its first enqueue attempt (`RequestContext.dispatch_ready_since_ns`); the timeline itself starts at the decode | the worker, when the loop reads the packet |
| request body complete or failed | `request_body_ready` | its first enqueue attempt (`body_ready_since_ns`) | the worker, when the loop reads the last chunk, or in the turn whose read finds the body complete |
| client reset, or a body over its bound or ended early | `request_cancelled` | its first enqueue attempt (`cancel_ready_since_ns`) | the worker, when the loop reads the packet |
| route module evaluation settled | `request`, for each request parked on it | the settlement (`modules/state.zig:StalledWaiter.ready_since_ns` across retries) | the worker, in the collect pass after the settlement (`modules.zig:collectModuleSettlements`) |
| response producer can advance: a grant, socket or ring room, or a body stream's read settled | `response_advance` | its first enqueue attempt (`RequestContext.response_advance.ready_since_ns`) | the worker, when it reads the grant or the wake, or when the bridge reports the read |
| handler's thenable settled | `request_completion` | `completion.zig:Completion.ready_at_mono_ns` | the worker, when the bridge reports the settlement during the drain that settled it |
| request deadline | `request_deadline` | the deadline (`deadlines.zig:Entry.due_mono_ns`) | known in advance |
| timer | `timer_callback` | `timers.zig:TimerEntry.due_mono_ns` | known in advance |
| setImmediate | `immediate_callback` | `immediates.zig:ImmediateEntry.scheduled_at_mono_ns` | the worker, in the turn that called setImmediate |
| fetch head or error | `fetch_completion` | the packet's `ready_at_mono_ns`, kept in `worker/egress/task.zig:Task.ready_at_mono_ns` | the gateway, when it encodes the packet it publishes ([egress.md](egress.md#a-fetch-end-to-end)) |
| fetch body chunk batch, end or error | `fetch_body_ready` | `egress/core/fetch_body.zig:Body.ready_at_mono_ns`, the first gateway stamp since the body's item last ran | the gateway |
| fetch or body settled with no gateway stamp: a detach, an abort ack (which carries none), a failed upload, a body cancel | `fetch_completion`, `fetch_body_ready` | 0 | the worker |
| crypto job | none | `worker/js/crypto/jobs.zig:Entry.completed_at_ns` | the pool thread, when the job finishes |
| fs fault response | `fs_fault_completion`, owned by no request | `worker/fs/fault.zig:Task.completed_at_ns` | the worker, when it reads the response off the fault channel |

A stamp kept in its source survives a full queue. Timers and immediates are collected only while the ready queue has room and otherwise stay in their containers with their stamps (`resources.zig:collectDueTimers`, `collectReadyImmediates`); a deadline stays on its heap; completions, tasks and bodies keep their stamps for the rescan; a fault's waiters are counted only once its item is queued; the ingress items keep the instant of their first attempt on the request's context until one succeeds (`worker/request/ingress/runtime.zig:queueStamped`); a response advance keeps its first stamp in `response_advance` until its turn (`response_stream.zig:queueAdvance`); and a module's waiters that find the queue full keep the settlement's instant in the stalled list (`modules.zig:queueSettledWaiters`). For all of them the wait for queue room counts as waiting. A push that finds both queues full wakes nothing, whatever the item: the full ready queue keeps the loop from blocking, and the next tick's collect pass reruns every rescan (`scheduler.zig:tryQueueReadyWorkReadySince`).

Work that vanishes while its item waits gives its count back. A timer or immediate its owner clears after its item was queued (`resources.zig:cancelTimeout`, `cancelImmediate`) has the item's slot cleared of its owner (`queue.zig:ReadyQueue.withdraw`), so the stale item pops in no window and consumes nothing, and the request takes the count back at once (`context.zig:RequestContext.noteReadyWithdrawn`): when nothing of it is ready any more and it is not executing, its runnable slice closes into waiting there and what follows is I/O. A fetch body does the same when it leaves the table, or when its view is cancelled with no reader and no decoder left, since its `fetch_body_ready` item then answers no reader and pops in no window (`worker/egress/body/cleanup.zig`, through `worker/egress/context.zig:Context.withdrawReady`). An item that still has work keeps its count: an aborted fetch's completion rejects the fetch's promise, and a released source that feeds tee branches resumes its decoder.

A body's stamp is set only while it is 0 and cleared when its item runs (`egress.zig:executeFetchBodyReady`), so a later chunk does not move the end of the request's I/O forward while the body waits for its reader. A detach clears it before it fails the body, since no gateway packet made the body ready (`worker/egress/gateway_runtime.zig:failActiveFetches`). A read that JavaScript starts on a body already readable queues the item with the body's older stamp (`worker/egress/body/consume.zig:scheduleConsume`), from inside the request's own turn, where `noteReady` only counts it.

A crypto job never enters the ready queue. The collect pass settles up to 16 finished jobs per call (`worker/js/crypto/runtime.zig:collectCompleted`), each in a window of its owner that a request's `noteReady` at the pool thread's stamp precedes and that consumes the count at once, so the request's I/O ends when the job finished and the wait for the collect pass is waiting.

An fs fault is one task per path, shared by every reader of the path (`worker/fs/fault.zig:State.faults_by_path`), and its completion item belongs to no owner. Once the item is queued, `worker/fs/fault_completion.zig:noteWaitersReady` counts one ready item at the response stamp for each waiter whose request is still active under the same generation, and marks the waiter `ready_counted`; when the item runs, each waiter settles in a window of its own owner that consumes the count. The stamp is taken before the file is copied into the tmpfs, so the copy is the waiters' waiting. A reader that joins a fault whose item is already queued is counted at once, from inside its own turn (`worker/fs/fault.zig:schedule`). A settle that stops early withdraws the counts it did not consume (`worker/fs/fault_completion.zig:releaseUnconsumedWaiterCounts`, through `noteReadyWithdrawn`), so the waiting each request accrued since its waiter was counted closes, and its next slice follows its remaining items.

Some sources are stamped when the loop gets to them instead of at the event: the control packets (ingress descriptors and response grants), socket and ring readiness, and the fault responses, which the loop reads only between turns (a synchronous fault's wait reads fault responses at once, `worker/fs/fault_sync.zig:faultSync`), and a route module's settlement, which `worker/host/module_settlement.zig:collo_runtime_module_eval_settled` parks during a drain for the next collect pass. For a body chunk, a reset, a grant, a wake, a fault response or a module waiter, the delay between the event and the drain is I/O. For a begin it lies outside the worker's span altogether.

## Response advances

Every response source, buffered, segmented, fetch-backed or a JavaScript stream, resumes through one `response_advance` item per request (`serve/response.zig:executeAdvance`), which runs in the request's owner window, so its CPU enters the request's record and its deadline and CPU budget apply. A grant that ends a wait for body credit queues it (`request/ingress/runtime.zig:enqueueResponseCredit`), and so does room in the control socket or the payload ring (`response.zig:notifyTransport`). A wait for credit arms no write poll and marks no ring, so the request's time is I/O until the wake and waiting from the wake until the advance runs. [request.md](request.md#bodies-and-credit) owns the credit contract.

## Owner windows

Each window has one owner, which every border publishes to the sentinel with what is left of its limits (`sentinel.zig:Sentinel.publish`, which only `owner.zig` calls): a request's armed wall deadline and its CPU deadline, the window's start on the VM thread's CPU clock plus the budget it has left; an evaluation's armed deadline; the worker owner's wall limit, `unowned_time_limit_ns` from the window's start. The sentinel stops only the published owner's JavaScript, when it passes a limit while it runs; a limit already spent when a window opens is not published, and the work item's boundary answers that request instead (`serve/termination.zig:admitAtBoundary`). The page's owner section gets the same owner and wall deadline, where the server faults a worker whose owner overran it (`WorkerWriterView.publishOwner`). A request is executing in the timeline exactly while a window of its own is open.

| Work | Window | Executing in the timeline |
| --- | --- | --- |
| a work item | the owner its queue slot names, resolved at enqueue: the item's request, or the evaluation whose top-level code set the timer or started the fetch; none for an item whose entry was gone at enqueue | that request, consuming the ready item its enqueue counted |
| `fs_fault_completion` | none for the item; each waiter settles in a window of its own owner | each live waiter, in turn |
| a crypto settlement, in the collect pass | the job's owner | the job's request |
| a reaction another owner registered, inside a drain | the registrant | the registrant, while the drainer stops executing |
| a reaction whose registrant was released or whose evaluation closed | the worker owner | nobody, while the drainer stops executing |
| a route module's evaluation, at boot or in a request's work item | the evaluation of its module instance | nobody; a request whose item started it stops executing |
| a route module's settlement, in the collect pass | its instance's evaluation, or the worker owner once that evaluation closed | nobody |
| the deferred-work pump | the worker owner | nobody |
| a request's finish, from one of its turns or from an ending the loop applies between items | the request | nothing more: the finish seals the timeline first |
| a response advance of any source, a body stream's reaction and its cancel | the request | that request |

The engine calls `vm_hooks.zig:ownerTransitionCallback` twice around each microtask it runs under a restored owner that differs from the owner it interrupts, once before the microtask and once after (`bindings/jsc/runtime/vm.cpp:ColloRestoredTurnScope`, `collo_vm_set_owner_transition_hook` in `bindings/include/collo/abi.h`). A microtask runs under a restored owner when its promise settled while an owner other than its registrant was running, or when a restored continuation queued it (the WebKit patch `0004-microtask-owner-context`, `bindings/jsc/runtime/vm.cpp:ColloCrossTaskToken`). Each call enters the owner of its `entering` side: the restored owner on the way in, the interrupted one on the way out. A null side, a registrant whose exec context was released or an evaluation that closed, is the worker owner (`owner.zig:ownerOf`). The entering request's turn begins without consuming an item, and the leaving request's turn ends, so while the foreign reaction runs, the draining request's time is its waiting or its I/O, by its own count, and its CPU is the registrant's.

Module top-level code runs outside any turn. While a route's entry evaluates, and while a module settlement reads its export and drains around it, the owning evaluation is the bridge's turnless context (`collo_vm_set_turnless_exec_ctx`, installed by `evaluations.zig:Methods.enterTurnless`) and its window is open, so host calls resolve to it, every reaction its code registers carries its token, and a turn of it that never yields meets its deadline: the init deadline in the boot's synchronous part, the deadline of the request whose work item started it otherwise, and its routes' own budget once its synchronous part ended. A settlement whose evaluation closed runs with the worker owner's exec context installed instead. All of this time is waiting or I/O for the live requests, and its CPU is the evaluation's or the worker owner's, which no record carries.

## Where the numbers land

`response_finish.zig:finishRequest` runs once per request. A finish need not run inside one of the request's turns: an ending the loop applies between items, such as a spent CPU budget (`termination.zig:endSpentBudgets`), finishes outside every window. A response whose last step waited for credit or room finishes in the `response_advance` turn that sends it, so that wait is I/O until the wake and waiting from the wake until the advance runs, unless the request has other items ready. The finish reads `finished_mono_ns` and seals the timeline with it before any cleanup, so the records' times end there. It then runs in the request's own window, which it opens when it was called from outside one, so the cleanup that follows, which can still run JavaScript, such as the rejection of a pending body read (`body_read.zig:rejectPendingRead`), adds to the record's CPU and not to its wall time. After the cleanup it folds the open window into `cpu_ns` (`owner.zig:foldOpenWindow`), writes that CPU to the live slot, appends the usage record, and only after that publishes the completion and signals the server. When the record ring is full the worker stops; the live slot, which the server's floor reads, already holds the request's CPU.

| Measure | Usage record | Live slot |
| --- | --- | --- |
| CPU of the request's owner windows | `cpu_ns` | `cpu_ns`: the windows closed so far, rewritten at the finish, at every loop tick and before the loop blocks (`observability.zig:flushLiveRequestCpuBestEffort`) |
| execution | `exec_ns`: the span less I/O and waiting | none |
| I/O and waiting | `io_ns`, `waiting_ns` | none |

The two are `common/worker_state/page/usage_records.zig:CompletedRecord` and `common/worker_state/page/live_slots.zig:LiveRequestSlot`; the completion record (`completion_ring.zig:WorkerCompletionRecord`) carries the request's identity and outcome and no measure. The server reads them as [request.md](request.md#completion-and-finish) describes. A record carries execution because nothing could derive it from the rest: the server's wall time starts before the worker's span and ends after it.

The usage drain turns a worker's record into a line of `usage.jsonl` through `server/analytics/usage.zig:fromCompleted`: `ts` is the server's end of the request on the wall clock, the wall time runs from the server's dispatch to that end, the cold-start flag is the dispatch's, and the execution, CPU, I/O and waiting come from the worker's record. A floor for a request the server ended (`server/supervisor/usage_drain.zig:synthesizeRecordForLifecycle`) takes its CPU from the request's live slot when one matches every identity field the dispatch assigned, zeroes it when the floor's status is `internal_error`, and reports no I/O or waiting.

Every measure in a worker record is the worker's claim. The completion's `status` and `http_status` are checked for range (`common/worker_state/page/completion_ring.zig:validateWorkerCompletionRecord`), and the access record takes the worker's `http_status` unless the worker completed without a head on a stream that is still open and was not reset, which the lane answers and records as 502 (`server/ingress/runner/request_finish.zig:completionLeftNoAnswer`, the outcome table in [request.md](request.md#completion-and-finish)). A usage record enters the log only under a request the worker's request table expects and with the server's identity ([request.md](request.md#completion-and-finish)), but its CPU, I/O, waiting, byte counters and status are the worker's. A live slot counts only when it matches the dispatch's identity, and its CPU is the worker's as well. A false number distorts only the records of that worker's own requests, since its numbers reach no others ([security.md](security.md)).

## Open points

- The loop reads begins, body chunks, resets and fault responses only between turns and stamps them then, so their wait behind a running turn is I/O, and a begin's wait is in no worker record at all.
- Microtasks are not counted in `ready_items`. While another owner's reaction runs in a request's drain, that request's time is I/O unless it has queued items, even when its own reactions wait in the same drain.
- Execution is wall time. A synchronous fault (`worker/fs/fault_sync.zig:faultSync`) blocks the thread inside the request's turn for up to the request's deadline, and that wait counts as execution; so do preemption by the kernel and collection on the VM thread during a turn.
- The worker owner's CPU, like an evaluation's, reaches no record.
- A reaction of a request already past its deadline that runs inside another owner's drain is not stopped by the sentinel, since a window opened past its owner's deadline publishes none; the server's backstop for that request bounds it.
- An evaluation that a request's work item starts takes the time of its synchronous part out of that request's execution, which counts it as waiting or I/O. Every route is evaluated at boot, so this happens only for a route the boot left `idle`, whose module then runs no top-level code again.
- The live slot holds the windows closed by the loop's last flush. The sentinel writes the running owner's CPU, its CPU before the window plus the window so far, to the page's owner section at each wake, before a fire and before it ends the worker (`WorkerWriterView.publishRunningOwnerCpu`); a crash it did not see coming, such as a segfault, still loses the part of the window after its last wake.
- `worker/tests/request/context.zig` pins the state machine and the withdrawal; `worker/tests/runtime/multiplexing.zig` pins that a restored continuation keeps its registrant's identity and that its CPU is the registrant's, and that a stranded reaction runs under the worker owner, whose limit stops it; `worker/tests/runtime/lifecycle.zig` pins a record's CPU as deltas of the owner windows, never the thread's reading; `worker/tests/runtime/limits.zig` pins the CPU budget at the sentinel, at a boundary and at a crypto settlement, and the worker owner's limit; `worker/tests/runtime/timeline.zig` pins the withdrawn timer, the stamp a full queue keeps and the record's execution; `worker/tests/runtime/fetch.zig` pins the count a cancelled reader gives back; `worker/tests/runtime/wasm.zig` pins the pump's CPU on the worker owner. No test checks the hook's effect on the timeline, the crypto and fault sub-turns' timelines, or a stamp's way from every source into a record.
