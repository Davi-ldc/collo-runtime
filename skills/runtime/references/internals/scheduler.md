# The scheduler

This document covers how the server keeps the workers of each worker definition: the pool that hands out request slots and holds the requests that wait, the launcher thread that turns a pool's claim into a published worker, the scale-out verdict that decides when a definition gets a worker more, the reaper thread that retires workers, how a worker's death is noticed, and the caps that bound all of it. The code is in `runtime/src/server/supervisor/` (`pool.zig`, `launcher.zig`, `scale_out.zig`, `reaper/`, `supervisor.zig`, `worker_table.zig`, `worker_registry.zig`, `worker_factory.zig`, `scheduler_limits.zig`) and in `runtime/src/common/limits/pool.zig`, and their `//!` headers own the mechanics; the lane's side of a dispatch, a finish and a death is in [request.md](request.md). References name a file and a symbol in it, as in `pool.zig:Pool.acquire`. A bare file name is in `server/supervisor/` or `server/ingress/` (its `runner/` included), a name two directories share carries its directory (`reaper/root.zig`, `runner/root.zig`), and any other path is relative to `runtime/src/`.

## The supervisor and its records

`supervisor.zig:Supervisor` keeps one pool per worker definition (`pools[d]`) and one worker record per pool table entry, entry `e` of pool `d` at `records[d * pool_workers_max + e]`. Both are allocated at `init` and freed at `deinit`, so a record pointer stays valid after its worker leaves, and holders tell the workers one record serves apart by its key (`worker_table.zig:Record.key`). The supervisor has no lock of its own; the locks below belong to the pools, the records, the launcher and the reaper.

The launcher thread alone builds records and assigns worker keys (`worker_registry.zig:buildRecord`), filling a record while its entry is launching, when no other thread can see it (`worker_table.zig:Record.occupy`). The reaper empties a record once its pool says no lane holds or reads the worker (`worker_table.zig:Record.vacate`). At shutdown the exiting thread carries out what the reaper's queue still holds (`reaper/root.zig:Reaper.drainRetirements`), then tears down every worker a record still holds without asking its pool, since every thread that could use one has stopped (`supervisor.zig:Supervisor.deinit`). A live worker's egress session is the one record field the pool's mutex guards: the launcher writes it (`supervisor.zig:Supervisor.setWorkerEgress`) and finds the worker of a removed session by it (`Supervisor.retireEgressSession`), and the lanes read it (`workerEgress`).

| Lock | Guards | Order |
| --- | --- | --- |
| `pool.zig:Pool.mutex` | a pool's table, slots, waiters and reader tenures, and the record fields `worker_table.zig` names | before a lane's command-queue mutex and never taken with one held; inside a record's `metrics_mutex` in one place (`analytics_drain.zig`) |
| `worker_table.zig:Record.metrics_mutex` | the page mapping, the console ring's mark and drain cursor, and the boot token's identity and whether its end is owed; spans each drain of its console ring, the metrics thread's and the teardown's | before the request table's mutex; never held across the boot token's end (`Supervisor.progressBootEgress`) |
| `request_table.zig:RequestTable.mutex` | a worker's request table: one entry per request in flight and the routes of its last 256 ended requests | a leaf |
| `worker_table.zig:Record.send_mutex` | a worker's send scratch and its server-to-worker payload ring | nests with neither of the two above |
| `launcher.zig:Launcher.mutex` | submissions, gateway and session losses, counters | a leaf, never held across a call |
| `reaper/root.zig:Reaper.mutex` | the retire queue and counters | a leaf; the reaper takes a pool's mutex only inside a pool method and calls out with neither held |

Some record fields take no lock. The lanes pace the worker's forwarded response output with an atomic count and the reader that waits for it (`worker_table.zig:Record.forwarded_in_queues`, `window_waiter`), and register the lanes whose request bodies wait for room in its server-to-worker ring, one per slot (`Record.body_waiters`); request.md describes the [window](request.md#the-reader-lane-and-forwarding) and the [credit](request.md#bodies-and-credit). `Record.occupy` clears the waiters for each new worker but keeps the count, since the release of a command an earlier worker of the record left in a queue still takes its unit back.

## The pool

`pool.zig:Pool` is a plain structure under one mutex, with no thread, no I/O and no clock, and it allocates only at `init`. Its table has `pool_workers_max` entries, each empty, launching, live, retiring or dead. A live entry points at its worker's record and has the definition's `concurrency` slots, kept as a bit per slot with the lane that holds it, and a slot belongs to one request of one lane from the `acquire` or handoff that takes it to the `release` that gives it back. A lane releases the slot of a request the worker heard of only at its `request_done`, the worker's death or the lane's teardown ([request.md](request.md#completion-and-finish)), so `concurrency` bounds the requests in flight in the worker process. The waiters are a ring of at most `pool_waiters_max` requests, each a lane, a request key and a deadline, and `launching` counts the launches in flight.

`Pool.acquire` takes the lowest free slot of the most recently used live worker that has one, the lowest entry on a tie (`pool.zig:mostRecentFreeEntry`). That order is the pool's free list: there is no separate list, and each entry carries a `last_use` stamp that every take and give-back advances. Load packs onto warm workers this way, and idle ones stay idle until the reaper retires them. A published worker that serves no waiter starts at the cold end, with `last_use` 0 (`Pool.publish`).

A request that finds no free slot becomes the newest waiter, and a full FIFO answers `.full`, which the lane turns into 503. A freed slot goes to the head waiter at once (`Pool.release`), and a published worker's slots go to the head waiters, oldest first (`Pool.publish`); each handoff carries the slot and a reader grant, and its caller posts it as `dispatch_ready` to the waiter's lane, or dispatches in place when the waiter is a request of its own lane (`request_finish.zig:handOn`). A waiter whose deadline passed is dropped on the way, since its lane answers it (`pool.zig:popLiveWaiter`). Free slots and waiters therefore never coexist, which `Pool.acquire` asserts, and no retry timer exists. A request that ends while it waits leaves the FIFO through `Pool.cancelWaiter`, a scan of at most `pool_waiters_max` entries under the mutex.

`Pool.growthWanted` says what a pool's waiters ask of the launcher (`pool.zig:Growth`). Nothing grows while the memory gate is closed, `launches_max` launches are in flight, no entry is empty (launching, live, retiring and dead entries all count as taken), or no more requests wait than the launches in flight will serve, `waiter_count > launching × concurrency` (`pool.zig:growthWantedLocked`). Past those, a pool with no live worker and no launch in flight answers `launch`: its first worker, a cold start, which the launcher claims at once. A pool with a live worker answers `watch`, once until the launcher stops watching it: a worker more beside the live ones starts only on the launcher's scale-out verdict ([Scale-out](#scale-out)). A pool whose first launch is still in flight answers `none`, since the verdict weighs the CPU its live workers use. A lane asks when one of its requests starts to wait and after a death it owns, the reaper asks after each removal, and the metrics thread and the launcher ask after a death they announce; each submits to the launcher on `launch` or `watch`, with a `launcher.zig:GrowthReason`, and the launcher claims again for a definition after each publish. The answer is advisory, so the launcher's claim decides again under the mutex and takes an empty entry for the launch (`Pool.launchStarted`), which the launch holds until `publish` or `launchEnded`. When growth is refused and the pool has no live worker and no launch in flight, `Pool.takeStranded` hands its waiters out for an immediate 503, since nothing would serve them before their deadlines.

The memory gate is the reaper's last reading of node memory against `fork_deny_percent` (`supervisor.zig:Supervisor.memoryGate`). The reaper caches the used percentage at each periodic pass and each demand-reclaim reading (`reaper/root.zig:readPressure`), so a growth check costs one atomic load; the re-reads inside a reap leave the cache alone. The launcher's claim reads the cache again (`Supervisor.claimLaunch`) and wakes the reaper's demand reclaim when the gate refuses, or when a launch goes ahead at or above `autoscale_high_water_percent`.

One lane at a time reads a worker's output, and the pool decides which. Every slot a lane takes comes with a `ReaderGrant`, which the lane discharges before it dispatches and also when it gives the slot back unused (`pool.zig:grantReader`, `worker_registration.zig:dischargeReaderGrant`):

| `pool.zig:ReaderGrant` | When | The lane that took the slot |
| --- | --- | --- |
| `you_become_reader` | the worker has no reader | registers the worker's output channels and reads them under the new epoch for the whole tenure |
| `already` | the lane reads the worker, another lane reads a busy worker, or a release was asked in this tenure already | nothing; the reader forwards this request's output |
| `transfer_from` | the worker was idle and another lane reads it | posts `release_worker` with that tenure to the reader, which goes on reading and forwarding until it gives the role up |

The reader gives the role up through `Pool.transferReader`, which decides under the mutex and keeps a live worker's reader while the worker has a request in flight. A `release_worker` that arrives after the asking lane's request started therefore changes nothing, and the role moves only while the worker is idle. The next lane to take a slot after the reader let go becomes the reader, so two lanes never read one worker at once.

| `pool.zig:Transfer` | When | The reader (`worker_registration.zig:applyReaderTransfer`) |
| --- | --- | --- |
| `stale` | the tenure already ended, or the worker left the table | stops reading on that tenure's behalf |
| `kept` | the worker is live, or retiring after its notice, with a slot held | goes on reading and forwarding |
| `free_held_payloads` | the worker is live and idle, and the reader still holds forwarded ring payloads | frees them in ring order and asks again (`command_flow.zig:giveUpTenure`): every owner gave its slot back, an owner answers before that or never, and the next reader decodes from the ring's read cursor |
| `vacated` | a live idle worker, or one out of service that a lane still holds | cancels its polls on the worker and wakes the reaper to watch the worker |
| `retire` | the worker is out of service and this was its last hold | as `vacated`, and queues the retirement |

A handoff whose lane never saw it, or saw it only after the worker left service, goes back with its grant (`Pool.returnHandoff`, `command_flow.zig:handleDispatchReady`), ending a tenure the grant made, so the pool never names a reader that has no polls on the worker; a refused `release_worker` is forgotten so that the next grant asks again (`Pool.releaseRequestLost`). An entry's epoch keeps counting across the workers it holds and is never 0 (`pool.zig:nextEpoch`). A lane takes a slot of a worker with no reader only by becoming its reader, so the epoch moves whenever a lane takes a slot of a worker no lane reads, which is what fences the reaper's watch below.

A worker leaves service through `markDead` (a fault, its exit or its deadline's grace), `retireForEgress` (departure `egress` when no gateway could give it a session, `egress_removed` when its gateway removed its session for a protocol violation), `retireIdle`, `retireOnNotice` or `retireOnUnreadNotice`, which its entry records as its `Departure`, and no slot of it is handed out afterwards. `Pool.markDead` checks under the mutex that the record still holds the worker key its caller saw, and returns a `Death` that names every lane holding a slot of the worker or reading it, or sets `retire` when none does; only the first caller gets one. A worker that announced `worker_retiring` (`Pool.retireOnNotice`, departure `recycled`) leaves with whatever requests it holds: they finish on it, its reader keeps forwarding their output, and no lane is told of a death, but a death while it drains is taken again as one, so the lanes of those requests learn of it. The worker is finished once no lane holds or reads it, and exactly one call reports that: `retire` from `release`, `returnHandoff`, `transferReader`, `retireIdle`, `retireOnNotice` or `retireOnUnreadNotice`, or a `Death` with `retire` set. Its caller queues the retirement to the reaper, which calls `Pool.remove` after the teardown so a later launch can reuse the entry. When the last request of a worker retiring on its notice ends while a lane still reads it, `release` or `returnHandoff` answers `release_reader` instead, and the releasing lane asks the reader to give the role up; the reaper's idle passes ask again while such a reader holds on (`Pool.retiringReaders`).

| `pool.zig:Pool` call | Caller | Answer |
| --- | --- | --- |
| `acquire` | a lane at admission | `.acquired` with a slot and a grant, `.wait`, `.full` |
| `release`, `returnHandoff` | the lane that finishes a request; the lane or launcher whose `dispatch_ready` was refused or never read, or the lane it reached after the worker left service | `.idle`, `.handed_to` a waiter, `.retire`, `.release_reader` |
| `cancelWaiter` | a lane whose waiting request ended | whether the waiter was still queued |
| `growthWanted`, `takeStranded` | lanes, the launcher and the metrics thread, and the reaper for `growthWanted` | advisory growth, `launch`, `watch` or `none`; the waiters left for 503 |
| `launchStarted`, `publish`, `launchEnded` | the launcher thread | a `LaunchTicket`, a `watch` for a scale-out the caller did not allow, or nothing; the handoffs to waiters; the entry back |
| `keepScaleOutWatch` | the launcher thread, at each scale-out sample | whether the pool still wants a scale-out; when it does not, its watch ends and the next waiter asks again |
| `markDead`, `retireForEgress` | the first thread to see a death; the launcher | a `Death`, or null |
| `transferReader` | the reader lane, or a lane ending a tenure it never took up | `stale`, `kept`, `free_held_payloads`, `vacated`, `retire` |
| `retireOnNotice` | the worker's reader lane when it reads the notice | `stale`, `draining`, `retire`, `release_reader` |
| `retireOnUnreadNotice` | the reaper when the control socket of a worker its scan listed idle with no reader turns readable, with the key and the reader epoch the scan saw | `stale`, `retire` |
| `idleWorkers`, `retireIdle`, `retiringReaders`, `remove` | the reaper thread, and for `remove` the exiting thread at shutdown | idle candidates with their reader and reader epoch; `not_idle`, `retire`, `release_reader`; the retiring workers whose reader still has to let go; the emptied entry |

No pool method takes another lock or calls out, so the pool's mutex is never held across a send, a wait or a callback, and a caller posts the commands a result asks for after the method returns (`service_deps.zig:postToLane`). The visitors of `Pool.findLive` and `Pool.visitWorker` run under the mutex and only touch the record fields it guards or duplicate descriptors.

## The launcher

`launcher.zig:Launcher` is one thread for the node. The zygote serves one fork at a time on one thread, so a single launcher loses no fork throughput, and at most one fork request is outstanding (`Launcher.forking`). The launcher never kills a worker, waits for an exit or removes a cgroup: a failed launch goes to `Deps.failed` with what the child left, and the reaper does the rest. Besides its `poll`, it waits only inside a gateway call, an egress attach or a gateway spawn, and neither runs while a fork request is outstanding, because a thread blocked past a fork reply's deadline fails that fork as `fork_reply_timeout`, which kills the zygote and stops the server.

`Launcher.submit` sets a bit per definition, so submissions coalesce and never fail for room. Each turn of the thread (`launcher.zig:threadMain`) claims launches for every definition submitted or deferred since the last one (`claimSubmitted`), while the launch table has room (`hasRoom`: launches in flight plus failed launches whose leftovers the reaper has not torn down, below `definitions × pool_cold_starts_in_flight_max`), through `Deps.claim` (`Supervisor.claimLaunch`, `Pool.launchStarted`). A definition the table had no room for waits for the next turn. A claim that finds the pool wanting a scale-out puts the definition in the watch, and the turn's scale-out step samples the watched definitions once their sample is due and claims for each one the verdict grants (`stepScaleOut`, [Scale-out](#scale-out)). After a publish the launcher claims for the definition again, because the waiters the new worker could not serve submit nothing more.

| `launcher.zig:LaunchState` | Holds | Waits for | Bound |
| --- | --- | --- | --- |
| `queued` | a ticket | its turn at the zygote, the oldest claim first | none |
| `fork_requested` | a send scratch, the egress wake set, the launch machine with the cgroup leaf and its local steps, the egress session | the fork reply on the zygote's control socket | `fork_reply_timeout_ms`, 5 s |
| `init_sent` | the launch machine (`host/launch.zig:Machine`) | `WorkerReady` on the init socket, or the child's exit on its pidfd | `child_window_ms`, 3 s |
| `awaiting_reattach` | a ready worker whose egress session's gateway was lost | a turn with no fork outstanding, to attach it to the current gateway | none |

`launcher.zig:startFork` gets what a fork needs cheapest first, so a launch that cannot get one of them never forks: the worker's 1 MiB send scratch, its egress wake set, a fork job id the launcher numbers and the cgroup leaf with the definition's memory limit (`host/cgroup_root.zig:WorkerCgroupRoot.createWorkerDir`), which the launch's machine owns from then on (`host/launch.zig:Machine.init`), the egress session when the definition has a `network` grant (`worker_factory.zig:definitionHasEgressGrant`, `attachLaunchEgress`; a definition without one gets no wake set, no session and so no gateway on its account), and then the fork request with the leaf (`zygote/host_client.zig:sendForkRequest`). While the zygote clones, the machine creates the child's shared page and channels (`Machine.prepare`); a failure there is kept for the reply. A launcher with no worker host, the cgroup root the boot prepared (`launcher.zig:WorkerHost`), fails every launch as `cgroup_leaf`, which only fixtures that never fork have. On the reply (`launcher.zig:receiveForkReply`), `Machine.start` takes the child and sends `WorkerInit`, whose fields and descriptors [boot.md](boot.md#the-servers-side) lists, and the machine's `onEvent` reports how the ready wait ended (`launcher.zig:applyOutcome`). The child window is fixed at that send, and the boot token minted then has the window's end plus `MODULE_EVAL_BUDGET_NS` as its deadline; the launch keeps the token's gateway, session and deadline for the worker's record (`launcher.zig:ReadyWorker.boot_egress`) and closes its own copies of the session's descriptors once `WorkerInit` went out.

Each turn waits in one `poll` until a source is ready or the earliest deadline of a launch, of the egress side or of the next scale-out sample while a definition is watched (`launcher.zig:pollTimeoutMs`):

| Entry (`launcher.zig:buildPollSet`) | Polled | Wakes the thread for |
| --- | --- | --- |
| the wake eventfd | always | `submit`, `stop`, `gatewayLost`, `egressSessionLost`, `leftoversReaped` |
| the zygote's pidfd | until it reports the exit | the zygote's exit, which stops the server |
| the zygote's control socket | while a fork request is outstanding | the fork reply |
| a live worker's control socket, for room | while its `egress_attach` waits | the reattach's send |
| each `init_sent` launch's init socket and pidfd | until `WorkerReady` or a failure | `WorkerReady`, an init failure, the child's exit |

A reply or a `WorkerReady` that arrived while the thread was in a gateway call is read before its deadline is judged, and a reply the zygote sent before it died is still read, since its child no longer needs the zygote (`launcher.zig:waitAndHandle`, `handleReady`). A failed `poll` sleeps 10 ms and tries again, and deadlines keep expiring meanwhile (`launcher.zig:poll_retry_ns`).

At `WorkerReady` (`launcher.zig:onReady`) the server's end of the worker's control socket stops blocking, once for the worker's life, because lanes send and read on it from their loops. A launch whose session's gateway was lost waits in `awaiting_reattach`, and one whose session the gateway removed fails with `egress_attach`, alive, for the reaper (`Launch.egress_session_removed`), also when the removal comes while it waits for its reattach (`launcher.zig:reattachReady`). A launch with a current session publishes, and its boot token stays valid for the startup evaluations still pending ([egress.md](egress.md#the-token)); a launch that booted detached publishes with no session, and the reattach pass reaches it. `Deps.publish` (`service_deps.zig:launchPublish`) builds the record (`worker_registry.zig:buildRecord`), publishes it (`Pool.publish`), posts `dispatch_ready` for each handoff (`service_deps.zig:postHandoff`), and wakes the reaper to watch the worker when it serves no waiter and so has no reader. Every launch, published or failed, leaves a `LaunchTrace` for the cold-start benchmark and local-e2e (`Launcher.takeTraces`).

A failed launch (`launcher.zig:endFailed`) releases what it holds and hands the child's pidfd, cgroup leaf and state page, with the launch's definition (`Leftovers`), to `Deps.failed` (`service_deps.zig:launchFailed`), which gives the ticket back (`worker_factory.zig:endLaunch`), answers 503 to the waiters nothing is left to serve (`strandWaiters` with `launch_failed`) and queues the leftovers to the reaper. A failed launch starts no other, so a definition whose boot always fails waits for its next request to try again.

| `launcher.zig:LaunchFailure` | Cause |
| --- | --- |
| `cgroup_leaf`, `egress_wake_set` | the cgroup leaf could not be created or configured, or there is no cgroup root; the wake set or a detached launch's wake descriptors could not be created |
| `zygote_died`, `zygote_protocol`, `fork_refused` | the zygote exited or closed its socket before it replied; its reply came without the child's descriptors, the child's init outcome broke the protocol, or the `WorkerInit` send failed for any reason but a closed child end; it refused this fork and stays up for the next |
| `fork_reply_timeout` | no reply within `fork_reply_timeout_ms`; a late reply would read as the answer to the next request |
| `egress_attach`, `egress_gateway_required` | the gateway refused the session, its gateway removed the launch's session, or a launch whose session's gateway was lost before `WorkerReady` was refused a new one or could not be sent it; no gateway is wired or the attachment came back incomplete |
| `launch_resources` | the launch could not create or map the page, the payload ring or their eventfds (`LaunchFailure.fromLaunchError`) |
| `worker_init_failed`, `child_window_expired` | the child reported an init failure or ended before `WorkerReady`, found at the `WorkerInit` send or during the wait, and the launcher's warning names its reason or whether it died for memory ([boot.md](boot.md#a-failed-boot)); it missed its window |
| `control_socket`, `out_of_memory`, `stopping` | the control socket could not be made non-blocking, an allocation failed, the launcher stopped first |

`zygote_died` and `fork_reply_timeout` end the zygote (`LaunchFailure.endsZygote`): no fork request follows, the launcher kills the zygote so that its pidfd reports the exit (`launcher.zig:loseZygote`), and the zygote's exit stops the server, since nothing restarts it.

A gateway loss (`Launcher.gatewayLost`) starts a pass on the launcher thread: a gateway spawn at most once per `egress_prewarm_interval_ms`, then, one per turn, each live worker whose session is not of the current gateway (`Supervisor.nextStaleEgressWorker`). The worker gets a new session on its wake set, its record takes the session first, so that no token minted after the attach names the old one (`Supervisor.setWorkerEgress`), and then its control socket gets the session's worker half as an `egress_attach` packet, waiting up to `egress_attach_send_timeout_ms` for room. The gateway's refusal of the session, or a control socket that refuses the packet or takes nothing in time, retires the worker (`Deps.retireForEgress`, announced as `egress_session_failed`); an attach error of any other kind, or descriptors the server could not duplicate, leaves the worker detached on its old session and starts the pass over (`launcher.zig:reattachNextStale`, `trySendEgressAttach`). A session the gateway removed on its own (`Launcher.egressSessionLost`) is never replaced, and the report's cause decides the rest (`launcher.zig:dropLostSession`, [egress.md](egress.md#sessions)). A launch that held it fails at `WorkerReady` whatever the cause. A live worker's `liveness_closed` is left to its pidfd and control socket (counted in `egress_sessions_closed`), since every exit closes the pipe and a worker that detached on its own asks to be retired itself (`worker_retiring` with `egress_detached`). Only a `protocol_violation` retires the live worker (`Supervisor.retireEgressSession`, which takes it out of service through `Pool.retireForEgress` with departure `egress_removed`), announced to its lanes as `egress_session_removed`. While the pass waits for a gateway, a launch boots detached. A launch whose session's gateway was lost by `WorkerReady` attaches to the current gateway before it publishes; it publishes detached when no gateway is current or the attach fails for any reason but a refusal, and fails with `egress_attach` on a refusal or a failed send (`launcher.zig:reattachReady`).

## Scale-out

A worker runs its JavaScript on one VM thread, and its leaf's `cpu.max` holds it to one core (`common/limits/worker.zig:cpu_max_cores`), so a definition's workers run in parallel only on CPUs they find free. A worker more helps its definition when the slots it adds take requests that wait on I/O, or when an idle CPU gives its VM thread a core of its own. Otherwise it splits a CPU its definition's workers already wait for: no request runs sooner, every one pays more context switches, preemptions and colder caches, and the node pays the worker's memory. One CPU with 32 connections at the default `concurrency` of 2 grew to 16 workers when every wait launched one, at 1.4 to 1.9 times the CPU per request and 11 times the memory of one worker per CPU (`report/speed-gap/report.md`). Scale-in stays with the reaper's idle passes, and `pool_workers_max` stays the ceiling.

The launcher keeps the definitions whose pools answered `watch` (`launcher.zig:Launcher.scale_out_watch`) and, every `scale_out.sample_interval_ns` while it keeps one, takes a sample through `Deps.scaleOut` (`supervisor.zig:Supervisor.sampleScaleOut`, `scale_out.zig:Sampler`). A definition whose pool no longer wants a scale-out leaves the watch then (`Pool.keepScaleOutWatch`), and the next request that waits behind its workers brings it back. Each sample reads:

| Reading | Source | As |
| --- | --- | --- |
| the node's idle CPU | idle and iowait time of the CPUs the workers may run on, the server's affinity mask narrowed by the workers directory's `cpuset.cpus.effective`, from `/proc/stat`; at most the room left under the tightest `cpu.max` quota of the workers directory and its ancestors, from that cgroup's `cpu.stat` | thousandths of a core |
| each live worker's CPU | `usage_usec` of its leaf's `cpu.stat` | thousandths of a core |
| each live worker's wait for a CPU | `some total` of its leaf's `cpu.pressure`, the time at least one of its threads was runnable and not running | thousandths of the interval |

A reading counts only against one from the sample before, so a worker published since, and a definition watched since, wait one interval; a definition is therefore granted nothing before its waiters persisted a whole interval. The verdict (`scale_out.zig:decide`) grants a definition at most one launch per sample, when its sampled workers wait for a CPU less than `scale_out.stall_permille_max` of the time on average, since above that they already queue for a CPU and another worker would queue with them, and either of two holds. Its workers use less than `scale_out.cpu_bound_permille` of a core each on average: they are I/O-bound, their waiters wait for slots, and a new worker needs little CPU. Or a whole idle core is left in the sample's budget, which the launch then takes: the budget starts at the node's idle CPU, and each launch for CPU-bound workers takes a core from it, so definitions that share the node never count one idle core twice. Definitions are weighed from a start that moves by one each sample, so none always comes first. The launcher claims each granted definition at once with the scale-out allowed, and its pool decides again under its mutex.

Without PSI, a kernel whose cgroups have no `cpu.pressure`, a worker's wait reads as none and the CPU readings decide alone. A `/proc/stat` the server cannot read leaves no idle CPU, so CPU-bound definitions keep the workers they have while I/O-bound ones still grow.

Other rules were weighed. A cap per definition, such as one worker per CPU, ignores I/O-bound definitions, which need slots rather than CPUs, and lets each definition on a node assume every CPU is its own. The node's idle CPU alone cannot tell workers that wait on I/O from workers that wait for a CPU, so it stops I/O-bound growth on a busy node. The workers' CPU pressure alone grows one worker too many beside a lane that takes little CPU, since a CPU-bound worker alone on its CPU rarely waits; their CPU use alone reads a worker starved of CPU as I/O-bound. A queueing-delay target needs per-request timing in the pool, which keeps no clock. Reading a definition's CPU in one file, and weighting the CPU of tenants against each other, needs a cgroup per definition above its leaves, which the worker cgroup root does not have yet.

## The reaper

`reaper/root.zig:Reaper` is the node's one thread that retires workers: every worker that leaves its pool is torn down there, off the request path, and so is a failed launch's child: the kill, the exit wait, one drain of its console ring under its definition's name with worker id 0, then its page and leaf released (`reaper/root.zig:reapLeftovers`). Work arrives three ways. The thread whose pool call answered `retire` queues the worker (`Reaper.queueRetirement`, through `service_deps.zig:queueRetirement`, which passes the departure); the launcher queues a failed launch's leftovers (`Reaper.queueLeftovers`); and the reaper runs its own passes and watches the idle workers no lane reads. The retire queue holds one entry per record and one per launch-table entry, so it never fills: a pool reports each finished worker once and keeps its entry until `remove`, and the launcher counts the leftovers it handed over until the reaper reports them torn down (`Launcher.leftoversReaped`).

Each turn rescans the workers to watch, keeping the key and the reader epoch of each (`reaper/root.zig:scanReaderless`), waits in one `poll` until a source is ready or the next periodic pass is due, every 5 s by default (`reaper/reaping.zig:default_interval_ns`), handles what is ready, runs the passes when PSI fired or the interval is up, and carries out the queued retirements (`reaper/root.zig:processQueue`).

| Entry (`reaper/root.zig:buildPollSet`) | Wakes the reaper for |
| --- | --- |
| the wake eventfd | a queued retirement or leftovers, a pidfd rescan, stop |
| the demand-reclaim eventfd (`Supervisor.demand_reclaim_eventfd`) | a launcher claim at or above the high water, or one the memory gate refused (`Supervisor.nudgeDemandReclaim`) |
| the PSI trigger on `/proc/pressure/memory`, for POLLPRI | memory stalls past `psi_some_trigger`; when a kernel without PSI refuses the trigger, as one before Linux 6.4 does without `CAP_SYS_RESOURCE`, or the trigger reports an error, only the interval pass and demand reclaim read pressure ([memory-pressure.md](memory-pressure.md#the-node)) |
| the pidfd and the control socket of each live idle worker no lane reads | that worker's exit or a hang-up of its socket, taken as its death; or a readable socket, which the reaper never reads, since a lane may become the worker's reader at any moment and read it itself. A lane takes a slot through the pool without waking the reaper, so before the poll a lane may become the reader and the worker's answer turn the socket readable: the reaper takes the readability to `Pool.retireOnUnreadNotice` with the key and the epoch its scan saw, and the pool retires the worker as `recycled` only while it is live, holds no slot, has no reader and has that epoch. No lane took a slot since then, and a slot comes back only once its request's `request_done`, the last thing the worker sends for it, was read, so the bytes are the worker's `worker_retiring` notice or bytes it has no business writing. Otherwise the pool answers `stale` and the reader reads what the socket holds, a notice included (`reaper/root.zig:handleWatched`, `noticeReadable`) |

The periodic pass reads node memory, caches it for the memory gate, runs the idle pass, then the plan the pressure calls for (`reaper/root.zig:runPasses`). A reading that fails never reads as calm: it stands on the last reading that succeeded, 0% included, or reads as critical before the first and whenever the read failed for want of memory (`reaper/memory.zig:LastReading`, `readPressure`). Node memory is the highest share in use among the machine and every limited cgroup above the workers and above the server (`reaper/memory.zig:MemoryDomains`, [memory-pressure.md](memory-pressure.md#the-node)). The idle pass first posts `release_worker` again to the reader of each retiring worker that holds no request (`retryReleases`, `Pool.retiringReaders`), whether its retirement started idle or on its notice, since a post can be refused and a reader ignores one for a tenure it no longer holds; then it retires the workers idle past `worker_idle_ttl_ns`, 10 min by default and 0 to turn the pass off, within `sweep_budget_ns` and `sweep_cap_max` (`reaper/reaping.zig:idleTtlPass`). Demand reclaim runs when a launcher claim wakes it and memory is at soft pressure or above (`reaper/root.zig:demandPass`).

| Pressure (`reaper/memory.zig:memoryPressureFromUsedPercent`) | Used memory | Plan (`reaper/reaping.zig:memoryPressurePlan`) |
| --- | --- | --- |
| none | below 70 % | nothing, and the soft clock resets |
| soft | from 70 % | nothing for 30 s; then workers idle 10 min, 5 %, at most 4; after 10 s, idle 5 min, 5 %, at most 4; after 10 s more, idle 3 min, 10 %, at most 8 |
| hard | from 85 % | workers idle 3 min, 25 %, at most 8 |
| critical | from 92 % | any idle worker, 50 %, at most 16 |
| demand reclaim | soft or above, woken by a claim | any idle worker, 25 %, at most 4 (`reaper/reaping.zig:demand_plan`) |

A reap (`reaper/reaping.zig:reapWithPlan`) keeps the best candidates by score, up to the plan's cap. The score is the worker's private resident bytes from `smaps_rollup`, which leaves out the pages it still shares with the zygote, or its cgroup's `memory.current` when those cannot be read, weighted by idle age as a fraction of the idle TTL, clamped to 50 through 1000 thousandths (`reaper/memory.zig:workerMemoryVictimScoreWithUnknownFallback`). The reap retires the plan's percentage of the candidates, rounded up, at least one and at most the cap (`memoryPressureReapBudget`), and reads memory again after each retirement, stopping once usage falls below the high water. Only idle workers are candidates (`Pool.idleWorkers`), and each is asked again before it goes (`Reaper.retireIdleWorker`, `Pool.retireIdle`): a worker no lane reads is torn down at once, and a worker with a reader gets `release_worker` posted to that reader, whose `transferReader` answers `retire` and queues the retirement.

A retirement (`reaper/root.zig:retire`) checks with the pool that the worker is out of service with no holder and no reader, names how it ended (`idle`, `recycled`, `egress_reattach` for a worker no gateway could give a session, `egress_session_removed` for one whose gateway removed its session, or for a death `memory_high`, `memory_max` or `crash`, read while its cgroup still exists, `worker_table.zig:Record.classifyDeath`, `worker_table.zig:Death.ending`), and tears it down (`worker_registry.zig:teardown`): SIGKILL through the pidfd, a wait for the exit up to `PROCESS_EXIT_WAIT_MS`, the last drain of its console ring (`worker_registry.zig:drainDyingConsole`), its line in `workers.jsonl` with the CPU of its whole life from its leaf's `cpu.stat`, its leaf's `memory.peak`, both read through `common/cgroup.zig:readLeafFigure`, and that ending (`worker_registry.zig:writeWorkerRecord`, `analytics/workers.zig`), then `Record.vacate`, whose handle teardown closes the worker's descriptors, unmaps its page and payload rings and removes its cgroup leaf with retries. An egress retirement can reach the reaper ahead of the worker's own death, since the gateway reports on another path than the pidfd, so before its kill the reaper classifies both egress endings and keeps the retirement's only for a worker still running: a memory death the page or leaf shows wins, then `crash` when the pidfd already reads exited (`reaper/root.zig:egressRetirementEnding`, `worker_table.zig:Record.hasExited`). `Pool.remove` then frees the entry, and the reaper submits a launch with reason `capacity` when the pool wants one. The worker's egress session needs nothing, because the exit hangs up the liveness pipe its gateway watches. At shutdown the service stops the reaper last and carries out what its queue still holds on the exiting thread (`Reaper.drainRetirements`).

## Death detection

| Seen by | How | What follows |
| --- | --- | --- |
| the worker's reader lane | its pidfd (`exited`), a hang-up of its control socket (`peer_closed`), a fault in its output, a descriptor naming a request the worker's request table holds under another key (`request_table.zig:RequestTable.forwardCheck`) | the death path (`worker_fault.zig:faultWorker`): `Pool.markDead`, the last of the output when the reason leaves it trusted, `worker_died` to the other lanes the `Death` names, and the lane's own requests ended |
| a lane holding a request on the worker | a failed send, a forwarded descriptor or `request_done` that shows a fault, the grace backstop (`deadline_grace_expired`) | the same path, through the lane's registration of the worker (`command_flow.zig:faultForwardingWorker`) |
| a lane with no registration of the worker | a forwarded descriptor or `request_done` that shows a fault and arrives after the lane's request on the worker ended | `Pool.markDead`, which checks that the record still holds the worker's key, then `worker_died` to the lanes the `Death` names and a replacement (`worker_fault.zig:faultWorkerSeenElsewhere`) |
| the reaper | the pidfd, or a hang-up of the control socket, of a live idle worker no lane reads (`reaper/root.zig:workerExited`) | `Pool.markDead`, `worker_died` with `exited` to the lanes it names, the retirement at once when it names none |
| the metrics thread | a console ring that contradicts itself (`log_ring_corrupt`), a VM thread still working for an owner past that owner's deadline by the grace plus one metrics interval (`owner_overran`) | `Pool.markDead` under the record's `metrics_mutex`, then `service_deps.zig:announceWorkerDeath` (`analytics_drain.zig`) |
| the launcher | a reattach the gateway refused or the worker's socket did not take (`egress_session_failed`); a session its gateway removed for a protocol violation (`egress_session_removed`, `crash`, the tenant's fault) | `Pool.retireForEgress` with departure `egress` or `egress_removed`, announced the same way (`service_deps.zig:launchRetireForEgress`, `launchRetireEgressSession`) |
| the launcher | the zygote's pidfd | the server stops (`service_deps.zig:launchZygoteExited`) |

A worker's pidfd and control socket are always watched: by its reader for the whole tenure, which an idle worker keeps, and by the reaper while the worker is live, idle and has no reader; a lane that gives the role up wakes the reaper to rescan (`Reaper.wakeForPidfdScan`). The first `markDead` owns the death and every later one gets null, so each lane ends its requests on the worker once, with the reason it recorded first (`completions.zig:Registration.fault`). A worker that exited or hung up counts as `memory_high` when its page says its sentinel ended it for memory, as `memory_max` when its cgroup counted an `oom_kill`, and as `crash` otherwise (`worker_table.zig:Record.classifyDeath`); its requests' records say `memory` for either memory death (`worker_table.zig:Death.errorCode`). A lane that owns a death, and `service_deps.zig:announceWorkerDeath` for the metrics thread and the launcher, then ask for a replacement or answer 503 to the waiters nothing can serve; the reaper submits one after the retirement frees the entry.
