# The request path

This document follows one HTTP/2 request through the server: the ingress lane that accepts its connection, admission into the pool of its worker definition, the dispatch to a worker, the response, the finish and the records the request leaves, then the failure domains, the deadline and every named limit on the way. The lane's code is in `runtime/src/server/ingress/` with its `runner/` and `http2/` directories, the pool, the request table and the usage records are in `runtime/src/server/supervisor/`, and their `//!` headers own the mechanics; [scheduler.md](scheduler.md) covers the pool, the launcher and the reaper. A reference such as `dispatch.zig:dispatchWithHead` names a file and a symbol in it. A bare file name is in one of those directories, a name two of them share carries its directory (`runner/root.zig`, `http2/connection.zig`), and any other path is relative to `runtime/src/`.

## The lane thread

The server runs one lane per listener, each on its own thread pinned to the CPU the lane plan gave it (`service.zig:Service.init`, `runner/root.zig:LaneWorker.threadMain`). Once its loop runs, the lane thread alone changes its connection, request and stream slabs, its deadline wheel and connection deadline heap, its worker registrations, its read buffer and its HPACK scratch. Other threads reach a lane only by posting to its command queue under `runtime_mutex` (`runner/root.zig:LaneWorker.post`), by raising one of its wake bits under the same mutex, which writes the queue's eventfd only when the bit was clear (`runner/root.zig:LaneWorker.raiseWake`, `wake`), by reading its counters under `counters_mutex` or its atomic `lane_state`, and, for the metrics thread, by draining its access records (`runner/root.zig:LaneWorker.access_ring`).

A lane's tables are fault-in slabs (`slab.zig:FaultInSlab`): each reserves its capacity as address space with MAP_NORESERVE and touches an entry only when it first hands it out, from a high-water mark and then from a LIFO free stack, so a lane costs memory as far as it has been used, not as far as it could be. Every entry carries a generation that never repeats, which is what a key names along with the index, so a key that outlives its entry reads as stale.

Every event source of a lane completes on the lane's one io_uring (`ring_driver.zig:run`), and each completion runs one handler of `fault.zig:loop_handlers`:

| Source | Event | Handler |
| --- | --- | --- |
| the listener's multishot accept | an accept tag (`accept.zig:unpackAcceptUserData`) | `accept_flow.zig:handleAcceptCqe` |
| the command queue's eventfd, for commands and wake bits | `command` (`event_sources.zig:EventKind`) | `command_flow.zig:handleCommands` |
| the lane's one deadline timerfd | `deadline_timer` | `deadline_driver.zig:handleDeadlineTimer` |
| a client socket, one one-shot poll per interest | `connection_read`, `connection_write` | `ring_driver.zig:handleConnectionReadable`, `handleConnectionWritable` |
| a worker the lane reads: its completion eventfd, control socket, fault socket and pidfd | `worker_completion`, `worker_control`, `worker_fs_fault`, `worker_pidfd` | `worker_completions.zig:handleWorkerCompletions`, `ring_driver.zig:handleWorkerControlReadable`, `handleWorkerFsFault`, `handleWorkerPidfd` |
| a worker the lane sends to, while one of its sends waits for room in the socket | `worker_control_writable` | `ring_driver.zig:handleWorkerControlWritable` |

A pass of the loop (`ring_driver.zig:runPass`) renews the lane's egress lease when the gateway generation moved, re-arms the accept when it is due, takes up to 64 completions and runs their handlers, then runs the queued work: each connection a handler queued for a turn, the worker faults deferred out of stream handlers, and one `request_ended` packet for the gateway (`ring_driver.zig:runQueuedWork`). Handlers only prepare submissions: the pass ends in one `io_uring_enter` that submits them all, and waits for a completion only when the pass found no work. Only a pass that fills the ring's 256 submission entries enters early, and every enter is counted (`event_sources.zig:LaneRing`), so the lane's counters show `ring_enters` against `loop_passes`. A completion whose connection or registration moved on since its poll was armed carries an older generation and is counted as stale (`ring_driver.zig:dispatchCqe`, `workerPollReady`).

An accepted socket takes a connection slot and holds it until it closes (`accept_flow.zig:startConnection`); a socket that finds the lane's 4096 slots taken, or cannot be set up, closes alone as `connection_limit` or `setup_failed` (`fault.zig:classifyAccept`). A connection's slot is about 1.2 KiB: its streams live in the lane's stream slab, and every socket read of every connection goes into the lane's one read buffer, a frame header and the largest frame long (`http2/lane_resources.zig:LaneResources`). The lane handles every byte of a read before it reads another connection, so between reads a connection keeps only what a frame cut by the read boundary needs (`http2/frame_reader.zig`): the preface's progress, part of a frame header, a control frame's payload of at most 192 bytes, and where it stands in the padding and priority fields of DATA and HEADERS. DATA reaches its stream in pieces as its bytes arrive, the frame's whole length taken from the receive windows with its first piece. Only a header block is held whole, and the unfinished blocks of a lane's connections share a budget of 8 MiB: the connection whose fragment would pass it closes with GOAWAY ENHANCE_YOUR_CALM and no other connection is touched (`http2/lane_resources.zig:HeaderBlockBudget`). The TLS handshake runs in BoringSSL and hands the traffic keys to kernel TLS (`tls_handshake.zig:drive`), and the server's SETTINGS announce 64 concurrent streams, 64 KiB frames, a 512 KiB stream window and a 32 KiB header list, with a WINDOW_UPDATE that raises the connection window to 2 MiB (`writing.zig:queueServerSettingsAndAck`). One turn of a connection reads its socket at most 8 times (`http2/connection.zig:reads_per_drive_max`) and stops reading while writes are queued, so a client that does not read its responses is not read either. Each connection has one deadline at a time, from its accept on (see Deadlines).

When the server stops, the lane refuses new work and drains what it holds (`ring_driver.zig:handleStop`). Every HTTP/2 connection gets GOAWAY with NO_ERROR, a socket accepted after the stop closes before its handshake (`accept_flow.zig:acceptConnection`), and a newly matched stream gets 503. Admitted requests run to their end. The lane gives up each reader tenure over a worker it has no request on, keeps reading the workers other lanes still use until they go idle, and closes itself to posts once its command queue is empty, since a `dispatch_ready` left unrun would hold a worker slot for good. Connections still open then close as `server_stop`.

## Admission

A header block is at most 32 KiB, whether one HEADERS frame carries it or CONTINUATION frames extend it: a split block is reassembled within that and 128 frames (`connection_slot.zig:Slot.h2AppendHeaderBlock`), and a block past the bound is never decompressed and closes the connection (`reading.zig:decodeHeaderBlock`). A block within it is decompressed whole, which keeps both HPACK tables in step, within 259 fields and 32 KiB of decoded bytes (`reading.zig:decodeHeaderBlock`, `request_head.zig:max_header_count`), then checked by `request_head.zig:parse`, which also normalizes the authority once and keeps it in the head it returns (`request_head.zig:ParsedHead.authority`). A head over those bounds gets 431, a declared body over 4 MiB gets 413 and a malformed head, a malformed authority included, gets RST_STREAM PROTOCOL_ERROR, each on its own stream (`reading.zig:refuseRequestHead`). A head with `expect: 100-continue` that announces a body gets its 100 before the lane's stream handler runs (`reading.zig:processRequestHead`). Every whole request head opens a stream as far as the connection's deadlines go, whatever the lane then answers on it, so it ends the pre-request deadline for good and restarts the idle one (`connection_slot.zig:Slot.noteStreamOpened`).

`admission.zig:startDynamicH2` takes the stream into the connection's table, refusing it with RST_STREAM REFUSED_STREAM past 64 streams on the connection or once the lane's 8192 stream entries are taken (`stream_table.zig:h2ReserveStream`), and classifies the stream by its path alone (`admission.zig:streamTarget`). A path under `/__collo/` belongs to the server (`server/config/pattern.zig:isReserved`): `/__collo/healthz` is answered from the server's state with atomic loads and a zero-timeout poll of the zygote's pidfd (`admission.zig:healthState`), even while the server stops, and any other such path gets 404 with an access record. Every other path is matched once against the immutable route table, and a miss gets 404 with an access record. A matched stream gets 503 once the server is stopping. The authority selects nothing: it reaches the worker as the request's normalized authority, which also replaces its `host` header (`admission.zig:h2HeadersForIpc`).

Admission fixes the request's one deadline, the admission time plus its definition's `timeoutMs`, and takes a request id (`service.zig:Service.allocateRequestId`, an atomic counter that skips 0), a lane request slot, a wheel entry at the deadline and the stream's binding to the request (`stream_table.zig:h2BindRequest`). A full request slab sheds that stream alone, with REFUSED_STREAM. The lane's slot (`request_slot.zig:RequestSlot`) holds the route key, the deadline and the access facts; the lane assigns the route, the deadline and the facts' identity, and nothing a worker sends changes them. Then the lane asks the definition's pool for a worker slot (`admission.zig:placeRequest`):

| `pool.zig:Pool.acquire` answers | The lane |
| --- | --- |
| `.acquired`: a free slot of the most recently used live worker that has one, with a reader grant | discharges the grant (`worker_registration.zig:dischargeReaderGrant`) and dispatches at once (`dispatch.zig:dispatchWithHead`) |
| `.wait`: the request is the newest waiter in the pool's FIFO | copies its head into an `OwnedHead`, since the decoded head is freed once the stream handler returns, and calls `admission.zig:growOrStrand` |
| `.full`: the FIFO holds `common/limits/pool.zig:pool_waiters_max` (256) requests | answers 503 at once (`request_finish.zig:RequestOutcome.unserved`) |

A waiter stays the lane's own state: it keeps its lane slot and its wheel entry, and the pool records only whose turn comes next. `admission.zig:growOrStrand` submits a launch when the pool wants one under the memory gate (`pool.zig:Pool.growthWanted`). When growth is refused and the pool has no live worker and no launch in flight, it answers the waiters nothing can serve (`pool.zig:Pool.takeStranded`) with 503, its own directly and other lanes' through `dispatch_failed`.

## Dispatch to a worker

A request reaches a worker only through `dispatch.zig:dispatchWithHead`: at admission, when a `dispatch_ready` hands it a slot (`command_flow.zig:handleDispatchReady`), or when this lane frees a slot that its own waiter takes (`request_finish.zig:handOn`). A handed slot whose worker left service before the request used it goes back, and the request asks its pool again (`dispatch.zig:dispatchToWorker`). The dispatch binds the request to the worker slot, adds it to the lane's registration of the worker, keys its wheel entry to the worker at the deadline, turns the stream from `preparing` to `active`, and records the request in the worker's request table before the worker can hear of it (`request_table.zig:RequestTable.record`), so the worker's usage record never reaches a drain ahead of its entry. A request that waited for a worker launched after its admission is marked a cold start, with the worker's boot time and the time it waited in its access facts.

The `request_begin` carries the request's `DispatchWork` (`common/ipc/messages.zig:DispatchWorkView`, encoded by `common/ipc/dispatch.zig:encodeDispatchWorkInto`): the request and worker identities, the normalized authority, method, path, query, headers, body framing, route captures, the route's index in its definition's route table (the `route` of its `RouteKey`, which a worker of the definition finds at the same index in the table WorkerInit carried), the deadline and an egress token. The lane mints the token from its own lease on the current gateway (`server/gateway/lease.zig:Lease.mint`) for the worker's session, which it reads under the pool's mutex because the launcher rewrites it on a reattach (`supervisor.zig:Supervisor.workerEgress`). The token holds the request's identity and deadline, the one policy of the gateway's table and the per-request fetch budget (`dispatch.zig:requestTokenFields`), in 56 bytes with a 16-byte HMAC-SHA256 tag under the gateway's key (`common/ipc/egress_token.zig`). A lease that holds another gateway's key mints `egress_token.none`, and the worker refuses that request's fetches itself. The dispatch takes no manager lock and makes no gateway call.

The lane encodes the `DispatchWork` into its own 1 MiB scratch and sends descriptor and payload as one SEQPACKET datagram through the worker's `dispatch_send_scratch`, under `Record.send_mutex`, since every lane that holds a slot of the worker may send to it (`dispatch.zig:sendBegin`, `worker_table.zig:Record.send_mutex`). Once the begin is in the socket, the wheel entry moves to the deadline plus `hard_timeout_grace_ns` (`dispatch.zig:beginReachedWorker`), and the body the stream buffered while it waited follows. A send that would block is backpressure: the begin is parked with its own copy of the payload, zeroed when freed because it holds the token (`request_slot.zig:ParkedBegin`), a writability poll on the worker's control socket retries it (`ring_driver.zig:armWorkerControlWritable`), and the request's deadline still bounds the wait. A request's sends leave in order: its begin, then a reset, then the buffered body (`dispatch.zig:flushRequestSends`). A send that fails for the worker's doing stops the request's sends and queues the worker's death path for the end of the running handler (`dispatch.zig:failSend`).

## Bodies and credit

A request body is bounded by its `content-length`, or by 4 MiB without one (`stream_table.zig:h2RecordRequestBodyChunk`, `common/limits/http_body.zig:MATERIALIZED_BODY_BYTES_MAX`). A body that breaks its length gets 400 and one over the bound gets 413 (`request_body.zig:rejectH2RequestBody`): a waiting request ends with the answer, and a dispatched one leaves its stream and is cancelled toward its worker.

The HTTP/2 credit of body bytes goes back to the client only once the server no longer holds them (`http2/connection.zig:DataFrameHandling`). A stream whose request waits buffers its DATA with the credit withheld (`flow_control.zig:h2AppendPreparingBody`); the buffer leaves after the begin, and its credit returns as WINDOW_UPDATE frames once the worker has the bytes (`request_body.zig:flushPendingBody`). A dispatched stream sends each chunk at once, inline up to `shared_payload_threshold` (32 KiB) and through the worker's server-to-worker payload ring above it, under `send_mutex` because the ring takes one producer at a time (`request_body.zig:sendBodyChunk`); a run of up to 32 unpadded DATA frames goes as one batch packet (`reading.zig:tryHandleDataFrameBatch`, `request_body.zig:sendBodyBatch`). A chunk that finds the socket or the ring full queues on its stream behind the request's earlier bytes with its credit held, so a worker that stops reading stalls the client's sender. The receive windows bound what a stream can buffer: 512 KiB per stream and 2 MiB per connection, below the buffer bounds that `flow_control.zig` asserts at compile time.

A ring has one writer side and one reader side, and a writer that finds no room marks the ring's header and checks the room once more; the reader's next release clears the mark and signals the writer's credit eventfd, and a release that finds no mark makes no system call (`common/ipc/ingress_channel/payload_ring.zig:SharedPayloadReadRelease`). A lane whose body finds the server-to-worker ring full first registers itself for the worker slot its request holds (`worker_table.zig:Record.body_waiters`), then marks the ring (`request_body.zig:waitForRingRoom`). The worker's release signals its own completion eventfd, which the worker's reader lane polls anyway; after draining it the reader raises the `payload_credit` wake bit on each registered lane (`worker_completions.zig:drainWake`), whose next pass retries every send blocked on a ring (`dispatch.zig:retryRingBlockedSends`). No lane polls a credit eventfd. The worker-to-server ring works the same way in the other direction: the worker marks it when a response chunk finds no room, and the reader's release signals the worker's payload credit eventfd (`worker/serve/response_payload_writer.zig`).

A client's RST_STREAM ends a waiting request (`stream_gone`, recorded as 499) and a dispatched one whose begin never left. A request whose begin reached the worker stays until the worker completes it, after a `request_reset` tells the worker the stream is gone, so a reset never frees a slot the worker may still use; a completion already parked on the request ends it at once (`request_body.zig:handleH2ResetFrame`, `dispatch.zig:cancelRequestToWorker`).

## The reader lane and forwarding

One lane at a time reads a worker's output: its control socket, completion eventfd and ring, fault socket and pidfd (`worker_registration.zig:armWorkerPolls`). The reader is the first lane to take a slot of a worker that has none, and it keeps the role while the worker alternates between idle and busy; [scheduler.md](scheduler.md) covers how the role moves. Every lane with a slot sends to the worker, and the reader forwards what belongs to other lanes through their command queues.

The reader drains up to 64 packets per wake (`worker_control.zig:control_packets_per_drain_max`) and stops early at a connection with bytes to write, so they go out before more of the response (`worker_control.zig:Pace`). It receives a packet only while the worker's forwarding window still holds a whole batch of 32 descriptors: at most 64 of a worker's forwarded descriptors and answers to their ring payloads wait in lanes' queues at once (`common/limits/ingress.zig:forwarded_commands_per_worker_max`, `h2_worker_ipc.zig:windowHasRoom`), so a worker that writes faster than the lanes it answers can apply waits in its own socket. A full window stops the reader's control poll, not its completion poll, and the release that makes room for a batch again raises the `window_reopened` wake bit on the reader, which resumes the drain (`h2_worker_ipc.zig:releaseForwardUnit`, `worker_completions.zig:resumeWindowBlockedReaders`). The reader takes a unit only while the window has one (`h2_worker_ipc.zig:acquireForwardUnit`), so the count never passes the window, every decrement is a release, and no step back into room goes unannounced. A packet that carries descriptors, is shorter than its kind or is of a kind the channel does not carry is a worker fault, and the rest decode with the reader's account of the worker-to-server ring (`completions.zig:Registration.ring_payloads`). A descriptor acts only on the request it names exactly: one whose request ended or whose stream went away is a race and drops, and any other mismatch is the fault `descriptor_names_no_request` (`h2_worker_ipc.zig:resolveDescriptor`). A response head is decoded within 256 headers and 16 KiB (`writing.zig:max_worker_response_header_count`, `max_worker_response_header_bytes`) and encoded with the connection's HPACK encoder; a head without END_STREAM and its first chunk, both inline in one batch packet, go out as one write (`h2_worker_ipc.zig:tryHandleHeadChunkPair`). The lane decides whether a head went out from its own HTTP/2 record (`stream_table.zig:responseHeadQueued`); no flag a worker writes enters that decision.

A descriptor of another lane's request travels as `forwarded_descriptor` (`h2_worker_ipc.zig:forwardDescriptor`), once the reader checked it against the worker's request table: a request the worker holds under another key is the fault `descriptor_names_no_request`, and one the worker does not hold drops at the reader (`request_table.zig:RequestTable.forwardCheck`), so a worker's output reaches another lane's queue only for that lane's own requests on that worker. An inline payload is copied into the command; a ring payload stays in the ring, held in the reader's account until the owner answers `payload_consumed`. The owner answers every ring payload it was forwarded before it drives the connection or finishes the request, and the reader frees ring bytes only over the answered prefix, in ring order (`h2_worker_ipc.zig:handlePayloadConsumed`). When the owner's queue refuses a descriptor, the reader drops the rest of that response (`completions.zig:ForwardLoss`) but still forwards the completion, so no client gets a response with a gap: a lost head ends the request with 502 when the completion arrives, and after a lost later descriptor the completion parks until the grace backstop resets the stream (`request_finish.zig:finishDispatched`, `deadline_driver.zig:expireDispatchedRequest`).

A completion wake drains the control socket first, because a worker sends a response before it publishes the completion, and reads the eventfd and the ring only once the socket is empty; a socket still holding packets after 4 drains leaves both for the poll's next wake (`worker_completions.zig:handleWorkerCompletions`). The drain copies each record once and acts only on the validated copy (`worker_completions.zig:drainCompletions`). A record of another lane's request is forwarded once, and only while the worker's request table holds that request under that key (`request_table.zig:RequestTable.claimCompletion`), so a worker cannot fill another lane's queue with completions.

| Command (`commands.zig:Command`) | Sent by | The receiving lane | When the post is refused |
| --- | --- | --- | --- |
| `dispatch_ready` | the lane whose `Pool.release` handed a slot on, or the launcher's publish (`service_deps.zig:postHandoff`) | discharges the reader grant, then dispatches the waiting request or gives the slot back (`command_flow.zig:handleDispatchReady`) | the sender returns the slot with its grant (`pool.zig:Pool.returnHandoff`), which may hand it to the next waiter |
| `dispatch_failed` | a lane, the launcher or the metrics thread after `Pool.takeStranded` | answers 503 if the request still waits | the request gets 503 at its deadline |
| `forwarded_descriptor` | the worker's reader | applies it as its own read and answers its ring payload (`h2_worker_ipc.zig:handleForwardedDescriptor`) | the reader frees the ring bytes and drops the rest of the response; it takes only reserved places, so it is refused when the lane is not running or when obligations past their share fill the reserve |
| `forwarded_completion` | the worker's reader | parks the completion or finishes the request | the record drops; it takes any free place, a reserved one first |
| `payload_consumed` | the request's owner | frees the answered prefix of the ring | the bytes stay held, and the payloads behind them wait until their requests' deadlines |
| `release_worker` | a lane granted `transfer_from`, or the reaper retiring an idle worker | gives its tenure up if the pool lets it go (`command_flow.zig:giveUpTenure`) | the pool forgets the request (`Pool.releaseRequestLost`), and the reaper posts again on its next pass |
| `worker_died` | the lane, reaper, metrics thread or launcher that saw the death | runs the death path for its own requests and tenure (`worker_fault.zig:faultWorker`) | the lane learns of the death from the worker's channels or its requests' deadlines |

A lane's queue has 1024 ordinary places and a reserve: for each entry of each pool's table, one death, one reader grant, one forwarded completion per slot and the entry's 64 places of forwarded output (`lane.zig:obligationReserve`). A forwarded descriptor and its payload answer take only reserved places, so a worker's output never takes an ordinary place. A death, a reader grant and a forwarded completion take a reserved place first and an ordinary one once the reserve is full. Every other command takes only ordinary places (`commands.zig:Command.placement`, `Queue.push`). Commands to one lane run in the order they were posted, and each handler checks the keys its command carries against the lane's own state before it acts (`command_flow.zig`).

## Completion and finish

A completion finishes its request at once, unless the lane's record says the response head went out and the response has not ended: then it parks on the request until the end is queued, the stream goes away or the wheel entry fires, which stays armed (`h2_worker_ipc.zig:h2CompletionDeferDecision`, `worker_completions.zig:deliverCompletion`). A completion for a request whose begin never left is stale.

Every request ends in `request_finish.zig:finishRequest`, once, whatever ended it, and a parked completion wins over any other outcome. A dispatched request emits its access record, settles its usage and its request table entry, notes the end of its egress token, answers or resets its stream, leaves the worker's registration, frees its lane slot and wheel entry, and only then gives its worker slot back (`request_finish.zig:finishDispatched`). A waiting request leaves the pool's FIFO (`pool.zig:Pool.cancelWaiter`); if a handoff took it first, its `dispatch_ready` finds the request gone and gives the slot back.

| `request_finish.zig:RequestOutcome` | The client gets | Access status | Usage |
| --- | --- | --- | --- |
| `worker_completion` | the worker's response, or 502 when the worker ended with no head on an open stream | the worker's status, or the lane's 502 | the worker's record |
| `waiter_expired`, `unserved` | 503 | 503 | none |
| `rejected` | the lane's own answer to a waiting request | that answer's status | none |
| `stream_gone` | nothing, the stream is gone | 499 | none |
| `send_expired` | 504; the worker stays in service | 504 | none |
| `deadline_expired` | 504, or RST_STREAM after the head | 504 | a floor naming `deadline_grace_expired` |
| `worker_died` | 502, or RST_STREAM after the head | 502 | a floor naming the fault reason |
| `shutdown` | nothing; the connection closes | 503 | a floor with `internal_error` |

A request whose begin never reached the worker leaves no usage, whatever ended it (`request_finish.zig:settleOutcomeFor`). The lane writes the access record's identity, duration and every status it synthesizes; a worker's completion supplies only its status, error code and its CPU, I/O and waiting times (`request_finish.zig:emitAccessRecord`). The record goes onto the lane's access ring of 2048 records, with one producer and one consumer, which the metrics thread drains every 100 ms into `access.jsonl`; a full ring drops and counts (`server/analytics/access.zig:AccessRing`, `analytics_drain.zig`). Before admission, only a 404, for a route miss or a reserved path, writes a record; the health answer, a refused stream, a head the lane cannot forward and the answers of a stopping server leave none.

The worker appends a request's usage record to the ring on its page before it publishes the completion. The request table entry recorded at dispatch goes from `in_flight` to `awaiting_record` when the request settles as completed, and the drain that writes or drops the worker's record frees it; when a drain took the record first, the entry is `recorded` and the settle frees it (`request_table.zig:RequestTable.settle`). The metrics thread drains every worker each tick (`usage_drain.zig:drainAll`), and a settling lane drains the worker itself once 32 settled requests await their records (`request_table.zig:awaiting_record_max`). A drain keeps a record only when the request table of the worker whose ring held it expects one under that request id, and writes it with the server's identity for the worker and the route pattern the table recorded (`usage_drain.zig:requestIdentity`). A request the server ended gets a floor, built from what the worker's live slot measured when one matches, unless the worker already authored a record (`usage_drain.zig:synthesizeFinalAccountingForLifecycle`).

The freed slot goes to the oldest waiter at once (`pool.zig:Pool.release`). A waiter of this lane is dispatched on it before the finish returns, another lane's waiter gets `dispatch_ready`, a refused post returns the slot to the pool, which may hand it on again, and a dead worker's last slot sends the worker to the reaper (`request_finish.zig:handOn`); no retry timer exists on the path. The token's end goes into the lease's batch of up to 1024 entries (`server/gateway/lease.zig:Lease.noteEnded`), sent as one `request_ended` packet at the end of the pass, or at once when the batch fills; an entry for a gateway other than the lease's is dropped, since that gateway's budgets went with it. The send never waits, and a batch the gateway's socket refuses is counted and costs only fetches that run until their tokens' deadlines (`server/gateway/lease.zig:Lease.flush`).

## Failure domains

A failure belongs to a connection, a worker, the lane or the server (`fault.zig`). A loop handler returns `LaneFault!void`, so the lane's own faults are the only errors that leave one; a client's or a worker's failure is a value the handler acts on before it returns: `ConnectionOutcome` (`keep`, or `close` with a `ConnectionCloseReason` and a GOAWAY code), `WorkerOutcome` (`ok`, `would_block`, or `fault` with a `WorkerFaultReason`) and, for a worker's response, `ResponseQueueOutcome`. Each callee's errors are sorted by its own table where it is called (`fault.zig:classifyConnectionError`, `classifyWorkerError`, `classifyResponseQueueError`), and a table names every error of its callee, so an error a callee adds does not build until someone assigns its domain.

A connection closes on a TLS failure, an HTTP/2 connection error (a protocol, frame size or flow-control error, an HPACK desync, a SETTINGS frame of more than 32 entries, a header block of more than 128 frames, more than 128 control or empty DATA frames in one read), a header block past 32 KiB in any number of frames, a header block the lane's budget cannot hold, a write queue past 1 MiB, a failed allocation sized by the client, the peer's close, its pre-request, idle or stall deadline, or the server's stop (`fault.zig:ConnectionCloseReason`). The close takes two steps. The decision stops the connection's reads and puts GOAWAY at the end of its queue when HTTP/2 can still speak, and the connection's next turn resets each of its streams toward its worker through the client-reset path, flushes the GOAWAY and tears the connection down (`connection_flow.zig:closeRuntimeConnection`, `finishClose`). A failure of one stream answers or resets that stream alone: a malformed head (`reading.zig:refuseRequestHead`), a body over its bounds (`request_body.zig:rejectH2RequestBody`), or a response the stream cannot buffer, which also cancels the request toward a worker that stays alive (`h2_worker_ipc.zig:actOnQueueError`).

A worker fault runs the death path (`worker_fault.zig:faultWorker`). The pool takes the worker out of service first (`pool.zig:Pool.markDead`); a reader whose fault reason leaves the output trusted (`peer_closed`, `exited`, `deadline_grace_expired`, `egress_session_failed`) reads and forwards the last of it (`worker_fault.zig:finalDrainTrusted`); the other lanes the death names get `worker_died`; and the lane ends its own requests on the worker with 502, or with 504 for each one past its own deadline when the fault is the grace backstop's, or with RST_STREAM after a head, putting the reason into each access record and usage floor. A fault met inside a stream handler takes the worker out of service at once and leaves the rest for the end of the handler (`worker_fault.zig:deferWorkerFault`). The lane then asks for a replacement or strands the waiters (`admission.zig:growOrStrand`), and the reaper does the retirement (`service_deps.zig:queueRetirement`); no kill, exit wait or cgroup removal runs on a lane.

| `fault.zig:WorkerFaultReason` | Cause | Error code (`worker_fault.zig:errorCodeForFault`) |
| --- | --- | --- |
| `packet_short`, `packet_too_large`, `unknown_kind` | a control packet shorter than its kind, larger than 1 MiB, or of a kind its channel does not carry | `crash` |
| `unexpected_descriptor`, `too_many_descriptors`, `zero_length_datagram_with_descriptors` | a packet that carries descriptors, more than one receive holds, or an empty datagram with descriptors | `crash` |
| `ingress_channel_undecodable`, `fs_fault_request_undecodable` | a packet or a fault request that fails to decode | `crash` |
| `descriptor_names_no_request`, `response_head_invalid`, `response_descriptor_invalid` | a descriptor for a request the worker was not sent, a head over the caps or with a header the client may not receive, a descriptor its stream's response state does not admit | `crash` |
| `completion_ring_fatal`, `completion_ring_corrupt`, `completion_sequence_mismatch`, `completion_record_invalid` | an overrun completion ring, or a ring or record that fails validation | `crash` |
| `payload_ring_invalid` | ring cursors that contradict each other, or a descriptor claiming bytes the ring does not hold | `crash` |
| `channel_failed` | a socket or eventfd of the worker that failed with no other reason | `crash` |
| `peer_closed`, `exited` | a hang-up of the control or fault socket, the exit its pidfd reports | `memory` when the page or the cgroup says so (`supervisor.zig:Supervisor.classifyWorkerDeath`), `crash` otherwise |
| `deadline_grace_expired` | a request past its deadline and the grace | `deadline` |
| `usage_record_protocol`, `log_ring_corrupt` | a usage or console ring on its page that contradicts itself, seen by a drain | `crash` |
| `allocation_failed`, `egress_session_failed` | an allocation for a packet that failed, no gateway able to give the worker a session | `internal_error` |

A lane fault is a broken invariant of the lane's own state: a ring error that is not transient, or a transient one 64 times in a row (`fault.zig:ringErrorIsTransient`), a completion tag it never packed, a fatal accept errno, a failure of its timerfd or command eventfd, a table or queue sized from its own limits that overfills, records of its own that disagree, a message it built wrong, or the creation of any of these at start (`fault.zig:LaneFault`). The lane thread stores the error, marks itself failed and raises the stop flag (`runner/root.zig:LaneWorker.threadMain`). The service's thread sees it within 5 ms, stops the lanes, the metrics and console threads, the launcher and the reaper in that order, and returns the error, so the server exits (`service.zig:Service.run`, `stopAndDrainForExit`); a lane owns one share of every connection on the node, which is why its fault stops the server. Teardown after a lane fault ends each request as `shutdown`, closes each connection and announces the deaths the lane still owed (`ring_driver.zig:deinitRuntime`). The server's own faults are the zygote's exit, a listener failing and a boot that does not complete (`fault.zig`), and off the lanes a post or pool call that fails stops the server too (`service.zig:Service.recordFatalError`).

## Deadlines

A request has one deadline, fixed at admission from its definition's `timeoutMs`: 30 s by default (`server/config/model.zig:default_settings`) and at most 15 min (`common/limits/server.zig:request_timeout_ms_max`). It travels in the `DispatchWork` and in the egress token, and the lane's wheel entry follows the request:

| The request | Its wheel entry | When the entry fires |
| --- | --- | --- |
| waits for a worker slot | at the deadline | 503 (`waiter_expired`), and the waiter leaves the FIFO |
| holds a slot, its begin parked on a full socket | at the deadline | 504 (`send_expired`); the worker never heard of the request and stays in service |
| its begin reached the worker | at the deadline plus `hard_timeout_grace_ns`, 250 ms (`supervisor.zig:default_hard_timeout_grace_ns`) | the grace backstop |

A worker answers 504 itself when the deadline passes, so the backstop fires only for one that did not (`deadline_driver.zig:expireDispatchedRequest`). It first lets a completion that came in time win: the reader reads the control socket to its end, for up to 64 drains, then the ring (`worker_completions.zig:readForBackstop`), and a lane that only holds the request runs the commands the reader forwarded to it. A worker that kept its socket filling through that read gets one more grace, once (`request_slot.zig:RequestSlot.backstop_deferred`). A completion parked behind its response then ends the request and resets a response that never ended; otherwise the worker takes the fault `deadline_grace_expired`, which answers every request on the worker past its own deadline 504, on every lane, and the others 502, or RST_STREAM after a head (`worker_fault.zig:finishRequestsOnWorker`). A healthy worker therefore never dies of a deadline.

The deadline wheel, the heap of connection deadlines and the accept backoff share the lane's one timerfd (`deadline_driver.zig:nextDeadlineNs`). An entry due before every other re-arms it (`admission.zig:insertWheelEntry`), a removed entry may leave it armed early, which costs one spurious wake, and one wake expires at most 64 entries (`deadline_driver.zig:expired_batch_max`). The pool drops a waiter whose deadline passed when a slot frees, since its lane answers it (`pool.zig:Pool.release`). The access record's duration starts at admission, so time spent waiting shows in it.

A connection has one deadline at a time, one entry in the heap, and its state chooses which (`deadline_driver.zig:desiredDeadline`):

| Deadline | Runs | At expiry |
| --- | --- | --- |
| pre-request, 3 s | from the accept until the client's first whole request head, whatever else it sends | GOAWAY NO_ERROR, then the close |
| none | while a stream serves a request, waiting for a worker or dispatched (`connection_slot.zig:Slot.servesRequest`), and no header block is open | |
| stall, 10 s | from the last byte read or written, while a header block is open, or while no stream serves a request and the lane holds something only the client can move: part of a frame, writes the socket has not taken, or response bytes the send windows hold back | the close at once, without waiting for the write queue |
| idle, 300 s | from the moment the connection last came to serve no request, while nothing stalls; every new stream restarts it, one the lane answers alone included, and no other frame does | GOAWAY NO_ERROR naming the last stream, then the close once that is written |

While a stream serves a request, that request's deadline bounds whatever the connection holds for it, so a client that stops reading a long response, or in the middle of a request's DATA frame, loses its connection only when the request ends, and the connection's other streams with it. An open header block is the exception: it stops every other frame of the connection and its CONTINUATION frames must follow without a gap (RFC 9113 §6.10), so it stays under the stall deadline. Every request's finish, whatever ended it and wherever it ran, queues its connection for a turn (`request_finish.zig:finishRequest`), whose drive files the deadline the connection then calls for. A close that flushes its GOAWAY is bounded by the stall deadline, counted from the later of the last byte and the close's decision, so a client that stopped reading before an idle or pre-request expiry still gets a whole stall period to take the GOAWAY. The heap is re-keyed lazily: a deadline that moves later, as the stall deadline does with every byte, only changes the state it follows from, and its old entry, when it expires, files the later one; only a deadline that appears or moves earlier touches the heap at once, at the end of every drive, the loop's turn of a connection and the reader's drive of one with bytes waiting alike (`deadline_driver.zig:syncConnectionDeadline`, `connection_flow.zig:driveHttp2`).
