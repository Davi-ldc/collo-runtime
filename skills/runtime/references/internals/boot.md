# Boot and shutdown

This reference follows a node's processes from the command line to the exit status: the roles of the one binary, the server's boot in order with the reason each step sits where it does, the zygote's preparation and fork loop, a worker's birth up to `WorkerReady`, and the shutdown with what it leaves on disk. The server's boot is in `runtime/src/server/boot/` and `server/main.zig`, the zygote and the worker child are in `runtime/src/zygote/`, and the host's side of the zygote contract is in `runtime/src/host/` and `zygote/host_client.zig`; their `//!` headers own the mechanics. [security.md](security.md) owns the worker's sandbox steps, [scheduler.md](scheduler.md) the launcher and the reaper, [egress.md](egress.md) the gateway's own boot and sandbox, and [request.md](request.md) what an ingress lane does with a connection. A reference such as `fork_loop.zig:serveForkRequests` names a file and a symbol in it. A bare file name is in `server/boot/`, `zygote/` or `host/`; `root.zig` and `cgroup.zig` always carry their directory; any other path is relative to `runtime/src/`.

## One binary

The binary's entry, `main.zig:boot` at the root of `runtime/src/`, chooses the role from the base name of `arg0` before it reads an argument. `collo-zygote` (`fork_loop.zig:process_name`) runs the zygote, and `collo-egress-gateway` (`egress/gateway/launch.zig:process_name`) runs the gateway, which refuses any argument (`egress/gateway/root.zig:runFromInheritedControlFd`). Any other name reads a command: `serve` boots the server (`server/boot/root.zig:serve`), and anything else, or no command, prints the usage line and exits with status 2. A worker never enters `main`: it is a `clone3` child of the zygote and runs the zygote's code from the clone on (`child_boot.zig:workerChildMain`). The server and the gateway allocate from the root allocator, a `DebugAllocator` in Debug builds and `smp_allocator` otherwise; the zygote and a worker child allocate their process-lifetime state from `smp_allocator` (`warmup.zig`, `child_boot.zig`).

| Process | Started by | How | Starts with |
| --- | --- | --- | --- |
| server | the operator | `collo serve` | the operator's environment, descriptors and cgroup |
| zygote | the boot thread (`host_client.zig:spawnZygote`) | a spawn of the server's own binary under `collo-zygote` (`common/os.zig:process.spawnInternal`) | its control socket at descriptor 3, the trace pipe's write end at 4 when the trace is logged, the server's standard descriptors and an environment of fixed values |
| gateway | the launcher thread, at the first launch's session attach and after a loss (`server/gateway/manager.zig:Manager.attachWorker`, `Manager.prewarm`) | the same spawn under `collo-egress-gateway` | its control socket at descriptor 3 and the server's standard descriptors; [egress.md](egress.md#the-gateway-process) has its environment |
| worker | the zygote's fork loop (`fork_loop.zig:serveForkRequests`) | `clone3` with `CLONE_INTO_CGROUP`, `CLONE_PIDFD`, `CLONE_CHILD_SETTID` and `CLONE_CHILD_CLEARTID`, with no exec | the zygote's address space, its init socket and, with a trace, the trace pipe's write end |

The spawn is a vfork-style clone (`CLONE_VM`, `CLONE_VFORK`, `CLONE_PIDFD`) on a stack of its own that execs the binary, as glibc's `posix_spawn` makes it, so the caller gets the child's pidfd from the same system call that creates the child and no window exists in which a failure leaves the child unreaped; a child whose exec fails is reaped before the spawn returns its error. Both spawned processes start with an empty signal mask as the leaders of new sessions, with every descriptor from 3 up closed but the mapped ones, close-on-exec or not (`common/os.zig:process.spawnInternal`). The zygote writes each child's `OOM_SCORE_ADJ_WORKER` (500) after the clone, and the server writes the gateway's `OOM_SCORE_ADJ_EGRESS_GATEWAY` (300) and the zygote's `OOM_SCORE_ADJ_ZYGOTE` (200) after each spawn (`common/limits/process.zig`); a failed write only warns, and the server writes no score of its own. Every score is at or above 0, and raising a score takes no privilege, so each write succeeds unprivileged; the kernel picks workers first, then the gateway, then the zygote, and the server last while its own score, 0 unless whoever starts it sets one, stays below the zygote's.

`command_line.zig:parse` reads `collo serve <collo.json | entry.js> [--listen <host:port>]`. A path ending in `.json` names a configuration file, and any other path names an entry module, for which `server/config/synthesize.zig:synthesize` builds the configuration a file would: one worker named after the file's stem, one route `/*` and every built-in default. `--listen` replaces `settings.listen`, whose default is `127.0.0.1:8443` (`server/config/model.zig:default_listen`), and port 0 binds an ephemeral port. A malformed command line prints its reason and the usage line and exits with status 2.

## The server's boot

`server/boot/root.zig:serve` runs these steps in order on the main thread, which has started no other thread yet; its `//!` header states the same order:

| Step | What | Where | Why there |
| --- | --- | --- | --- |
| 1 | refuse an effective uid of 0 | `server/boot/root.zig:rootRefusal` | the zygote, every worker and the gateway run as the server's user, so a worker that escapes its sandbox holds what that user holds |
| 2 | block SIGHUP, SIGINT and SIGTERM, then start the signal monitor | `signals.zig:Signals.start` | every later thread inherits the mask, and a thread with one of them unblocked would take its default action and end the process without cleanup; nothing that needs cleanup exists yet |
| 3 | raise the soft open-file limit to the hard one | `server/boot/root.zig:raiseOpenFileLimit` | the routes keep `artifact_descriptors_max` descriptors open from step 5 on |
| 4 | load or synthesize the configuration, apply `--listen`, check the certificate files and the analytics directory it names | `server/boot/root.zig:loadConfiguration`, `checkConfiguredPaths` | a failure names the key that holds the path; `Server.init` opens them again |
| 5 | build the route table, every definition's artifact and the gateway's network policy image | `server/routes/root.zig:Routes.init` | every module a worker can load is read from disk here, once, into one sealed artifact per definition (`common/ipc/module_pack.zig`). Each definition's modules are read only from its root, the deepest directory holding its routes' entries, which no import widens; for `collo serve app.js` that is the entry's directory, and a `collo.json` resolves each entry against its own directory first ([security.md](security.md#what-the-server-reads-for-a-definition)). The artifact holds each module its routes reach, once, stored as Latin-1 or UTF-16 so the engine wraps it without a copy, and every route as its entry's module index and its bindings, in route order. A module's key is its public path `/var/task/<path>`, where `<path>` lies below the key directory: the root, or the ancestor of it that a packed import climbs to before it descends again (`server/routes/module_graph.zig:Graph.keyDirectory`), so the engine's lexical resolution of every relative import lands on a packed key. A configuration that cannot be served therefore fails before any child process exists ([request.md](request.md#admission) owns matching) |
| 6 | require a cipher the kernel can take over | `server/tls/root.zig:KtlsNegotiationPolicy.fromCapabilities` | it depends on no later step, so a missing `tls` module fails the boot before any child process exists |
| 7 | create the worker cgroup root | `cgroup_root.zig:WorkerCgroupRoot.init` | a delegated placement moves only the server out of its cgroup, and a child spawned earlier would stay there and keep the controllers off; it sweeps what dead hosts left before this server's first worker |
| 8 | spawn the zygote, with a trace pipe exactly when the trace is logged (`trace_drain.zig:loggingRequested`), and wait for its ready report | `host_client.zig:spawnZygote` | the supervisor borrows the zygote; the report follows its preparation, so no fork request reaches an unprepared zygote |
| 9 | start the trace drain, which starts nothing without a pipe | `trace_drain.zig:TraceDrain.init` | the zygote's boot events wait in the pipe until it starts |
| 10 | take the configured certificate, or generate a self-signed one and write a warning | `server/tls/self_signed.zig:SelfSignedCertificate.generate` | it needs the listen address from step 4 and must exist before step 11 builds the TLS context; a generated key is zeroed when `Server.init` returns, whether or not it succeeded |
| 11 | build the server: TLS context, lane plan, listeners, gateway manager, analytics sink, supervisor | `server/main.zig:Server.init` | it needs the routes, the zygote, the cgroup root and the certificate; the listeners listen from here, so a connection waits in the backlog until the lanes start |
| 12 | attach the signal monitor to the server | `signals.zig:Signals.attach` | a stop or a reopen that came during the boot reaches the server now |
| 13 | run the server until it stops | `server/main.zig:Server.run`, `server/ingress/service.zig:Service.run` | last, once the signal monitor can stop it; the service writes `collo: listening on https://<address>` once every lane accepts |

### Signals

`signals.zig:Signals` reads the three signals from one signalfd on the monitor thread, the first thread after the main one. The first SIGINT or SIGTERM records the stop and calls the attached server's `requestStop`; during the boot nothing is attached yet, so `attach` makes the call, the boot runs to its end and the server stops before it serves. A second one, at any time from step 2 until the monitor joins at the end of the teardown, writes `collo: a second shutdown signal ends the server without draining` and calls `exit_group` with 128 plus the signal number. SIGHUP never counts toward a stop: it asks the analytics sink to reopen its record files at its next flush (`server/analytics/sink.zig:Sink.requestReopen`), and one that arrives while nothing is attached is delivered by `attach`. The zygote and the gateway lead sessions of their own, so a terminal's Ctrl-C or hang-up reaches only the server, which stops them itself. A monitor whose `poll` fails logs at `err` and stops the server, and the boot then exits with status 1, since no signal asked for the stop.

### The worker cgroup root

`cgroup_root.zig:WorkerCgroupRoot.init` takes one of two placements, and the header of `host/cgroup_root.zig` owns the reasoning. With `COLLO_WORKER_CGROUP_ROOT` unset or empty the placement is delegated: the server's own cgroup, read from `/proc/<pid>/cgroup`, must be delegated to it, and the server moves itself, threads included, into `<own>/main`, enables `+memory +cpu +pids` on `<own>`, creates `<own>/workers` and enables them there too (`cgroup_root.zig:prepareDelegatedSubtree`), then kills and removes every `worker-*` leaf a previous run left in `<own>/workers`. With the variable naming a delegated, process-free directory, the server enables the controllers on it and claims `host-<pid>-<start>-<n>` under it, after reclaiming the `host-*` directories of hosts that are provably gone (`cgroup_root.zig:sweepDeadHostDirs`, by the proof `host_identity.zig` owns: no process has the pid, or the pid's start time differs); the server, the zygote and the gateway then stay in the server's own cgroup. A placement that cannot bound worker memory fails the boot with status 1 and a line that says how to provide one.

| Directory | Created | Holds |
| --- | --- | --- |
| `<own>/main` | by a delegated boot | the server, and the zygote and the gateway, which inherit its cgroup |
| `<own>/workers` | by a delegated boot | the worker leaves |
| `<root>/host-<pid>-<start>-<n>` | by a boot under `COLLO_WORKER_CGROUP_ROOT`; `<start>` is the server's start time in ticks since boot | this server's worker leaves, out of reach of other hosts that share the root |
| `worker-<fork job id>` | by the launcher before each fork (`cgroup_root.zig:WorkerCgroupRoot.createWorkerDir`) | one worker, under `memory.high` at its definition's memory limit, `memory.max` at 115% of it rounded down to a page, `memory.oom.group` set to 1, `cpu.max` of one core over 100 ms and `pids.max` 128 (`common/cgroup.zig:worker.configureLimitsAt`) |

The launcher numbers fork jobs from 1 at every boot (`server/supervisor/launcher.zig:Launcher.next_fork_job_id`), so a leaf a crash left behind would collide with a new id: a delegated boot clears `<own>/workers` for that reason, and `createWorkerDir` removes a leaf that already has its name, once, before it creates it again. Once its `WorkerInit` is sent, the host names a leaf only by the workers directory and the job id (`cgroup_root.zig:WorkerLeaf`): the server reads its files and removes it through that name, never through a path or a descriptor of its own, and it opens a leaf's files only beneath the workers directory with no link followed (openat2 with `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS` and `RESOLVE_NO_MAGICLINKS`, `cgroup_root.zig:openBeneath`), so a link planted as `worker-<id>` on a root that is not cgroupfs never carries a read or a `cgroup.kill` write elsewhere.

### The zygote's spawn and the trace pipe

`host_client.zig:spawnZygote` creates a SEQPACKET control socket pair and, when the caller asks for the trace (`SpawnOptions.trace`), the trace pipe, spawns the server's own binary, found through `/proc/self/exe`, as `collo-zygote` with the child's ends at `fork_loop.zig:inherited_control_fd` and, with a trace, `inherited_trace_fd`, which gives it the zygote's pidfd, writes its OOM score and waits up to `ZYGOTE_READY_TIMEOUT_MS` for `ZygoteReady`. That bound covers the VM's creation, the warmup corpus with its full collection and the helper-thread drain, and exists to catch a wedged zygote; a zygote that exits or stays silent fails the spawn, which kills and reaps it, and the boot exits with status 1. The zygote's whole environment is `fork_loop.zig:environment`, the compile-time array `TZ=UTC` and `LANG=C.UTF-8`, and nothing of the server's: the JSC and ICU caches the zygote fills before its first fork must agree with what every worker inherits, and a worker inherits it as it is. Its standard descriptors are the server's, so its errors and log lines appear on the server's stderr.

The trace pipe (`trace.zig`) exists only when the server logs the trace, in a Debug build or under `COLLO_BOOT_TRACE=1` or `COLLO_DEBUG=1` (`trace_drain.zig:loggingRequested`, which decides through `traceLogged`); without it no process of the node holds a pipe and no drain thread starts. It is nonblocking at both ends. The server keeps the read end and a write end for the launch's `host.*` events, and the zygote writes `zygote.*` events at descriptor 4, which it takes as the trace pipe when the descriptor is open and a FIFO and as no trace when it is closed; any other file there fails the zygote's boot (`fork_loop.zig:inheritedTraceFd`). Each worker child keeps that descriptor through its boot and writes `child.*` events until it closes it after its filter, with `child.trace.closed`, before its first tenant code (`child_boot.zig:Boot.closeTrace`); the child reads the descriptor only from its copy of the zygote's state, and the close clears it there (`state.zig:Zygote.closeTrace`), so no later trace call can write into a file that reuses the number. No tenant code ever holds the pipe, and the phases after the close reach the host only as boot stamps on the page. Each line is formatted within `TRACE_EVENT_BUFFER_BYTES` and written in one `write` below `PIPE_BUF`, so lines from different writers never interleave, and a line that does not fit or finds the pipe full is dropped; tracing never blocks or fails its caller. `trace_drain.zig:TraceDrain` is the pipe's only reader, a thread that keeps it empty and logs each line at info as `boot-trace <line>`. Every `std.log` line of the binary goes through `zygote/log_sink.zig:logFn` (`main.zig`'s `std_options`): to the process's standard error in the server, the zygote and the gateway, and into the worker's console ring in a worker, from the mapping of its page on ([The child](#the-child)). A read ends wherever the bytes in the pipe run out, so the drain carries a line two reads split into the next read and logs it whole, and it drops, with one line that says so, a line longer than `TRACE_EVENT_BUFFER_BYTES` with its newline, which no writer emits (`trace_drain.zig:LineAssembler`). It ends when `deinit` wakes it or every writer is gone.

### TLS

The kTLS check (`server/tls/ktls.zig:KernelCapabilities.probe`) installs throwaway keys on a loopback TCP pair for each of five cipher classes. A failure that says nothing about support is tried again, up to `ktls_probe_max_attempts` attempts, and the class then counts as missing, with a warning. `KtlsNegotiationPolicy` keeps the TLS 1.2 AES-GCM suites of the sizes the kernel takes and offers every TLS 1.3 suite when the kernel takes both AES-GCM sizes and ChaCha20, only AES-GCM when it takes both sizes without ChaCha20, and no TLS 1.3 otherwise; with nothing left the boot asks for `modprobe tls` and exits with status 1. `Server.init` probes again and builds the BoringSSL context from that second result (`server/tls/root.zig:BoringSslContext.initForKernelKtls`), so a handshake completes only with a cipher the kernel can take over; the context copies the certificate and key, zeroes its copy of the key and accepts only ALPN `h2`. Without `settings.tls` the boot generates an EC P-256 key and a certificate signed by it (`server/tls/self_signed.zig`), valid for `validity_days` from the start and naming `localhost`, `127.0.0.1`, `::1` and the listen address unless that address is unspecified, `127.0.0.1` or `::1`. Neither touches the disk, and each start presents a new key. A configured certificate or key that BoringSSL refuses exits with status 2.

### Lanes and listeners

`server/net/lane_plan.zig:build` fixes the lane count once, from the listen address. The target is the receive queue count of the interface that holds the address, or the CPUs the process may run on when the address is loopback, unspecified or held by no interface; it is capped by those CPUs and by how many lanes `MemAvailable` divided by `lane_memory_share_divisor` pays for at a lane's worst-case footprint, and each lane takes one of the first allowed CPUs. `server/net/listener.zig:IngressListeners.init` binds one nonblocking listener per lane to the same address, with `SO_REUSEPORT` when there is more than one lane and the lane's CPU as an `SO_INCOMING_CPU` hint, resolves port 0 at the first bind and listens with a backlog of 128. With more than one lane, `server/net/reuseport_bpf.zig:attachCpuSelector` then attaches a reuseport eBPF program that steers each connection to the lane pinned to the CPU that received it; a program the kernel refuses is logged, and the kernel's reuseport hash spreads connections instead. The boot logs the plan at info, and a listen address in use or held by no interface exits with status 1. Each lane thread pins itself to its CPU when it starts, and a pin that fails stops the server (`server/ingress/runner/root.zig:LaneWorker.threadMain`).

### The service and the gateway

`Server.run` builds the ingress service, whose `init` reads the launch's boot inputs from the server's environment once (`server/supervisor/launcher.zig:resolveBootInputs`): the tmpfs size `COLLO_WORKER_FS_TMPFS_MIB` asks for in MiB, which a malformed, zero or oversized value leaves at the launch's default, and the benchmark's handler stamp under `COLLO_BENCH_HANDLER=1`. Every other runtime limit is a constant of `common/limits/worker.zig`. `Server.run` then routes the gateway manager's loss reports to the service for as long as the service exists (`server/gateway/manager.zig:Manager.setDeps`). `Service.run` sets up the launcher and the reaper, which keep pointers into the service, starts the console thread, the metrics thread, the reaper, the launcher and the lanes in that order, and waits until every lane reports active before it calls `on_serving`, which writes the listening line; a lane that fails to start, or a stop that comes first, skips the line. The service's thread then checks for a stop or a lane error every `metrics_drain_stop_poll_ns`.

`collo serve` does not prewarm the gateway; `Server.prewarmEgressGateway` exists for the sandbox benchmark and the local-e2e harness. The manager spawns nothing at `init`, so the first gateway starts on the launcher thread inside the first launch's session attach, before that launch's fork request (`server/supervisor/launcher.zig:attachForLaunch`, `Manager.attachWorker`). A launch for a definition without a network grant attaches nothing and sends its child no egress descriptor (`host/launch.zig:LaunchEgress.none`), so a node none of whose definitions has a grant never spawns a gateway. The spawn waits up to `GATEWAY_READY_TIMEOUT_MS` for a gateway that reports ready only once sandboxed ([egress.md](egress.md#the-gateway-process)). A spawn that fails leaves the launch to boot its child detached and starts the launcher's reattach pass ([scheduler.md](scheduler.md#the-launcher)), which spawns again at the first launcher turn with no fork outstanding once `egress_prewarm_interval_ms` has passed since the failed attach, and from then on at most once per interval (`server/supervisor/launcher.zig:restartPass`, `prewarmForPass`).

### What the boot reports

The boot's own status lines go through `report.zig`: prefixed `collo: `, formatted on the stack within `line_bytes_max`, where a longer message is cut and ends in `...`, and written in one `write`, so one never interleaves with another thread's output. The lane plan and every other log line go through `std.log`'s default handler on stderr, the console thread writes the workers' console lines (`server/ingress/service_observability.zig:consoleThreadMain`), and the usage line is written as is. A boot writes the self-signed warning when it generated a certificate and the listening line with the bound port; a failure ends with one line that names its cause, after any line a library such as BoringSSL logs itself.

| Exit status (`server/boot/root.zig:ExitStatus`) | When |
| --- | --- |
| 0, `ok` | the server stopped because a signal asked it to |
| 1, `failure` | anything the other rows do not list, among them no kTLS cipher, no delegated cgroup subtree, a zygote that does not start, a listen address in use or held by no interface, a certificate the boot cannot generate or BoringSSL refuses once generated, a lane fault, the zygote's exit, memory exhausted during the boot, and a stop no signal asked for |
| 2, `invalid` | a malformed command line, an effective uid of 0, or a configuration that cannot be served: the file, an entry module, a path it names, or a configured certificate or key BoringSSL refuses |
| 128 plus the signal number | a second SIGINT or SIGTERM during the boot, the drain or the teardown |

## The zygote

### Preparation

`fork_loop.zig:runFromInheritedFds` reads whether descriptor 4 holds a trace pipe, creates its one VM (`state.zig:Zygote.init`), prepares it once (`fork_loop.zig:prepareZygoteAtBoot`) and only then reports ready:

| Step | What | Why there |
| --- | --- | --- |
| 1 | create the VM, which as the process's first fixes the engine's options for the whole process (`bindings/jsc/runtime/vm.cpp:collo_vm_create`) | those options bound the threads the engine can ever ask for, which a worker must start before its filter |
| 2 | read the main thread's thread-id word with `PR_GET_TID_ADDRESS` and check that it holds the thread's id (`common/os.zig:process.callingThreadIdWord`, `fork_loop.zig:Prepared.thread_id_word`) | every clone hands it to the kernel, which writes the child's id there, so a child's glibc names its own thread; a kernel without `CONFIG_CHECKPOINT_RESTORE` has no `PR_GET_TID_ADDRESS`, and the zygote refuses to prepare with a line naming the option |
| 3 | set the helper-thread idle timeout to `PREFORK_HELPER_THREAD_IDLE_TIMEOUT_NS` (`bindings/root.zig:setHelperThreadsTimeoutOverrideNs`) | before the corpus, so the helper threads it starts retire within that timeout |
| 4 | run the warmup corpus, always (`warmup.zig:runCorpus`), then a full collection and allocator trim (`collo_vm_collect_full_gc_and_trim`) | JSC builds much of its state lazily, so the corpus moves builtin bytecode, structure caches and the RegExp, JSON, URL and Promise machinery into pages every worker shares, and the collection drops the corpus's own garbage |
| 5 | prepare for the fork (`bindings/jsc/zygote/prepare_for_fork.cpp:collo_vm_prepare_for_fork`): drain the compiler worklists, finalize deferred VM cleanup, release the allocator's free pages and suspend the libpas scavenger until its thread exits | a compiler thread observes its idle timeout only while parked, so a compile still running would hold its thread past the drain; draining is what lets the corpus tier up safely |
| 6 | sleep one idle timeout, then probe `/proc/self/task` until one thread is left, at most `PREFORK_DRAIN_MAX_CHECKS` times `PREFORK_DRAIN_CHECK_INTERVAL_NS` apart (`common/os.zig:process.waitForSingleThreadedSelf`) | a fork from a multithreaded process can leave a lock held by a thread the child does not have |
| 7 | undo `MADV_DONTFORK` on every mapping but the kernel's own (`common/os.zig:process.makeAddressSpaceForkInheritable`) | JSC reserves its heaps with `MADV_DONTFORK`, and a child born without them faults on the first cell it touches; this runs after the last reservation |
| 8 | return `fork_loop.zig:Prepared`, which only the preparation makes and every fork needs | `serveForkRequests` takes it, so no fork can precede the preparation |
| 9 | install `SIGCHLD` with `SA_NOCLDWAIT` (`fork_loop.zig:installWorkerChildAutoReap`) | the kernel reaps every worker, so the zygote never waits for one |
| 10 | send `ZygoteReady` | the server sends no fork request before it |

The corpus is `warmup.js`, embedded in the binary and free of tenant code: `runCorpus` registers it as a one-module pack under `/__collo/zygote/warmup.js`, evaluates it, calls its default export inside one VM turn so its microtasks drain, requires a nonempty digest and unregisters the pack whatever the outcome (`collo_module_unregister_pack`), so every worker registers its definition's artifact on the VM it inherits. The corpus's module record stays in the main realm's registry, and its source strings keep the corpus's mapping alive in the zygote, where every worker shares it. Any failure of these steps, such as a missing `CONFIG_CHECKPOINT_RESTORE`, an exception in the corpus, a top-level await or a thread left after step 6, ends the zygote before its report; it prints its error on the server's stderr, and the server exits with status 1. The zygote applies no sandbox of its own: it keeps the server's user, namespaces and cgroup, and it holds no tenant data, since a fork request carries only a job id and a leaf and everything a worker is given reaches the child after the fork.

### The fork loop

`fork_loop.zig:serveForkRequests` answers one request at a time on the control socket. A request carries a fork job id and exactly one descriptor, the worker's cgroup leaf (`common/ipc/zygote_worker.zig:recvForkRequest`), and a request with any other count, or with a nonzero reserved field, ends the zygote before anything else runs, so no child is ever cloned into the zygote's own cgroup. The loop checks that the leaf is an empty cgroup2 directory (`zygote/worker_boot/cgroup.zig:validateEmptyWorkerCgroupDirFd`), creates the child's init socket pair, proves the zygote single-threaded again and clones the child into the leaf with a pidfd and the thread-id word (`common/os.zig:process.cloneForkWithPidFd`). The child closes the leaf, the control socket and the parent's end of the pair and never returns into the loop. The parent closes the leaf and the child's end, writes the child's OOM score, which the child cannot write itself once its root has no `/proc`, and replies with the child's pid, the parent's end of the init socket and the pidfd (`common/ipc/zygote_worker.zig:sendForkReply`). The pidfd is the server's handle on the child from then on, since the kernel may give the pid to another process once the child exits.

Every request the loop consumes gets exactly one reply, or the zygote ends. A failure that comes from this fork's resources, with the VM untouched, gets a reply with pid 0 and no descriptor (`common/ipc/zygote_worker.zig:sendForkFailed`, `fork_loop.zig:isTransientForkError`) and the loop serves on; anything that makes a reply impossible or a fork unsafe ends the zygote:

| Failure | The zygote |
| --- | --- |
| the receive refused for kernel memory (`SystemResources`), with the request still queued | retries every `RECV_PRESSURE_RETRY_INTERVAL_NS`, and ends after `RECV_PRESSURE_MAX_ATTEMPTS` |
| the server's hang-up, or a packet shorter than a request | returns from the loop and exits with status 0 |
| a truncated packet or control message, which loses the job id, an unknown kind, a nonzero reserved field, or any descriptor count but one | ends |
| a leaf that is not an empty cgroup2 directory, whatever the reason | refuses the fork and serves on |
| descriptor or memory pressure on the init socket pair, or a `/proc/self/task` it cannot read | refuses the fork and serves on |
| a second thread | ends |
| `clone3` failing with `EAGAIN`, `ENOMEM`, `EMFILE`, `ENFILE`, `EACCES`, `EPERM`, `EBUSY`, `ENOSPC`, `EOPNOTSUPP` or `EBADF` (`common/os.zig:process.cloneForkError`) | refuses the fork and serves on; `EMFILE` and `ENFILE` are descriptor pressure on the pidfd, as on the init socket pair; `EBUSY`, `ENOSPC`, `EOPNOTSUPP` and `EBADF` concern the leaf, `EACCES` and `EPERM` usually do, and when those two concern the zygote instead, refusing every fork still leaves the running workers serving |
| any other error, or a reply it cannot send | ends |

A zygote that ends prints one line naming its error on the server's stderr and exits with status 1 at once, through `_exit`, tearing nothing down, its VM included: the kernel releases everything it holds, and exit handlers could hang beside a second thread (`fork_loop.zig:runFromInheritedFds`). The launcher sees the exit on the zygote's pidfd, and the server stops with `ZygoteDied`, since nothing restarts the zygote ([scheduler.md](scheduler.md#the-launcher)). On the server's side (`host_client.zig`) one request is in flight at a time, a reply still missing after `fork_reply_timeout_ms` kills the zygote, because a late reply would read as the answer to the next request, and a pid-0 reply fails that launch alone as `fork_refused`.

### Why the loop allocates nothing and leaves the VM alone

After its preparation the loop allocates nothing and touches no VM state: its buffers are on the stack, and the receive and the replies allocate nothing (`common/ipc/zygote_worker.zig`). The conventions gate `zygote fork loop stays VM-free and allocation-free after prepare` reads `serveForkRequests` for VM and allocator calls, and requires the `Prepared` value in its parameters and the single-thread check in its body; its callees keep the rule without a gate. Every worker therefore inherits the pages the preparation left, whenever it is forked: a page the zygote wrote between two forks would be copied, and the workers born before the write and those born after it would no longer share it. `clone3` also runs no `pthread_atfork` handler, which is safe only because the loop checks that the zygote is single-threaded and leaves the allocator and the VM untouched before it forks (`common/os.zig:process.cloneForkWithPidFd`).

## A worker's birth

### The server's side

The launcher thread drives every launch, and [scheduler.md](scheduler.md#the-launcher) owns its states, bounds and failures. It numbers the fork job, creates the leaf with the definition's memory limit and one core (`common/limits/worker.zig:cpu_max_cores`) and hands it to the launch's machine (`host/launch.zig:Machine.init`), which owns its descriptor from then on. It attaches the egress session before the fork, never while a fork request is outstanding, sends the fork request and, while the zygote clones, runs the machine's local steps (`Machine.prepare`); a failure there waits in the machine for the fork reply, which must be read before the next request (`server/supervisor/launcher.zig:startFork`). At the reply, `Machine.start` takes the child and sends `WorkerInit`:

| Step | Where | Why |
| --- | --- | --- |
| create the shared page, written with state `forked` and reason `crash`, the completion eventfd, the payload ring memfd and its credit eventfd | `launch.zig:Machine.prepare` (`createShared`), `common/worker_state/page/mapping.zig:createMemfd`, which writes the header, and `mapHostReader` | a child that dies before it stores a state of its own reads as crashed; none of it needs the child, so it overlaps the clone |
| fix the child window, mint the boot token, send `WorkerInit` with its descriptor table, and close the host's copies of the leaf and the two memfds, which the mappings make unnecessary | `launch.zig:Machine.sendWorkerInit` | the steps before the send spend the launcher's time, never the child's |

`WorkerInit` (`common/ipc/messages.zig:WorkerInit`) carries what varies between workers: the memory limit the child checks against its leaf, the tmpfs size (256 MiB or the memory limit, whichever is smaller, or `COLLO_WORKER_FS_TMPFS_MIB` clamped to the limit), `flag_isolate_realm` from the definition's `isolateRealm`, `flag_egress` when the definition has a network grant, `flag_bench_handler` for the cold-start benchmark, the boot token, the init deadline, each request's CPU budget (`request_cpu_budget_ns`, from the definition's `cpuMs`, 0 for none) and the limit on JavaScript no request owns (`unowned_time_limit_ns`, the definition's `timeoutMs`). Every limit that does not vary, the CPU quota and the fetch, timer, ready-queue and request-task capacities, is a constant of `common/limits/worker.zig` that both ends compile. Its descriptor table (`common/ipc/zygote_worker.zig:WorkerInitPart`) is, in order: the state page, the completion eventfd, the ingress payload memfd, the payload credit eventfd and the leaf; the session's sixteen region descriptors when the message carries a boot token; the worker's four egress wake descriptors exactly with `flag_egress`; and the definition's artifact, always. The message alone decides the table: the sender sets `flag_egress` exactly when the wake descriptors travel, and the receiver names the first missing part of a short table and refuses any other count. `launch.zig:LaunchEgress` says which egress shape a launch sends. The count does not grow with the routes, since every route travels in the one artifact; the largest table, 26 descriptors, is `common/ipc/messages.zig:max_fds_per_message`.

### The child

The child runs on the one thread `clone3` gives it, which becomes the worker's VM thread, and ends in `_exit` on every path (`child_boot.zig:workerChildMain`). Its first act checks that glibc's CPU clock id for the thread is the one the kernel builds from the thread's own id (`child_boot.zig:validateOwnThreadIdentity`), which holds because the clone wrote the child's id into glibc's copy, and reports `internal_error` otherwise. [security.md](security.md#birth-and-confinement) lists its sandbox steps in order with why each sits where it does. The child waits for `WorkerInit` up to `WORKER_INIT_TIMEOUT_MS` once it has entered its namespaces (`child_boot.zig:Boot.receiveWorkerInit`), a bound beside the launcher's window, and exits with status 1 and no message when it passes. It then maps the page `WorkerInit` brought and installs it as the binary's `std.log` sink (`zygote/log_sink.zig`) before it closes every descriptor it was not given and points its standard input, output and error at `/dev/null` (`child_boot.zig:closeUnexpectedWorkerFds`, `common/os.zig:fd.redirectUnallowedStandardFdsToDevNull`). A log line before the sink goes to the server's stderr, which the child inherited, and every later line, from any of its threads, the sentinel's included, goes into its console ring flagged `LogLineFlags.runtime` under request id 0, which the server's console drain writes to its own stderr ([A failed boot](#a-failed-boot) says who drains the ring of a launch that fails). A line of the sentinel takes neither the sink's lock nor the ring's when another holds it and is dropped instead (`zygote/log_sink.zig:never_wait_scope`). It stamps each phase of its boot on `CLOCK_MONOTONIC` (`common/worker_state/page/boot_stamps.zig:BootPhase`, 17 phases), into a local buffer for the two phases before the page and into the page from then on, so a child stuck mid-boot leaves its progress readable; the launcher copies the stamps into the launch's trace at `WorkerReady` (`server/supervisor/launcher.zig:onReady`), which is why the child writes the last one, `ready`, before it sends that message.

Once `applyPreThread` has dropped every capability, threads may exist, and the child finishes the engine's side of the fork:

| Step | Where | What and why |
| --- | --- | --- |
| resume the VM | `bindings/jsc/zygote/prepare_for_fork.cpp:collo_vm_post_fork_child` | resets the registry of WTF automatic threads, whose entries the child inherited without their threads; restarts the libpas scavenger with no thread suspender, since suspending a thread takes signals the filter denies, with a ten-year deep-sleep timeout so its thread never retires, and with that thread created now; clears the zygote's helper-thread overrides, its memory status override, which names the zygote's cgroup, and the turn state |
| pin the helper threads, and let an idle one release its allocator cache | `bindings/root.zig:setHelperThreadsTimeoutOverrideNs` with `child_boot.zig:WORKER_HELPER_THREAD_PIN_TIMEOUT_NS`, then `setHelperThreadsCacheReleaseNs` with `common/limits/worker.zig:thread_cache_idle_release_ns` | no automatic thread retires, since one that retired after the filter could never be created again and the next compile would abort the worker, and an idle one stops its libpas allocators once, so the scavenger can reach its deep sleep in an idle worker; both right after the resume, since a thread reads them as it parks and one parked under the pin is never woken by a later change |
| reseed | `child_boot.zig`, `collo_vm_reseed_after_fork` | three seeds from `getrandom` replace the global object's, the VM's and the heap's random states, which the child inherited from the zygote like every other worker; the engine's cryptographic source keeps no state across the fork, since it calls `getrandom` on every draw |
| install `process` | `collo_vm_install_process` | `process` with `platform`, `version`, the worker's `pid` and an empty `env`, in every realm the worker will create too; each route's bindings reach only its handler's `env` |
| set the engine's collection trigger | `bindings/root.zig:setGcMaxHeapSizeOverrideBytes` | 90% of the memory limit (`common/cgroup.zig:memory.gcHeapLimitBytes`): the engine requests a collection once the bytes allocated since the last one exceed it, and no allocation fails ([memory-pressure.md](memory-pressure.md#the-engines-collection-trigger)) |
| point the engine's memory reading at the leaf | `bindings/root.zig:setMemoryStatusOverride`, `memoryStatus` | the engine reads its footprint from the leaf's `memory.current`, opened before the chroot, against the memory limit, so its critical mode engages at 80% of that limit; the child traces `child.memory_status=<footprint>,<limit>` once |
| build the runtime | `worker/api.zig:initRuntime` | builds the runtime's domains, whose capacities are the constants of `common/limits/worker.zig` (`worker/runtime/types.zig:RuntimeLimits`); it starts no thread, and WebCrypto runs inline on the VM thread |
| attach the host runtime, start the sentinel | `worker/runtime/vm_hooks.zig:attachHostRuntime`, `worker/runtime/root.zig:Runtime.startSentinel` | the sentinel's thread must exist before the filter, which denies `clone` |
| prespawn the engine's threads | `collo_vm_prespawn_compiler_threads` | starts the JS worklist's threads and the wasm worklist's thread with empty queues, and the GC collector thread through an eden collection it waits for, so every one is parked before the filter freezes the set |
| make the control socket nonblocking, install the filter | `child_boot.zig`, `zygote/worker_boot/sandbox.zig:applySeccomp` | [security.md](security.md#birth-and-confinement) |
| expose `node:fs` | `collo_vm_enable_node_fs_for_worker` | opens `node:fs` for the process, whose every operation fails with EPERM until then, and installs it, only once the worker is inside its root and its filter, which alone confine it: the facade passes every path to the kernel (`bindings/host_functions/node/fs.cpp`) |
| close the trace write end | `child_boot.zig:Boot.closeTrace` | the last step before the first tenant code, so no tenant code holds the pipe |

The set the prespawn starts is complete because the zygote's VM creation fixed the engine's options for the process: one wasm compiler thread, a JIT worklist of exactly two threads, one GC marker and so no marking helpers, no marked-block warm-up thread, and polling traps, since signal-based traps start a work-queue thread on their first use (`bindings/jsc/runtime/vm.cpp:collo_vm_create`).

### The boot token, the route's entry and WorkerReady

The child hands WorkerInit's boot token to the runtime with its options (`zygote/child_boot.zig`, `worker/runtime/types.zig:RuntimeOptions.boot_egress_token`): the token module top-level code fetches with, which is `egress_token.none` for a detached launch and for one without a network grant ([egress.md](egress.md#the-token)). After the filter and the trace's close it maps the definition's artifact, always present, parses it once (`common/ipc/module_pack.zig:parse`, `validateDefinition`: at least one route, every key under `/var/task`), takes the routes from it, registers it as the VM's one pack (`worker/modules/routes.zig:bootRegisterPack`) and evaluates every route's entry in route order (`worker/runtime/evaluations.zig:evaluateBootRoutes`), so a ready worker's first request needs no module work. After the boot a route is ready, evaluating or failed, and no request evaluates a module. Each entry runs under an evaluation, the owner of its module instance's top-level code: opened before the entry's code first runs, joined by every route that shares the instance, and holding its own copy of the boot token, so the timers, immediates and fetches of a route's top-level code belong to that route's evaluation and to no other route's. The evaluations' fetches count together against the one token's fetch limit, since each evaluation presents a copy of the one boot token (`worker/egress/fetch_runtime.zig:schedule`). With `flag_isolate_realm`, route 0 runs in the VM's main realm and every other route in a realm it creates now, after fork and after the filter (`collo_realm_create`), each with its own globals, intrinsics and module registry; without it every route shares the main realm, and routes with the same entry share its module instance. Creating a realm runs no JavaScript and gives it every install the VM made (Web APIs, console, `process`, `node:fs`) and a `Math.random` seed derived from the worker's. Realms are created fresh rather than prewarmed in the zygote: a prewarmed realm costs the zygote its heap, and the worker's first full collection writes its pages, so they turn private in every worker anyway: a worker that uses fewer realms than the zygote prewarmed pays for all of them, and one that uses them all saves about 50 KiB a realm (`runtime/bench/realm_cost.zig`, step `bench-realm-cost`, measures both). Every evaluation the boot opens is armed at the init deadline less `WORKER_INIT_CLEANUP_RESERVE_NS`, so the sentinel can stop the VM in time for the child to report `init_deadline_exceeded` and exit on its own before the launcher's window ends; it bounds the synchronous part of every route, no further route is evaluated once it has passed, and only JavaScript can be interrupted, so the native steps before it are bounded by the window alone. The boot fails when the artifact does not map, parse, pass its checks or register, when a realm cannot be created, when an evaluation cannot be opened or armed, when the deadline stops the evaluation, and when memory runs out. A route becomes ready once its entry's evaluation settles and its handler is read from the default export (`worker/modules/routes.zig:resolveHandler`): the default export itself when it is callable, and otherwise the `fetch` of an object default export, called with the object as `this`, which is the shape of Cloudflare Workers' `export default { fetch }`, of a class instance whose `fetch` is a prototype method and of Hono's `export default app`. The callable check comes first, so a function with a `fetch` property of its own is still the handler. `fetch` is read once, and the route keeps the function and its receiver rooted for the worker's life (`worker/runtime/types.zig:RouteHandler`), so assigning another `fetch` to the object later, or changing its prototype, never changes the route's handler. The read is an ordinary property get, so a getter or a proxy trap runs, under the route's evaluation like the rest of its top-level code. Every request calls the handler with `(request, env)` and no third argument (`worker/serve/dispatch.zig:invokeHandlerOrFinish`). A synchronous throw, a read of the default export or of its `fetch` that raises, or a default export that offers no handler pins its route failed and logs the cause once at boot, naming for the last the kinds it found (`default_export=<kind>`, plus `fetch=<kind>` for an object, `routes.zig:NoHandler`), and the worker still reports ready and serves its other routes but never runs that route's handler (`worker/modules/routes.zig:bootEvaluateRoute`). An evaluation whose routes all ended within the synchronous part closes at once, and with it every timer and fetch its top-level code started. Top-level awaits still pending settle after `WorkerReady`, with their timers and fetches owned by their evaluations. Only these startup evaluations copy the boot token, and the last one to close sets `startup_evaluations_ended` on the lifecycle page, which lets the server end the token early ([egress.md](egress.md#the-token)). Once every route ran, each evaluation still in flight is armed at its routes' budget: `module_eval_budget_ns` from the end of the route's own synchronous part, one deadline for the routes that share a module instance. A rejected await, like a throw, pins only its route failed, and so does an await still pending when a deadline finds its budget spent: its evaluation's, or that of a request parked on the route (`worker/modules/routes.zig:expireEvaluation`, called from `worker/serve/dispatch.zig:deadlineTimeout`). The requests parked on a failed route get the 500 a throw gives, and a settlement that comes after the expiry is ignored. A failure ends only its own route: the worker asks the server to retire it, with one `worker_retiring` notice, only when no route can serve and at least one failed on an await, or on an error of the worker's own when its await settled (`internal_error`), either of which a fresh worker may get past (`worker/modules/routes.zig:pinFailed`, `worker/runtime/retirement.zig`); a resolved await pins its route `threw` only when the default export offers no handler or reading it or its `fetch` raised (`routes.zig:settleEvaluation`); a worker whose routes all threw synchronously keeps answering 500s, since a replacement would throw again. An evaluation closes once no route evaluates under it, at its instance's settlement or expiry: the close clears its token copy, takes it out of the worker's owners and ends the timers and fetches its top-level code left behind (`worker/runtime/evaluations.zig:closeEvaluation`), so a route's top-level timers end with its own evaluation, and one route's top-level code can neither clear another's timers nor outlive its own budget. A top-level turn that never yields is terminated at its own evaluation's deadline by the sentinel, which poisons the VM for every route, so the evaluation's close folds that fire into the worker's stop whatever the routes' states (`worker/scheduler/resources.zig:disarmRequestDeadline`). A wasm settlement or a reaction that outlives its evaluation runs under the worker owner (`worker/runtime/owner.zig`), which no deadline bounds yet.

The child then marks its page ready, sends `WorkerReady` on the init socket, which becomes its control socket, and enters its event loop. The child window runs from the `WorkerInit` send to an end `launch.zig:Machine.sendWorkerInit` fixes once, `WORKER_INIT_TIMEOUT_MS` after the send. That end travels as the init deadline. Boot egress has its own deadline, fixed at the same send: the init deadline plus `MODULE_EVAL_BUDGET_NS` (`launch.zig:bootEgressDeadline`). At `WorkerReady` the launcher makes its end of the control socket nonblocking and publishes the worker; a launch whose session's gateway was lost first attaches to the current gateway, and one whose session its gateway removed fails with `egress_attach` ([scheduler.md](scheduler.md#the-launcher)).

### The module loader

A VM holds at most one module pack (`bindings/jsc/runtime/module_loader.cpp`, `collo_module_register_pack` in `bindings/include/collo/abi.h`). Registration checks the pack's header and refuses a second pack, a pack over `COLLO_MODULE_PACK_MAX_BYTES` and one with more than `COLLO_MODULE_PACK_MAX_MODULES` modules, the two bounds `abi.h` repeats from the pack format and `runtime/tests/contracts/abi.zig` pins. The worker parsed the artifact in Zig before it handed the mapping over, but the bridge trusts only what it checks itself: every later read of an index entry, a record, a specifier or a source is bounds-checked against the mapping. A module's source provider is created on its first fetch, and its text is an external string over the shared mapping, so a worker keeps no private copy of any source and every worker of a definition shares those pages. Each such string holds a reference on the pack, so the mapping outlives `collo_module_unregister_pack` until the last string over it dies, a `Function.prototype.toString` result included. Keys are public paths, which `import.meta`, stack frames (the provider's file URL) and loader errors show unchanged.

### A failed boot

| `common/ipc/messages.zig:WorkerInitFailedReason` | The child sends it for |
| --- | --- |
| `missing_metrics_fd`, `missing_ingress_payload_fd`, `missing_ingress_payload_credit_fd`, `missing_egress_shared_fd` | a `WorkerInit` table short of that descriptor |
| `invalid_worker_init` | another missing descriptor or a table of the wrong size; a failed check of the page's mapping (seals, size, version), of the message's fields or of the cgroup leaf's one pass (kind, sole membership, every limit, the swap limit included); an artifact that fails its seals, size or format (`child_boot.zig:Boot.refuse`, `failureReason`) |
| `init_deadline_exceeded` | the evaluation's deadline stopped the VM |
| `internal_error` | a packet that does not decode, a thread identity glibc does not know, a sandbox step that fails (the tmpfs or the root's layout included), a step that checks the host's input but fails for the child's own want of memory or descriptors or with an errno nothing expects (`child_boot.zig:isResourceFailure`), and any other error |

The boot's own failure path writes no field of the page, so a failed boot leaves the state `forked` and the reason `crash` the host wrote, unless the sentinel stamped `dead` with reason `memory` or `sentinel` while the boot evaluated, which `launch.zig:Machine.endedCause` reads. The child maps its failure to one reason (`child_boot.zig:failureReason`), logs `worker boot failed: <error>` once, sends the reason and exits with status 1; it reports before the runtime's teardown, so a boot the init deadline stopped answers inside the cleanup reserve. It sends one outcome at most, and none after a send that failed or after `WorkerReady`, when the init socket becomes its control channel (`child_boot.zig:Boot.reportFailure`). A child whose wait for `WorkerInit` timed out, or one that dies outright, sends nothing. While the trace is open, every failure writes one trace event, `child.boot_failed=<error>`, and `child.worker_init.recv_failed=<error>` names a receive failure. A log line the child writes before its sink is installed reaches the server's stderr directly, and a later one its console ring, which the reaper drains once it has killed the child (`server/supervisor/reaper/root.zig:reapLeftovers`): every line reaches stderr under `[<definition>]`, the runtime's under `[<definition> runtime]`, and the tenant's also enter `logs.jsonl` with `worker_id` and `worker_generation` 0, since the server numbers a worker only at its publish, and request id 0, since the child was dispatched no request. A `WorkerInit` send that finds the child's end of the init socket closed fails the launch as `worker_init_failed`, for the cause its page and leaf name (`launch.zig:Machine.start`). After the send, the launcher ends the launch on whichever it sees first, reading a queued outcome before the child's exit (`server/supervisor/launcher.zig:readyEvent`): a `WorkerInitFailed` as `worker_init_failed`; a child that dies without sending a reason as `worker_init_failed` too, since its exit hangs up the init socket no later than its pidfd turns readable, and a socket that ends without an outcome reads as the child's exit (`launch.zig:Machine.finishInitOutcome`); the end of the window as `child_window_expired`; and an outcome that does not decode, or any other failed read, as `zygote_protocol`. For `worker_init_failed` the launcher's warning names the child's reason or, for a child that sent none, whether its page or its leaf's `memory.events.local` shows that it ended for memory, by the rule the server applies to a live worker's death ([memory-pressure.md](memory-pressure.md#a-memory-death), `launch.zig:InitFailure`, `Machine.endedCause`); the trace says the same in `host.worker_init.failed=<reason>` or `host.worker_init.worker_exited=<memory|crash>`. The launcher then answers 503 to the waiters nothing else can serve and hands the child's pidfd, leaf and page to the reaper, which kills the child, waits for its exit, drains its console ring, unmaps the page and removes the leaf; the child's tmpfs ended with its mount namespace, so nothing else is left.

## Shutdown

### The drain

The first SIGINT or SIGTERM calls `server/main.zig:Server.requestStop`, which raises the stop flag and wakes every lane with a `shutdown` command. The service's thread sees the flag within `metrics_drain_stop_poll_ns` and stops what it started, in the order of `server/ingress/service.zig:Service.stopAndDrainForExit`:

| Step | What | Why in this order |
| --- | --- | --- |
| 1 | the lanes stop taking work, finish what they hold and join ([request.md](request.md#the-lane-thread)) | the launcher still runs, so a request waiting for a worker can still get one, or 503 at its deadline |
| 2 | the metrics and console threads join | their loops ended at the stop flag, and no console drain queues a retirement after the reaper's last drain |
| 3 | the launcher stops, ends its launches in flight as `stopping` and joins | their children and leaves go to the reaper's queue |
| 4 | the reaper stops and joins, and the exiting thread carries out its queue (`server/supervisor/reaper/root.zig:Reaper.drainRetirements`) | every producer of retirements has joined; shutdown owns the latency |
| 5 | the final fold drains the lanes' access rings, the workers' console rings and the analytics streams (`server/ingress/service_observability.zig:finalObservabilityFold`) | every producer has joined, so the rings are complete |

The drain lasts as long as the longest admitted request, which its deadline and the grace backstop bound ([request.md](request.md#deadlines)); a second signal ends it at once.

### The teardown

`Server.run` takes the gateway manager's loss reports off the service before the service goes, and `serve`'s deferred steps then undo the boot in reverse:

| Step | What |
| --- | --- |
| 1 | the signal monitor detaches from the server (`signals.zig:Signals.detach`) |
| 2 | `server/main.zig:Server.deinit` closes the listeners, tears down every worker a record still holds, each teardown draining the worker's last console lines and writing its line in `workers.jsonl` (`server/supervisor/supervisor.zig:Supervisor.deinit`), closes the analytics sink, which writes and syncs the tail, stops the gateway, frees the TLS context and frees the routes last, once nothing reads them |
| 3 | the trace drain stops, when one runs (`trace_drain.zig:TraceDrain.deinit`) |
| 4 | the zygote stops (`host_client.zig:SpawnedZygote.deinit`): the server closes its control socket and, with a trace, its trace write end, the zygote's loop returns on the hang-up, and the zygote exits with status 0 at once, without destroying its VM; the server waits up to `PROCESS_EXIT_WAIT_MS`, sends SIGKILL and waits as long again if it must, and reaps it |
| 5 | the worker cgroup root goes (`cgroup_root.zig:WorkerCgroupRoot.deinit`), after every leaf named under it is retired, since a leaf holds the root's descriptor by number |
| 6 | the monitor joins and the main thread's signal mask is restored (`signals.zig:Signals.deinit`) |

A live worker gets no handshake. The lanes ended every admitted request before they joined, so the workers left are idle, and `Supervisor.deinit` tears them down on the exiting thread one after another with the reaper's teardown (`server/supervisor/worker_registry.zig:teardown`, [scheduler.md](scheduler.md#the-reaper)). Each exit hangs up the liveness pipe of the worker's egress session, and the gateway drops the session on its own. The gateway stops after the workers (`server/gateway/manager.zig:Manager.deinit`): a retired gateway is killed and reaped within `REAP_NO_WAIT_MS`, and the current one has its control reader joined, gets the `shutdown` message and the close of its control socket, has up to `PROCESS_EXIT_WAIT_MS` to exit, which it does at once through `_exit` without tearing anything down ([egress.md](egress.md#the-gateway-process)), then SIGKILL and as long again, and is reaped (`server/gateway/process.zig:GatewayProcess.deinit`).

### A second signal

A second SIGINT or SIGTERM skips whatever is left. The process ends with 128 plus the signal number, and the kernel closes its descriptors: the zygote's loop returns on its control socket's hang-up and the zygote exits, the gateway ends its loop on its own control socket's hang-up ([egress.md](egress.md#the-control-wire)), and each worker's event loop returns once its control socket hangs up (`worker/scheduler/loop.zig:run`), after which the child exits with status 0. Nothing removes their cgroup leaves then.

### What stays on disk

| Left behind | After a stop | After a crash or a second signal | At the next boot |
| --- | --- | --- | --- |
| `<own>/main` and `<own>/workers` | stay; `deinit` only closes the descriptor | stay | reused: the new server moves into `<own>/main` |
| a leaf under `<own>/workers` | removed by each worker's teardown, except one still busy after `rmdir_max_attempts` tries, which is logged | stays | killed through `cgroup.kill` and removed before the zygote starts (`cgroup_root.zig:removeWorkerDirsUnder`) |
| `host-<pid>-<start>-<n>` and its leaves | removed by `deinit` | stay | removed by the next host under that root that proves the owner gone, because no process has the pid or the pid's start time differs; a `worker-*` directly under the root has no owner and stays |
| the analytics files | written and synced at close | what the last flush wrote | appended to, never truncated |

## Open points

During the drain nothing reads the lanes' access rings, and only the reaper's teardown of a worker it retires reads that worker's console ring: the metrics and console threads leave their loops when the stop flag rises (`server/ingress/service_observability.zig:metricsThreadMain`, `consoleThreadMain`), and the final fold runs only after the lanes joined. A lane that finishes more requests during the drain than its access ring holds (`server/analytics/access.zig:AccessRing.capacity`, 2048 records, while `server/ingress/lane.zig:Config.max_requests` lets a lane hold 4096 requests) drops the records past it, and a live worker that writes more than its console ring holds (`common/worker_state/page/console_ring.zig:LOG_RING_BYTES`) in that time loses the newest lines; both losses are counted.

An idle worker's libpas scavenger reaches its deep sleep only once every thread that allocated has stopped its allocators, since a worker has no thread suspender to stop them by force. The engine's helper threads stop theirs after `thread_cache_idle_release_ns` of idleness (`child_boot.zig`, `bindings/root.zig:setHelperThreadsCacheReleaseNs`); the VM thread has to call `bindings/root.zig:releaseThreadAllocatorCache` when it goes idle, and any thread that parks with its cache keeps the scavenger polling every period (`bindings/jsc/zygote/prepare_for_fork.cpp:resumeFastMallocScavengerForSandbox`).

Without a prewarm, the first cold start of a node pays the gateway's spawn, up to `GATEWAY_READY_TIMEOUT_MS`, and a gateway that can never start never fails the boot: workers boot detached and every fetch is refused, while the launcher retries the spawn every `egress_prewarm_interval_ms` from the failed attach, warning at the failed attach and at the first failed retry (`server/supervisor/launcher.zig:attachForLaunch`, `prewarmForPass`).
